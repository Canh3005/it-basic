Chương 10 · JWT & OAuth2

JWT & OAuth2 — xác thực stateless cho API hiện đại

Chương 9 dùng HTTP Basic: gửi email + mật khẩu ở mọi request — không thể chấp nhận cho ứng dụng thật. Các SPA (React), mobile app và microservice cần một cách khác: đăng nhập một lần, nhận token ngắn hạn, rồi mang token đó theo mỗi request. Chương này xây hệ thống đó bằng JWT trên chính SecurityFilterChain đã học, thêm refresh token có xoay vòng, và đặt tất cả vào bức tranh rộng hơn của OAuth2/OpenID Connect.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-9
🎯 Mục tiêu chương
  • So sánh session và token; biết khi nào chọn cái nào.
  • Đọc hiểu cấu trúc JWT (header, payload, chữ ký) và các claim chuẩn; biết JWT ký chứ không mã hoá.
  • Cài đăng nhập → access token → gọi API bằng Spring OAuth2 Resource Server (Nimbus).
  • Thiết kế refresh token với rotation và phát hiện tái sử dụng.
  • Xử lý bài toán thu hồi token và biết nơi lưu token ở frontend.
  • Tránh các lỗi JWT kinh điển (secret yếu, thiếu exp, không kiểm iss/aud).
  • Hiểu OAuth2/OIDC: các vai, Authorization Code + PKCE; tích hợp IdP (Google, Keycloak) ở mức nhập môn.

2. JWT — cấu trúc và bản chất

JWT (JSON Web Token, RFC 7519) là chuỗi gồm ba phần Base64URL ngăn bởi dấu chấm:

}
Chữ ký (HS256)
signature = HMAC-SHA256( base64url(header) + "." + base64url(payload), secretKey )
JWT được ký (chống sửa), KHÔNG được mã hoá (ai cầm token cũng đọc được payload). Chỉ cần Base64-decode là thấy hết. Vì vậy: không bao giờ đặt mật khẩu, số thẻ, dữ liệu nhạy cảm vào payload. Chữ ký đảm bảo toàn vẹn & xuất xứ, không đảm bảo bí mật.

4. Cài đặt với Spring OAuth2 Resource Server

Có hai cách: tự viết filter đọc JWT (bằng jjwt), hoặc dùng hỗ trợ JWT có sẵn của Spring Security (Nimbus JOSE). Chọn cách sau: ít code bảo mật tự viết = ít chỗ sai, và cùng cơ chế dùng được khi sau này đổi sang IdP ngoài.

pom.xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-oauth2-resource-server</artifactId>   <!-- đã gồm Nimbus JOSE + JWT -->
</dependency>
application.yml + AppProperties
app:
  jwt:
    secret: ${JWT_SECRET}            # >= 32 BYTE ngẫu nhiên (xem chương 3 về bí mật); thiếu → fail fast
    issuer: shop-api
    access-ttl: 15m
    refresh-ttl: 14d
JwtConfig.java
@Configuration
class JwtConfig {

    @Bean
    SecretKey jwtKey(AppProperties props) {
        byte[] bytes = props.jwt().secret().getBytes(StandardCharsets.UTF_8);
        if (bytes.length < 32) throw new IllegalStateException("JWT secret phải >= 32 byte cho HS256");
        return new SecretKeySpec(bytes, "HmacSHA256");
    }

    @Bean
    JwtEncoder jwtEncoder(SecretKey key) {                       // ký token
        return new NimbusJwtEncoder(new ImmutableSecret<>(key));
    }

    @Bean
    JwtDecoder jwtDecoder(SecretKey key, AppProperties props) {  // kiểm token
        NimbusJwtDecoder decoder = NimbusJwtDecoder.withSecretKey(key).macAlgorithm(MacAlgorithm.HS256).build();
        decoder.setJwtValidator(JwtValidators.createDefaultWithIssuer(props.jwt().issuer()));   // exp, nbf + iss
        return decoder;
    }

    @Bean
    JwtAuthenticationConverter jwtAuthConverter() {              // claim "roles" → authorities ROLE_*
        JwtGrantedAuthoritiesConverter g = new JwtGrantedAuthoritiesConverter();
        g.setAuthoritiesClaimName("roles");
        g.setAuthorityPrefix("ROLE_");
        JwtAuthenticationConverter c = new JwtAuthenticationConverter();
        c.setJwtGrantedAuthoritiesConverter(g);
        return c;
    }

    @Bean
    AuthenticationManager authenticationManager(AuthenticationConfiguration cfg) throws Exception {
        return cfg.getAuthenticationManager();                   // dùng UserDetailsService + PasswordEncoder của chương 9
    }
}
SecurityConfig.java — thay httpBasic bằng resource server
@Bean
SecurityFilterChain api(HttpSecurity http, JwtAuthenticationConverter conv,
                        JsonAuthenticationEntryPoint entryPoint, JsonAccessDeniedHandler denied) throws Exception {
    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**", "/actuator/health").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth
            .jwt(jwt -> jwt.jwtAuthenticationConverter(conv))
            .authenticationEntryPoint(entryPoint)                  // 401 dạng ProblemDetail khi token thiếu/sai/hết hạn
            .accessDeniedHandler(denied))
        .exceptionHandling(e -> e.accessDeniedHandler(denied))
        .csrf(csrf -> csrf.disable())                              // OK: Bearer header, không cookie (chương 9 mục 8)
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .cors(Customizer.withDefaults());
    return http.build();
}

4.1. Phát token khi đăng nhập

TokenService.java
@Service
class TokenService {

    private final JwtEncoder encoder;
    private final AppProperties props;
    private final Clock clock;                                          // tiêm Clock để test được (chương 2, 11)
    // constructor ...

    String issueAccessToken(Authentication auth) {
        Instant now = clock.instant();
        List<String> roles = auth.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .map(a -> a.startsWith("ROLE_") ? a.substring(5) : a)      // "ROLE_ADMIN" → "ADMIN" (converter thêm lại)
                .toList();

        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer(props.jwt().issuer())
                .subject(auth.getName())
                .issuedAt(now)
                .expiresAt(now.plus(props.jwt().accessTtl()))
                .id(UUID.randomUUID().toString())                          // jti
                .claim("roles", roles)
                .build();

        JwsHeader header = JwsHeader.with(MacAlgorithm.HS256).build();
        return encoder.encode(JwtEncoderParameters.from(header, claims)).getTokenValue();
    }
}

@RestController
@RequestMapping("/api/auth")
class AuthController {
    private final AuthenticationManager authManager;
    private final TokenService tokens;
    private final RefreshTokenService refreshTokens;
    // constructor ...

    @PostMapping("/login")
    TokenResponse login(@Valid @RequestBody LoginRequest req) {
        Authentication auth = authManager.authenticate(               // sai mật khẩu → BadCredentialsException → 401
                UsernamePasswordAuthenticationToken.unauthenticated(req.email(), req.password()));
        return new TokenResponse(tokens.issueAccessToken(auth), "Bearer", 900, refreshTokens.issue(auth.getName()));
    }
}

public record LoginRequest(@NotBlank @Email String email, @NotBlank String password) { }
public record TokenResponse(String accessToken, String tokenType, long expiresIn, String refreshToken) { }

5. Refresh token và rotation

Refresh token sống lâu ⇒ nếu bị đánh cắp, kẻ cắp có thể làm mới vô hạn. Giảm rủi ro bằng rotation: mỗi lần dùng refresh token, phát cặp mới và vô hiệu token cũ. Nếu token cũ xuất hiện lại (bị dùng hai lần) ⇒ chắc chắn có kẻ sao chép ⇒ thu hồi cả họ token.

RefreshToken.java
@Entity
@Table(name = "refresh_tokens", indexes = @Index(columnList = "tokenHash", unique = true))
public class RefreshToken {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;
    @Column(nullable = false, unique = true, length = 64) private String tokenHash;   // SHA-256 hex — KHÔNG lưu token gốc
    @Column(nullable = false) private String userEmail;
    @Column(nullable = false) private String familyId;      // mọi token xoay vòng từ một lần đăng nhập chung family
    @Column(nullable = false) private Instant expiresAt;
    private boolean used;                                   // đã đổi lấy token mới
    private boolean revoked;
    // constructor, getter ...
}
RefreshTokenService.java
@Service
class RefreshTokenService {

    private static final SecureRandom RNG = new SecureRandom();
    private final RefreshTokenRepository repo;
    private final AppProperties props;
    private final Clock clock;
    // constructor ...

    @Transactional
    public String issue(String email) { return create(email, UUID.randomUUID().toString()); }

    @Transactional(noRollbackFor = TokenReuseException.class)       // phải COMMIT việc thu hồi dù ném lỗi
    public Rotated rotate(String presented) {
        RefreshToken t = repo.findByTokenHash(sha256(presented))
                .orElseThrow(() -> new InvalidTokenException("Refresh token không hợp lệ"));

        if (t.isRevoked() || t.getExpiresAt().isBefore(clock.instant()))
            throw new InvalidTokenException("Refresh token hết hạn hoặc đã thu hồi");

        if (t.isUsed()) {                                           // ⚠️ đã đổi rồi mà lại xuất hiện → bị đánh cắp
            repo.revokeFamily(t.getFamilyId());                      // UPDATE … SET revoked = true WHERE family_id = ?
            throw new TokenReuseException("Phát hiện tái sử dụng refresh token — mọi phiên bị thu hồi");
        }
        t.markUsed();
        return new Rotated(t.getUserEmail(), create(t.getUserEmail(), t.getFamilyId()));   // cùng family
    }

    private String create(String email, String familyId) {
        byte[] raw = new byte[32]; RNG.nextBytes(raw);                              // 256 bit ngẫu nhiên mật mã
        String token = Base64.getUrlEncoder().withoutPadding().encodeToString(raw);
        repo.save(new RefreshToken(sha256(token), email, familyId, clock.instant().plus(props.jwt().refreshTtl())));
        return token;                                                // chỉ trả MỘT LẦN cho client
    }

    private static String sha256(String s) { /* MessageDigest SHA-256 → hex */ }
}
Lưu hash của refresh token, không lưu token gốc — giống mật khẩu: lộ DB không đồng nghĩa lộ phiên đăng nhập. Dùng SHA-256 là đủ (token là chuỗi ngẫu nhiên 256 bit, không cần hash chậm như mật khẩu do con người đặt). Và dùng SecureRandom, không dùng Random/UUID đơn thuần cho token nhạy cảm.

5.1. Đăng xuất

POST /api/auth/logout {refreshToken} ⇒ đánh dấu revoked cả family; client xoá token cục bộ. Access token còn sống đến khi hết hạn (tối đa 15 phút) — mục 6 giải quyết nếu cần chặt hơn.

9. OAuth2 và OpenID Connect — bức tranh lớn

Cái bạn vừa xây là hệ xác thực tự quản. Nhưng khi người dùng bấm "Đăng nhập bằng Google", hoặc công ty có SSO nội bộ, ta bước vào OAuth 2.0 (uỷ quyền) và OpenID Connect – OIDC (xác thực, xây trên OAuth2). Bốn vai:

VaiLà aiVí dụ
Resource OwnerNgười dùng sở hữu dữ liệuBạn
ClientỨng dụng muốn truy cập thay mặt người dùngWeb shop của bạn (React + Spring)
Authorization Server (IdP)Xác thực người dùng, phát tokenGoogle, Keycloak, Auth0, Azure AD, AWS Cognito
Resource ServerAPI bảo vệ bằng tokenAPI Spring của bạn — đúng thứ ta vừa cấu hình

9.1. Authorization Code + PKCE — luồng chuẩn cho SPA/mobile

1. Client tạo PKCE
Sinh code_verifier ngẫu nhiên; code_challenge = SHA256(verifier)
2. Chuyển hướng
Tới IdP /authorize?…&code_challenge=… — người dùng đăng nhập tại IdP, không phải ở app bạn
3. Đồng ý
Người dùng chấp thuận quyền (scope)
4. Trả code
IdP chuyển về redirect_uri kèm code dùng một lần
5. Đổi token
Client gửi code + code_verifier tới /token
6. Nhận token
access_token (+ id_token OIDC, + refresh_token)
7. Gọi API
Authorization: Bearer access_token → Resource Server kiểm bằng khoá công khai của IdP
PKCE chặn kẻ chặn được code: không có code_verifier thì không đổi được token.
⚠️ Đừng dùng Implicit / Password grant

Implicit (token trả trong URL) đã bị khai tử; Resource Owner Password Credentials (ứng dụng nhận mật khẩu của người dùng rồi đem tới IdP) đã bị OAuth 2.1 loại bỏ. Luôn Authorization Code + PKCE.

9.2. API của bạn làm Resource Server cho IdP ngoài

Nếu giao việc đăng nhập cho Keycloak/Auth0/Google, API Spring không cần tự phát token nữa — chỉ cần tin IdP. Chỉ một dòng cấu hình: Spring tải tập khoá công khai (JWKS) từ IdP và tự kiểm chữ ký, iss, exp:

application.yml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://keycloak.example.com/realms/shop     # tự đọc /.well-known/openid-configuration → jwks_uri

Phần còn lại của SecurityFilterChain (oauth2ResourceServer(jwt)) giữ nguyên — đây là lý do ta chọn Resource Server ở mục 4: chuyển từ "tự phát token" sang "IdP phát token" chỉ là đổi nguồn khoá. Cần ánh xạ realm_access.roles (Keycloak) sang authority thì tuỳ biến JwtAuthenticationConverter.

9.3. "Đăng nhập bằng Google" cho ứng dụng web server-side

application.yml
spring:
  security:
    oauth2:

        registration:

            client-secret: ${GOOGLE_CLIENT_SECRET}

http.authorizeHttpRequests(a -> a.anyRequest().authenticated())

Bài tập

Đăng nhập → JWT

Dựa trên chương 9, cài POST /api/auth/login, TokenService, và chuyển SecurityFilterChain sang oauth2ResourceServer.

  • Giải mã payload bằng base64 -d (hoặc jwt.io) — liệt kê các claim.
  • Sửa một ký tự trong payload rồi gửi lại: mã trả về? Vì sao?
  • Đợi token hết hạn (đặt TTL 30 giây để thử): mã trả về?
Gợi ý

Sửa payload ⇒ chữ ký không còn khớp ⇒ 401 (Invalid signature). Hết hạn ⇒ 401 (Jwt expired). Đó là hai lớp bảo vệ mà NimbusJwtDecoder làm sẵn.

Thợ săn secret yếu

Tạo token HS256 bằng secret secret123. Dùng hashcat -m 16500 hoặc script Python thử từ điển để dò lại secret.

  • Dò được trong bao lâu? Từ đó tự ký token có roles: ["ADMIN"] và gọi /api/admin/… (trên môi trường của bạn).
  • Sinh secret đúng: openssl rand -base64 48. Nâng JwtConfig để từ chối secret < 32 byte (đã có trong mục 4).
  • Giải thích vì sao RS256 không có kịch bản này ở các dịch vụ chỉ kiểm token.
Gợi ý

HS256: ai có secret đều ký được. RS256: dịch vụ chỉ cầm khoá công khai — có kiểm được nhưng không thể ký. Đó là lý do hệ thống nhiều dịch vụ dùng bất đối xứng. Chỉ thực hành trên hệ thống của chính bạn.

Refresh token rotation

Cài POST /api/auth/refresh theo mục 5.

  • Đăng nhập, lấy R1. Gọi refresh với R1 → nhận R2. Gọi lại với R1 — chuyện gì xảy ra? R2 còn dùng được không?
  • Viết test mô phỏng "kẻ cắp dùng R1 sau khi người dùng thật đã đổi sang R2".
  • Vì sao rotate có noRollbackFor = TokenReuseException.class?
Gợi ý

Dùng lại R1 ⇒ TokenReuseException ⇒ cả family bị revoked ⇒ R2 cũng chết (người dùng thật phải đăng nhập lại — chấp nhận để chặn kẻ cắp). Nếu không noRollbackFor, ném exception sẽ rollback luôn lệnh revokeFamily ⇒ việc thu hồi biến mất!

Đá người dùng ra ngay

Khi admin khoá userX, access token đang sống của họ phải vô hiệu trong ≤ 1 giây.

  • Cài token_version (claim ver) và OAuth2TokenValidator so với DB.
  • Đo chi phí thêm một lần tra/request; thêm cache 30 giây (Caffeine). Đánh đổi gì?
  • So với denylist jti trên Redis: khi nào chọn cái nào?
Gợi ý

Validator tuỳ biến thêm vào DelegatingOAuth2TokenValidator. Cache 30 giây ⇒ cửa sổ thu hồi tối đa 30 giây — chấp nhận được? Muốn tức thì: Redis denylist/pub-sub xoá cache.

Resource Server cho Keycloak

Chạy Keycloak bằng Docker (quay.io/keycloak/keycloak start-dev), tạo realm shop, client công khai, một user. Lấy token qua Authorization Code (hoặc Direct Access Grants chỉ để thử).

  • Cấu hình API chỉ bằng issuer-uri.
  • Gọi API bằng token của Keycloak — thành công?
  • Role nằm ở realm_access.roles: viết JwtAuthenticationConverter ánh xạ sang ROLE_*.
Gợi ý

Spring tự lấy JWKS từ ${issuer-uri}/.well-known/openid-configuration. Converter: đọc jwt.getClaimAsMap("realm_access").get("roles") rồi map thành SimpleGrantedAuthority("ROLE_" + r).

Quiz

Q1

JWT gồm những phần nào? Nó được mã hoá hay chỉ được ký?

Xem đáp án
✓ Đáp án

Ba phần Base64URL: header (thuật toán), payload (claims), signature. Chỉ được ký — ai cầm cũng đọc được payload. Chữ ký đảm bảo toàn vẹn và xuất xứ, không đảm bảo bí mật ⇒ không đặt dữ liệu nhạy cảm vào payload.

Q2

Vì sao cần cả access token và refresh token?

Xem đáp án
✓ Đáp án

Access token ngắn hạn và stateless ⇒ nếu bị lộ, thiệt hại giới hạn trong vài phút, và API kiểm rất nhanh. Refresh token dài hạn nhưng do server kiểm soát (lưu hash, thu hồi, rotation) giúp người dùng không phải đăng nhập lại liên tục. Hai loại kết hợp cho cả an toàn lẫn trải nghiệm.

Q3

Refresh token rotation là gì và "phát hiện tái sử dụng" hoạt động ra sao?

Xem đáp án
✓ Đáp án

Mỗi lần đổi refresh token, server phát cặp mới và đánh dấu token cũ đã dùng. Nếu token đã dùng lại xuất hiện ⇒ có bản sao (bị đánh cắp) ⇒ server thu hồi cả họ (family) token đó, buộc đăng nhập lại.

Q4

JWT khó thu hồi — có những cách xử lý nào?

Xem đáp án
✓ Đáp án
  • TTL access token rất ngắn (thường đủ).
  • token_version của user kiểm lúc xác thực.
  • Denylist jti (Redis, TTL = thời gian còn lại).
  • Token opaque + introspection (đánh đổi: mỗi request một lần gọi IdP).
Q5

HS256 và RS256 khác nhau ra sao? Khi nào dùng RS256?

Xem đáp án
✓ Đáp án

HS256 dùng một khoá bí mật chung — ai kiểm được cũng ký được. RS256 dùng khoá riêng để ký, khoá công khai để kiểm — dịch vụ chỉ cần khoá công khai (JWKS), không thể giả mạo token. Dùng RS256/ES256 khi có nhiều dịch vụ hoặc IdP bên ngoài.

Q6

Authorization Code + PKCE giải quyết gì? Vì sao không dùng Implicit?

Xem đáp án
✓ Đáp án

Cho SPA/mobile (client không giữ được bí mật) đổi code lấy token an toàn: PKCE gắn code với code_verifier chỉ client gốc biết ⇒ kẻ chặn code vô dụng. Implicit trả token ngay trên URL (lộ qua lịch sử, referrer) nên đã bị loại bỏ.

Tổng kết

Sau chương 10, bạn đã nắm:

  • Session (stateful) vs token (stateless): chọn theo kiến trúc; JWT hợp SPA/mobile/microservice.
  • JWT = header.payload.signature — ký không mã hoá; luôn có exp, kiểm iss/aud, ép thuật toán phía server.
  • Dùng Spring OAuth2 Resource Server (NimbusJwtEncoder/Decoder, JwtAuthenticationConverter) thay vì tự viết filter.
  • Access token ngắn + refresh token opaque, lưu hash, rotation + phát hiện tái sử dụng.
  • Thu hồi: TTL ngắn + token_version, hoặc denylist jti; lưu ở trình duyệt: access trong bộ nhớ, refresh trong cookie HttpOnly.
  • OAuth2/OIDC: Authorization Code + PKCE; API của bạn là Resource Server; issuer-uri để dùng Keycloak/Auth0/Google; không tự viết SSO/MFA.

Kiểm thử Spring Boot — từ unit test đến Testcontainers

Code backend không có test là code không dám sửa. Spring Boot cho bạn một bộ công cụ kiểm thử rất đầy đủ — nhưng cũng dễ lạm dụng: gắn @SpringBootTest lên mọi test làm bộ test chạy 10 phút và không ai muốn chạy. Chương này dạy cách chọn đúng loại test cho đúng việc: unit test thuần (mili-giây), test lát cắt (@WebMvcTest, @DataJpaTest) cho từng tầng, và integration test với CSDL thật bằng Testcontainers cho những gì mock không chứng minh được.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-10
🎯 Mục tiêu chương
  • Chọn đúng loại test theo kim tự tháp: unit → slice → integration.
  • Viết unit test service bằng JUnit 5 + Mockito + AssertJ không cần Spring.
  • Dùng **@WebMvcTest + MockMvc** kiểm thử controller, validation và mã lỗi.
  • Kiểm thử bảo mật với @WithMockUser/jwt() của spring-security-test.
  • Dùng **@DataJpaTest + Testcontainers (PostgreSQL)** để kiểm thử repository, migration và N+1.
  • Viết integration test @SpringBootTest toàn luồng và quản lý dữ liệu/thời gian trong test.
  • Tránh các bẫy: test chậm do context, mock quá mức, test phụ thuộc thứ tự/dữ liệu chung.

Nhiều test nhanh ở đáy, ít test chậm ở đỉnh. Mỗi bug nên bị bắt ở tầng thấp nhất có thể: lỗi công thức tính tiền → unit test; sai mapping URL/validation → @WebMvcTest; truy vấn sai → @DataJpaTest; ghép sai cấu hình giữa các lớp → một vài @SpringBootTest. Đảo ngược kim tự tháp (toàn @SpringBootTest) cho bộ test chậm, mong manh, khó khoanh vùng lỗi.

spring-boot-starter-test đã gói sẵn mọi thứ: JUnit 5, Mockito, AssertJ, Hamcrest, JSONassert, JsonPath, Spring Test/MockMvc.

2. Unit test — không cần Spring

OrderServiceTest.java
@ExtendWith(MockitoExtension.class)                      // không khởi động Spring: nhanh và đơn giản
class OrderServiceTest {

    @Mock CustomerRepository customers;
    @Mock ProductRepository products;
    @Mock OrderRepository orders;
    @Mock OrderMapper mapper;
    @InjectMocks OrderService service;                    // tạo service bằng CONSTRUCTOR, tiêm các mock vào

    @Test
    void place_throwsWhenProductDiscontinued() {
        // given
        var customer = new Customer("An", "an@example.com");
        var banned = new Product("Cũ", new BigDecimal("10.00"), "sach");
        banned.discontinue();
        given(customers.findById(1L)).willReturn(Optional.of(customer));
        given(products.findById(7L)).willReturn(Optional.of(banned));
        var req = new CreateOrderRequest(1L, List.of(new CreateOrderRequest.Line(7L, 2)));

        // when / then
        assertThatThrownBy(() -> service.place(req))
                .isInstanceOf(BusinessRuleException.class)
                .hasMessageContaining("ngừng bán");
        verify(orders, never()).save(any());              // không được lưu gì
    }

    @Test
    void place_savesOrderWithItems() {
        var customer = new Customer("An", "an@example.com");
        var p = new Product("Java 21", new BigDecimal("99.00"), "sach");
        given(customers.findById(1L)).willReturn(Optional.of(customer));
        given(products.findById(7L)).willReturn(Optional.of(p));
        given(orders.save(any(Order.class))).willAnswer(inv -> inv.getArgument(0));   // trả lại chính nó

        service.place(new CreateOrderRequest(1L, List.of(new CreateOrderRequest.Line(7L, 3))));

        ArgumentCaptor<Order> captor = ArgumentCaptor.forClass(Order.class);
        verify(orders).save(captor.capture());
        assertThat(captor.getValue().getItems()).hasSize(1);
        assertThat(captor.getValue().total()).isEqualByComparingTo("297.00");
    }
}

Vì sao unit test này không cần Spring? Do chương 2: constructor injection ⇒ new OrderService(a, b, c, d) là đủ. Nếu service dùng field injection, bạn phải dùng reflection/@InjectMocks và Spring-test mới chạy được — đó là cái giá của lựa chọn đó.

Test xác nhận "hàm A gọi hàm B đúng 1 lần với tham số X" hỏng mỗi khi refactor dù hành vi không đổi. Ưu tiên kiểm tra kết quả/trạng thái quan sát được (giá trị trả về, exception, thứ được lưu) hơn là cách đạt kết quả. verify(...) chỉ khi tác dụng phụ chính là mục đích (gửi email, lưu DB).

3. @WebMvcTest — kiểm thử controller

Dựng chỉ tầng web: DispatcherServlet, controller được chỉ định, @ControllerAdvice, filter, cấu hình JSON. Service/repository không được tạo ⇒ bạn cung cấp mock.

ProductControllerTest.java
@WebMvcTest(ProductController.class)
@Import(SecurityConfig.class)                          // slice không quét @Configuration — nạp cấu hình bảo mật thủ công
class ProductControllerTest {

    @Autowired MockMvc mvc;
    @MockitoBean ProductService service;               // Boot 3.4+: @MockitoBean thay @MockBean (đã deprecated)
    @MockitoBean JwtDecoder jwtDecoder;                // SecurityConfig cần bean này; mock cho khỏi dựng thật

    @Test
    @WithMockUser                                      // giả lập người dùng đã đăng nhập (spring-security-test)
    void get_returnsProductJson() throws Exception {
        given(service.get(42L)).willReturn(new ProductResponse(42L, "Java 21", new BigDecimal("99.00")));

        mvc.perform(get("/api/products/42"))
           .andExpect(status().isOk())
           .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
           .andExpect(jsonPath("$.id").value(42))
           .andExpect(jsonPath("$.name").value("Java 21"));
    }

    @Test
    @WithMockUser
    void get_returns404ProblemDetail() throws Exception {
        given(service.get(99L)).willThrow(new NotFoundException("product", 99L));

        mvc.perform(get("/api/products/99"))
           .andExpect(status().isNotFound())
           .andExpect(content().contentType("application/problem+json"))
           .andExpect(jsonPath("$.code").value("PRODUCT_NOT_FOUND"));
    }

    @Test
    @WithMockUser(roles = "ADMIN")
    void create_rejectsInvalidBody() throws Exception {
        mvc.perform(post("/api/products")
                   .contentType(MediaType.APPLICATION_JSON)
                   .content("""
                            {"name": "", "price": -5}
                            """))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.errors.name").isArray())
           .andExpect(jsonPath("$.errors.price").isArray());
        verifyNoInteractions(service);                 // validation chặn TRƯỚC khi vào service
    }
}

4. @DataJpaTest + Testcontainers

@DataJpaTest dựng chỉ tầng JPA, mỗi test chạy trong một transaction rồi rollback (dữ liệu không rò sang test khác). Mặc định nó thay CSDL của bạn bằng H2 trong bộ nhớ — nhanh nhưng không phải PostgreSQL: khác kiểu dữ liệu, hàm, cách lock ⇒ test xanh mà production vẫn lỗi (đặc biệt với @Query native, jsonb, FOR UPDATE, Flyway migration viết cho PostgreSQL).

Test với đúng CSDL bạn chạy production. Testcontainers khởi động một container Docker thật (PostgreSQL, Redis, Kafka…) cho test rồi huỷ — không cần cài gì, cô lập, tái lập được. Từ Boot 3.1, @ServiceConnection tự nối ứng dụng tới container, không cần cấu hình URL.

ProductRepositoryTest.java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)    // KHÔNG thay bằng H2
@Testcontainers
class ProductRepositoryTest {

    @Container
    @ServiceConnection                                                      // tự gán spring.datasource.* theo container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired ProductRepository repo;
    @Autowired TestEntityManager em;

    @Test
    void findByCategoryAndStatus_filtersCorrectly() {
        em.persist(new Product("A", new BigDecimal("10.00"), "sach"));
        Product b = em.persist(new Product("B", new BigDecimal("20.00"), "sach"));
        b.discontinue();
        em.persist(new Product("C", new BigDecimal("30.00"), "do-choi"));
        em.flush();                                           // đẩy xuống DB để truy vấn thấy

        List<Product> r = repo.findByCategoryAndStatus("sach", ProductStatus.ACTIVE);

        assertThat(r).extracting(Product::getName).containsExactly("A");
    }

    @Test
    void uniqueSku_isEnforcedByDatabase() {
        repo.saveAndFlush(productWithSku("SKU-1"));
        assertThatThrownBy(() -> repo.saveAndFlush(productWithSku("SKU-1")))
                .isInstanceOf(DataIntegrityViolationException.class);       // ràng buộc UNIQUE do Flyway tạo
    }
}

Vì Flyway chạy trên container, test này đồng thời kiểm chứng migration khớp entity (ddl-auto: validate). Một lợi ích lớn: schema sai là test đỏ ngay, không đợi deploy.

5. @SpringBootTest — kiểm thử tích hợp

Khởi động toàn bộ context (có thể cả server thật trên cổng ngẫu nhiên). Dùng ít, cho các luồng quan trọng cần chứng minh các lớp ghép đúng: đăng ký → đăng nhập → gọi API có token → xem dữ liệu.

AuthFlowIT.java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class AuthFlowIT {

    @Container @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired TestRestTemplate rest;

    @Test
    void register_login_thenCallProtectedEndpoint() {
        // 1. đăng ký
        var reg = rest.postForEntity("/api/auth/register",
                new RegisterRequest("an@example.com", "Matkhau123"), Void.class);
        assertThat(reg.getStatusCode()).isEqualTo(HttpStatus.CREATED);

        // 2. đăng nhập → token
        var login = rest.postForEntity("/api/auth/login",
                new LoginRequest("an@example.com", "Matkhau123"), TokenResponse.class);
        assertThat(login.getStatusCode()).isEqualTo(HttpStatus.OK);
        String token = login.getBody().accessToken();

        // 3. gọi endpoint có bảo vệ
        HttpHeaders h = new HttpHeaders(); h.setBearerAuth(token);
        var me = rest.exchange("/api/me", HttpMethod.GET, new HttpEntity<>(h), Map.class);
        assertThat(me.getStatusCode()).isEqualTo(HttpStatus.OK);
        assertThat(me.getBody()).containsEntry("username", "an@example.com");

        // 4. không token → 401
        assertThat(rest.getForEntity("/api/me", String.class).getStatusCode()).isEqualTo(HttpStatus.UNAUTHORIZED);
    }
}

5.1. Giữ test nhanh

  • Spring cache ApplicationContext theo cấu hình. Mỗi tổ hợp khác nhau (@MockitoBean khác, @TestPropertySource khác, @ActiveProfiles khác) ⇒ một context mới (chậm). Gom test dùng cùng cấu hình; dùng chung một lớp cơ sở AbstractIntegrationTest.
  • Container dùng chung: khai báo static trong lớp cơ sở (hoặc @Testcontainers + singleton pattern) để cả bộ test dùng một PostgreSQL thay vì khởi động mỗi lớp.
  • Tránh @DirtiesContext (huỷ context ⇒ dựng lại); dọn dữ liệu bằng cách khác.
  • Với RANDOM_PORT, @Transactional trên test không rollback (server chạy ở thread khác) — dọn bằng @Sql/xoá trong @BeforeEach.
AbstractIntegrationTest.java
@SpringBootTest(webEnvironment = RANDOM_PORT)
@ActiveProfiles("test")
public abstract class AbstractIntegrationTest {

    @ServiceConnection
    static final PostgreSQLContainer<?> POSTGRES = new PostgreSQLContainer<>("postgres:16-alpine").withReuse(true);

    static { POSTGRES.start(); }                          // khởi động một lần cho cả JVM của bộ test

    @Autowired protected TestRestTemplate rest;
    @Autowired protected JdbcTemplate jdbc;

    @BeforeEach
    void cleanDb() {
        jdbc.execute("truncate table order_item, orders, products, app_users restart identity cascade");
    }
}

⚠️ Cấm Thread.sleep và Instant.now() rải rác

Test phụ thuộc đồng hồ thật hoặc sleep(2000) để "đợi hết hạn" vừa chậm vừa flaky. Tiêm Clock (production code) rồi cố định/tiến thời gian trong test; với bất đồng bộ dùng Awaitility (await().atMost(5, SECONDS).untilAsserted(...)).

7. Gọi dịch vụ bên ngoài trong test

Test không bao giờ gọi API thật (chậm, tốn tiền, không ổn định, có thể gây tác dụng phụ). Hai cách:

  • **@RestClientTest** (slice) + MockRestServiceServer: kiểm tra client HTTP của bạn gửi đúng request và xử lý đúng phản hồi mẫu.
  • WireMock (hoặc MockWebServer): dựng server giả thật sự lắng nghe cổng, trả phản hồi bạn dặn — kể cả lỗi 500, timeout, JSON sai — để kiểm thử retry/circuit breaker (chương 13).
WireMock
@Test
void paymentClient_retriesOn503() {
    wiremock.stubFor(post("/charge").inScenario("flaky").whenScenarioStateIs(STARTED)
            .willReturn(serviceUnavailable()).willSetStateTo("recovered"));
    wiremock.stubFor(post("/charge").inScenario("flaky").whenScenarioStateIs("recovered")
            .willReturn(okJson("{\"status\":\"OK\"}")));

    PaymentResult r = client.charge(new ChargeRequest("order-1", 1000));

    assertThat(r.status()).isEqualTo("OK");
    wiremock.verify(2, postRequestedFor(urlEqualTo("/charge")));          // lần 1 lỗi, lần 2 thành công
}

8. Chất lượng của chính bộ test

  • Đặt tên theo hành vi: place_throwsWhenProductDiscontinued, không phải test1. Đọc tên test phải hiểu yêu cầu.
  • Given–When–Then / Arrange–Act–Assert: ba phần rõ ràng; mỗi test kiểm một khái niệm.
  • Test hành vi, không test cài đặt: refactor mà hành vi không đổi ⇒ test không được đỏ.
  • Độ phủ (JaCoCo) là chỉ báo, không phải mục tiêu: 100% dòng vẫn có thể không kiểm gì (không assert). Dùng mutation testing (PIT) để kiểm chất lượng assert (Java chương 14).
  • Chạy trong CI mỗi commit: unit + slice nhanh trước; integration/Testcontainers sau; test đỏ chặn merge.
  • Test flaky phải sửa hoặc xoá — một test lúc đỏ lúc xanh làm cả đội ngừng tin bộ test.

Bài tập

Unit test service với Mockito

Viết TransferServiceTest cho chuyen(tu, den, soTien) gồm các trường hợp:

  • Thành công: số dư hai tài khoản đúng.
  • Không đủ số dư: ném BusinessRuleException và không lưu gì.
  • Tài khoản đích không tồn tại: NotFoundException.
  • Dùng @ParameterizedTest cho các số tiền biên: 0, âm, bằng đúng số dư.
Gợi ý

Dùng đối tượng TaiKhoan thật (không mock entity). verify(repo, never()).save(any()) cho nhánh lỗi. Số tiền ≤ 0 nên bị chặn ở validation hoặc ở entity — test chỉ ra ai chịu trách nhiệm.

@WebMvcTest cho API sản phẩm

Viết test cho POST /api/products bao gồm: tạo thành công (201 + Location), body sai (400 + errors), chưa đăng nhập (401), không đủ quyền (403).

  • Kiểm tra Content-Type: application/problem+json cho lỗi.
  • verifyNoInteractions(service) khi validation thất bại.
  • Bật spring.mvc.problemdetails.enabled — có ảnh hưởng test không?
Gợi ý

@Import(SecurityConfig.class) + @MockitoBean JwtDecoder; dùng .with(csrf()) nếu CSRF còn bật (với API stateless đã tắt). Thiếu @Import ⇒ filter bảo mật mặc định của Boot áp dụng và kết quả khác production.

Repository với Testcontainers

Dựng @DataJpaTest với PostgreSQL thật cho OrderRepository.

  • Kiểm tra findWithItemsById nạp đủ items mà không có LazyInitializationException khi truy cập ngoài transaction.
  • Viết test đếm câu SQL cho findRows() (không N+1).
  • Thử đổi sang H2 — có test nào xanh sai (hoặc đỏ sai) vì khác PostgreSQL không?
Gợi ý

Test ngoài transaction: @Transactional(propagation = NOT_SUPPORTED) hoặc gọi qua service. Khác biệt thường gặp: bigint generated by default as identity, jsonb, ilike, hành vi FOR UPDATE, phân biệt hoa thường của tên.

Bắt lỗi IDOR bằng test

Viết integration test với hai người dùng A và B. A tạo một đơn hàng.

  • B gọi GET /api/orders/{idCuaA} ⇒ phải nhận 404 (hoặc 403 — theo quy ước đội).
  • Cố ý xoá kiểm tra sở hữu khỏi service ⇒ test phải đỏ (đó là mục đích).
  • Bổ sung test cho PUT/DELETE cùng tài nguyên.
Gợi ý

Dùng TestRestTemplate kèm token thật của B qua login. Một test phân quyền chỉ có giá trị nếu bạn đã thấy nó đỏ khi cố tình làm hỏng code — luôn kiểm tra chiều đó.

Thời gian và refresh token

Dùng Clock cố định để kiểm thử RefreshTokenService.rotate:

  • Token còn hạn ⇒ cặp mới; hết hạn (tiến đồng hồ 15 ngày) ⇒ InvalidTokenException.
  • Dùng lại token cũ ⇒ TokenReuseException và toàn bộ family bị revoked (kiểm bằng truy vấn DB).
  • Không dùng Thread.sleep ở bất cứ đâu.
Gợi ý

Dùng MutableClock đơn giản (lớp test tự viết, advance(Duration)) để tiến thời gian giữa các bước. Kiểm tra trạng thái DB sau ngoại lệ — chính là chỗ noRollbackFor (chương 10) thể hiện.

Quiz

Q1

Kim tự tháp test là gì? Vì sao không nên dùng @SpringBootTest cho mọi test?

Xem đáp án
✓ Đáp án

Nhiều test nhanh ở đáy (unit), vừa ở giữa (slice), ít test chậm ở đỉnh (integration/E2E). @SpringBootTest dựng cả ứng dụng (chục giây, thường cần DB) — dùng cho mọi test sẽ cho bộ test chậm, mong manh, và khó biết lỗi nằm ở đâu. Mỗi bug nên bị bắt ở tầng thấp nhất có thể.

Q2

@WebMvcTest dựng gì và không dựng gì?

Xem đáp án
✓ Đáp án

Dựng tầng MVC: DispatcherServlet, controller được chỉ định, @ControllerAdvice, filter, converter/JSON. Không dựng @Service, @Repository, @Configuration thông thường ⇒ phải cung cấp mock (@MockitoBean) và @Import cấu hình bảo mật nếu cần.

Q3

Vì sao nên dùng Testcontainers với PostgreSQL thay vì H2?

Xem đáp án
✓ Đáp án

H2 không giống PostgreSQL: khác kiểu dữ liệu, hàm, SQL native, hành vi khoá và migration ⇒ test xanh nhưng production lỗi. Testcontainers chạy đúng CSDL production trong Docker, cô lập và tái lập được; @ServiceConnection (Boot 3.1+) tự nối ứng dụng tới container.

Q4

Khi nào nên và không nên mock?

Xem đáp án
✓ Đáp án

Mock phụ thuộc chậm/ngoài/phi tất định (DB, HTTP, email, thời gian) hoặc cần ép lỗi. Không mock value object, DTO, entity thuần, hay chính lớp đang test. Tránh verify quá chi tiết làm test dính cài đặt — ưu tiên kiểm kết quả quan sát được.

Q5

Làm sao test code phụ thuộc thời gian mà không Thread.sleep?

Xem đáp án
✓ Đáp án

Tiêm **Clock** vào code production (clock.instant() thay vì Instant.now()); trong test dùng Clock.fixed(...) hoặc đồng hồ tiến được. Với bất đồng bộ dùng Awaitility. Cách này nhanh, chính xác và không flaky.

Q6

Vì sao một test phân quyền chỉ đáng tin sau khi bạn đã thấy nó đỏ?

Xem đáp án
✓ Đáp án

Test luôn xanh có thể vì nó không kiểm gì (sai URL, thiếu assert, sai cấu hình security). Cố ý làm hỏng code (bỏ kiểm tra sở hữu) và xác nhận test đỏ để chắc rằng nó thật sự bảo vệ thứ cần bảo vệ — nguyên tắc cũng là ý tưởng của mutation testing.

Tổng kết

Sau chương 11, bạn đã nắm:

  • Kim tự tháp: unit (Mockito, không Spring) → slice (@WebMvcTest, @DataJpaTest) → ít integration (@SpringBootTest).
  • Constructor injection ⇒ unit test new Service(mock…) không cần Spring; mock biên chậm/ngoài, không mock giá trị/chính lớp.
  • **@WebMvcTest + MockMvc** kiểm URL, validation, JSON, ProblemDetail, phân quyền; @WithMockUser/jwt() đóng vai người dùng.
  • **Testcontainers + @ServiceConnection** cho CSDL thật; test cả migration, ràng buộc, N+1.
  • Chia sẻ context và container, dọn dữ liệu tường minh; tiêm **Clock**; Awaitility thay sleep.
  • Test hành vi, đặt tên rõ, không flaky; độ phủ là chỉ báo — kiểm chất lượng assert bằng mutation testing.

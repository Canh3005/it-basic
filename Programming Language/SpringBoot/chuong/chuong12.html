Chương 12 · Cache & Messaging

Cache, Messaging & Async — nhanh hơn và bớt phụ thuộc đồng bộ

Đến đây API của bạn đúng, an toàn, có test. Hai vấn đề mới sẽ xuất hiện khi tải tăng: chậm (cùng một truy vấn đắt chạy lại hàng nghìn lần) và ràng buộc chặt (đặt hàng xong phải gửi email, trừ kho, báo kế toán — nếu làm tất cả trong request thì chậm và một dịch vụ chết kéo cả luồng chết theo). Chương này có ba công cụ: cache (nhớ kết quả), bất đồng bộ (@Async, @Scheduled, sự kiện) và message queue (tách rời hoàn toàn các thành phần) — cùng với cái giá mà từng công cụ bắt bạn trả.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-11
🎯 Mục tiêu chương
  • Dùng Spring Cache (@Cacheable, @CachePut, @CacheEvict) với Caffeine (cục bộ) và Redis (phân tán).
  • Hiểu mẫu cache-aside, TTL, stampede và vì sao invalidation khó.
  • Dùng Redis trực tiếp cho rate limit và khoá phân tán đơn giản.
  • Chạy việc nền bằng **@Async, @Scheduled** (và vấn đề chạy trùng khi nhiều instance).
  • Dùng sự kiện ứng dụng để giảm kết dính trong cùng một tiến trình.
  • Hiểu message queue (RabbitMQ vs Kafka) và viết producer/consumer bằng Spring.
  • Áp dụng Transactional Outbox, consumer idempotent, retry + DLQ để messaging đáng tin cậy.

2. Spring Cache

Spring Cache là lớp trừu tượng (như @Transactional, chạy bằng proxy — chương 2): bạn gắn annotation lên method, Spring kiểm tra cache trước khi gọi method thật. Đổi nơi lưu (Caffeine ↔ Redis) chỉ là đổi cấu hình.

Bật & dùng
@Configuration
@EnableCaching
class CacheConfig { }

@Service
class ProductService {

    @Cacheable(cacheNames = "products", key = "#id")                  // có trong cache → trả ngay, KHÔNG chạy method
    public ProductResponse get(long id) {
        return mapper.toResponse(repo.findById(id).orElseThrow(() -> new NotFoundException("product", id)));
    }

    @CachePut(cacheNames = "products", key = "#result.id()")          // luôn chạy method, rồi GHI kết quả vào cache
    public ProductResponse update(long id, UpdateProductRequest req) { ... }

    @CacheEvict(cacheNames = "products", key = "#id")                 // xoá khỏi cache
    public void delete(long id) { ... }

    @CacheEvict(cacheNames = "products", allEntries = true)           // xoá cả vùng cache (dùng tiết kiệm)
    public void reindex() { ... }

    @Cacheable(cacheNames = "categories", unless = "#result.isEmpty()")     // không cache kết quả rỗng
    public List<CategoryResponse> categories() { ... }
}
AnnotationHành viDùng khi
@CacheableHit → trả cache, bỏ qua method. Miss → chạy method, lưu kết quảĐọc
@CachePutLuôn chạy method rồi cập nhật cacheGhi/cập nhật — giữ cache đồng bộ
@CacheEvictXoá entry (hoặc allEntries)Xoá/đổi dữ liệu
@CachingGộp nhiều thao tác cacheCập nhật ảnh hưởng nhiều khoá
⚠️ Cùng bẫy proxy như @Transactional

Gọi this.get(id) từ method khác trong cùng lớp thì @Cacheable bị bỏ qua (không qua proxy). Method phải public, gọi từ bean khác. Và key mặc định gộp mọi tham số — đặt key tường minh bằng SpEL (#id, #req.email) để không cache nhầm.

2.1. Caffeine — cache trong bộ nhớ, rất nhanh

pom.xml & application.yml
# <dependency> com.github.ben-manes.caffeine:caffeine  +  spring-boot-starter-cache </dependency>
spring:
  cache:
    type: caffeine
    cache-names: products,categories
    caffeine:
      spec: maximumSize=10000,expireAfterWrite=10m          # giới hạn kích thước + TTL

Caffeine nằm trong JVM của từng instance: nhanh nhất (không qua mạng) nhưng mỗi instance có bản riêng — chạy 3 instance thì 3 cache không đồng bộ; một instance @CacheEvict không xoá bản của hai instance kia. Hợp cho dữ liệu ít đổi, chấp nhận hơi cũ (danh mục, cấu hình) hoặc khi chỉ có một instance.

Tuỳ biến TTL & serializer theo vùng cache
@Bean
RedisCacheManagerBuilderCustomizer redisCaches() {
    var json = RedisSerializationContext.SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer());
    RedisCacheConfiguration base = RedisCacheConfiguration.defaultCacheConfig()
            .serializeValuesWith(json)                         // JSON dễ đọc/debug; mặc định là JDK serialization (cần Serializable)
            .disableCachingNullValues();
    return builder -> builder
            .withCacheConfiguration("products",   base.entryTtl(Duration.ofMinutes(10)))
            .withCacheConfiguration("categories", base.entryTtl(Duration.ofHours(1)));
}

Cache DTO/response, không cache entity JPA — entity có proxy lazy, quan hệ vòng, khó serialize; DTO là dữ liệu phẳng, ổn định (chương 8).

Quy tắc thực dụng: cache cái đọc nhiều – ghi ít – chấp nhận hơi cũ; luôn đặt TTL làm lưới an toàn ngay cả khi có invalidation chủ động; đo hit ratio (/actuator/metrics/cache.gets) — cache hit ratio thấp là cache vô ích.

3. Redis dùng trực tiếp

Redis không chỉ là cache: nó là kho cấu trúc dữ liệu trong bộ nhớ, đơn luồng nên thao tác nguyên tử, kèm TTL. Hai việc rất thường gặp trong backend:

3.1. Giới hạn tốc độ (rate limit)

LoginRateLimiter.java
@Component
class LoginRateLimiter {

    private final StringRedisTemplate redis;
    LoginRateLimiter(StringRedisTemplate redis) { this.redis = redis; }

    /** Tối đa 5 lần thử / phút / IP — cửa sổ cố định. */
    void check(String ip) {
        String key = "rl:login:" + ip;
        Long count = redis.opsForValue().increment(key);                  // INCR: nguyên tử, tạo khoá = 1 nếu chưa có
        if (count != null && count == 1) {
            redis.expire(key, Duration.ofMinutes(1));                     // chỉ đặt TTL ở lần đầu
        }
        if (count != null && count > 5) {
            throw new TooManyRequestsException("Quá nhiều lần đăng nhập, thử lại sau");     // → 429 + Retry-After
        }
    }
}

Đây là cửa sổ cố định (đơn giản, nhưng cho phép "bùng nổ" ở ranh giới cửa sổ). Với yêu cầu chặt hơn dùng token bucket qua thư viện (Bucket4j + Redis) hoặc Lua script để INCR + EXPIRE thành một thao tác nguyên tử (tránh trường hợp process chết giữa hai lệnh làm khoá không bao giờ hết hạn).

3.2. Khoá phân tán đơn giản

Chỉ cho 1 instance chạy việc
String lockKey = "lock:daily-report";
String token = UUID.randomUUID().toString();

Boolean acquired = redis.opsForValue().setIfAbsent(lockKey, token, Duration.ofMinutes(5));   // SET key val NX PX 300000
if (Boolean.TRUE.equals(acquired)) {
    try {
        runDailyReport();
    } finally {
        // chỉ xoá nếu khoá VẪN là của mình (so token) — dùng Lua để kiểm & xoá nguyên tử
        redis.execute(UNLOCK_SCRIPT, List.of(lockKey), token);
    }
}
⚠️ Khoá phân tán không phải khoá thật

Nếu việc chạy lâu hơn TTL, khoá hết hạn và instance khác vào ⇒ hai bên cùng chạy. Với tính đúng đắn nghiêm ngặt (chuyển tiền) dùng ràng buộc/khoá ở CSDL (@Version, SELECT … FOR UPDATE — chương 7), không dựa vào Redis lock. Redis lock hợp cho "cố gắng chỉ một instance" (job nền, chống bấm đúp), kèm idempotent ở phía thực thi.

4. Việc nền: @Async và @Scheduled

4.1. @Async

Bật & dùng
@Configuration
@EnableAsync
class AsyncConfig {
    @Bean(name = "mailExecutor")
    Executor mailExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4); ex.setMaxPoolSize(8); ex.setQueueCapacity(200);       // hàng đợi CÓ GIỚI HẠN
        ex.setThreadNamePrefix("mail-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());    // quá tải → người gọi tự chạy (làm chậm lại thay vì mất việc)
        return ex;
    }
}

@Service
class MailService {
    @Async("mailExecutor")                                      // chạy ở thread khác, trả về ngay cho người gọi
    public CompletableFuture<Void> sendWelcome(String to) {
        // gọi SMTP chậm …
        return CompletableFuture.completedFuture(null);
    }
}
  • Cùng bẫy proxy: gọi từ cùng lớp thì không bất đồng bộ; method public; bean khác gọi.
  • Không có transaction hay SecurityContext được truyền sang thread mới theo mặc định — đọc lại dữ liệu bằng id trong thread mới, truyền người dùng tường minh nếu cần.
  • Method void mà ném exception ⇒ nuốt lặng lẽ; cấu hình AsyncUncaughtExceptionHandler để log lỗi. Trả CompletableFuture thì xử lý bằng .exceptionally.
  • Giới hạn hàng đợi — hàng đợi vô hạn rồi hết bộ nhớ là sự cố kinh điển. Boot 3.2+ với Java 21: spring.threads.virtual.enabled=true làm @Async mặc định chạy trên virtual thread (chương 1).
  • @Async không bền: tắt máy giữa chừng ⇒ việc mất. Việc phải hoàn thành → dùng queue (mục 6).

4.2. @Scheduled

Tác vụ định kỳ
@Configuration @EnableScheduling class SchedulingConfig { }

@Component
class Jobs {

    @Scheduled(fixedDelayString = "PT1M")                       // 1 phút SAU KHI lần trước KẾT THÚC (không chồng lấn)
    void pollOutbox() { ... }

    @Scheduled(fixedRate = 30_000)                              // mỗi 30 giây từ lúc BẮT ĐẦU (có thể chồng nếu lâu hơn)
    void heartbeat() { ... }

    @Scheduled(cron = "0 0 2 * * *", zone = "Asia/Ho_Chi_Minh") // 02:00 mỗi ngày giờ VN (giây phút giờ ngày tháng thứ)
    void dailyReport() { ... }
}
⚠️ Chạy 3 instance ⇒ job chạy 3 lần

@Scheduled chạy trong mỗi JVM. Scale ngang lên 3 pod, báo cáo hằng ngày gửi 3 lần. Giải pháp: ShedLock (khoá job qua DB/Redis: @SchedulerLock(name = "dailyReport", lockAtMostFor = "10m")), hoặc tách job ra một instance riêng/Kubernetes CronJob, hoặc dùng bộ lập lịch phân tán (Quartz cluster). Mặc định scheduler Spring chỉ có 1 thread — job chậm chặn các job khác (spring.task.scheduling.pool.size).

5. Sự kiện ứng dụng — tách rời trong một tiến trình

Phát và nghe
public record UserRegistered(Long userId, String email) { }       // record làm sự kiện: bất biến, gọn

@Service
class RegistrationService {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)    // chỉ khi đăng ký ĐÃ commit (chương 7)

6. Message queue

Message broker là trung gian nhận thông điệp từ producer, lưu bền, và giao cho consumer — hai phía không cần chạy cùng lúc, không cần biết nhau.

💡 Mặc định

Cần "giao việc nền đáng tin cậy" ⇒ RabbitMQ (hoặc SQS/Cloud Tasks). Cần "dòng sự kiện nhiều bên đọc, phát lại, thông lượng lớn" ⇒ Kafka. Đừng dùng Kafka chỉ để gửi vài email.

6.1. RabbitMQ với Spring AMQP

Producer & consumer
// spring-boot-starter-amqp;  spring.rabbitmq.host/port/username/password
@Configuration
class RabbitConfig {
    @Bean Queue mailQueue()        { return QueueBuilder.durable("mail.send").withArgument("x-dead-letter-exchange", "dlx").build(); }
    @Bean Jackson2JsonMessageConverter converter() { return new Jackson2JsonMessageConverter(); }   // JSON thay vì Java serialization
}

@Service
class MailProducer {
    private final RabbitTemplate rabbit;
    MailProducer(RabbitTemplate rabbit) { this.rabbit = rabbit; }
    void send(MailMessage m) { rabbit.convertAndSend("mail.send", m); }
}

@Component
class MailConsumer {
    @RabbitListener(queues = "mail.send")
    void handle(MailMessage m) {
        mailer.send(m.to(), m.subject(), m.body());       // ném exception ⇒ retry/DLQ theo cấu hình (mục 7)
    }
}

7. Messaging đáng tin cậy

Thêm broker nghĩa là bạn bước vào hệ phân tán: mạng lỗi, trùng lặp và mất thứ tự là chuyện bình thường. Ba vấn đề phải giải quyết:

7.1. Dual-write và Transactional Outbox

Hai thao tác không nguyên tử
@Transactional
void place(...) {
    orders.save(order);                                     // (1) ghi DB
    kafka.send("orders.placed", event);                     // (2) gửi broker
}   // (2) thành công nhưng (1) rollback → sự kiện về đơn KHÔNG TỒN TẠI
    // (1) commit nhưng (2) lỗi/process chết → đơn có mà KHÔNG AI ĐƯỢC BÁO (kho không trừ, không email)

Không có transaction nào bao trùm cả DB và broker. Giải pháp chuẩn: Transactional Outbox — ghi sự kiện vào một bảng outbox cùng transaction với dữ liệu nghiệp vụ (nguyên tử!), rồi một tiến trình riêng đọc bảng đó và đẩy lên broker:

1. Một transaction DB
INSERT orders + INSERT outbox(payload) — cùng commit hoặc cùng rollback
2. Relay đọc outbox
@Scheduled poll SELECT … FOR UPDATE SKIP LOCKED (hoặc CDC bằng Debezium)
3. Gửi broker
kafka.send(...); chờ ack
4. Đánh dấu
UPDATE outbox SET published_at = now()
Sự kiện không bao giờ mất (nằm trong DB bền); có thể gửi trùng nếu chết giữa bước 3-4 ⇒ consumer phải idempotent.
Outbox
@Entity @Table(name = "outbox")
class OutboxEvent {
    @Id private UUID id = UUID.randomUUID();
    private String aggregateType, aggregateId, eventType;
    @Column(columnDefinition = "jsonb") private String payload;
    private Instant createdAt = Instant.now();
    private Instant publishedAt;
}

interface OutboxRepository extends JpaRepository<OutboxEvent, UUID> {
    @Query(value = "select * from outbox where published_at is null order by created_at limit 100 for update skip locked",
           nativeQuery = true)                               // nhiều relay chạy song song không giẫm chân nhau
    List<OutboxEvent> lockBatch();
}

@Component
class OutboxRelay {
    @Scheduled(fixedDelayString = "PT1S") @Transactional
    void relay() {
        for (OutboxEvent e : outbox.lockBatch()) {
            kafka.send(topicFor(e), e.getAggregateId(), e.getPayload()).join();   // chờ ack mới đánh dấu
            e.markPublished();
        }
    }
}

7.2. Consumer idempotent

Hầu hết broker đảm bảo ít nhất một lần (at-least-once): sự kiện có thể đến nhiều lần. ("Đúng một lần" end-to-end gần như không có; nó thực chất là at-least-once + xử lý idempotent.) Consumer phải xử lý trùng mà không gây hại:

Chống xử lý trùng
@Transactional
@KafkaListener(topics = "orders.placed", groupId = "inventory-service")
void on(OrderPlaced e, @Header(KafkaHeaders.RECEIVED_KEY) String key) {
    // processed_messages(message_id PRIMARY KEY): insert & hiệu ứng nghiệp vụ CÙNG transaction
    try {
        processed.saveAndFlush(new ProcessedMessage(e.eventId()));      // trùng → vi phạm PRIMARY KEY
    } catch (DataIntegrityViolationException dup) {
        return;                                                          // đã xử lý rồi → bỏ qua, ack bình thường
    }
    inventory.reserve(e.orderId(), e.lines());                           // chỉ chạy đúng một lần hiệu quả
}

Cách khác là thiết kế thao tác tự nhiên idempotent (SET status = 'PAID' an toàn khi lặp; balance = balance + 10 thì không).

}
📌 Nhất quán cuối cùng (eventual consistency)

Sau khi đặt hàng, tồn kho có thể trừ chậm vài giây. Thiết kế UI/nghiệp vụ chấp nhận điều đó (trạng thái "Đang xử lý") thay vì giả vờ mọi thứ tức thời. Với giao dịch xuyên nhiều dịch vụ cần hoàn tác: Saga (chương 13).

Bài tập

Cache sản phẩm với Caffeine

Thêm @Cacheable("products") cho ProductService.get. Bật log SQL.

  • Gọi GET /api/products/1 hai lần: có mấy câu SELECT?
  • Cập nhật sản phẩm 1 rồi GET lại: dữ liệu mới hay cũ? Thêm @CachePut/@CacheEvict cho đúng.
  • Gọi this.get(1) từ method khác cùng lớp — cache có hoạt động không? Vì sao?
Gợi ý

Lần đầu 1 SELECT, lần hai 0. Không evict ⇒ dữ liệu cũ đến hết TTL. this.get không qua proxy nên bị bỏ qua cache — chuyển sang bean khác hoặc tách lớp.

Dựng Redis cache và đo hit ratio

Chạy Redis bằng Docker. Chuyển spring.cache.type=redis, đặt TTL, JSON serializer.

  • Dùng redis-cli keys '*' và ttl <key> xem khoá được tạo & còn bao lâu.
  • Chạy 2 instance (cổng 8080/8081): đổi dữ liệu ở instance A và đọc từ B — thấy gì (Caffeine vs Redis)?
  • Đọc /actuator/metrics/cache.gets?tag=result:hit và miss để tính hit ratio.
Gợi ý

Redis cache dùng chung ⇒ evict ở A có hiệu lực ở B; Caffeine thì không (mỗi JVM một bản). Hit ratio < 50% thường nghĩa là cache không đáng giữ hoặc TTL/key sai.

Rate limit đăng nhập

Cài LoginRateLimiter bằng Redis (mục 3.1): 5 lần / phút / IP, quá giới hạn ⇒ 429 Too Many Requests + header Retry-After.

  • Dùng vòng lặp curl kiểm chứng.
  • Mô tả tình huống INCR thành công nhưng process chết trước EXPIRE — hậu quả? Sửa bằng Lua.
  • Vì sao nên giới hạn theo cả IP và theo email đang bị thử?
Gợi ý

Khoá không TTL ⇒ IP bị chặn vĩnh viễn. Lua: local c = redis.call('INCR', KEYS[1]); if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end; return c. Theo IP một mình dễ né (nhiều IP, botnet) và có thể chặn nhầm cả văn phòng dùng chung IP.

Gửi email bất đồng bộ + sau commit

Khi đăng ký thành công, gửi email chào bằng @TransactionalEventListener(AFTER_COMMIT) + @Async.

  • Cố tình làm transaction đăng ký rollback sau khi publish sự kiện — email có gửi không?
  • Bỏ AFTER_COMMIT (dùng @EventListener) — thử lại: chuyện gì xảy ra?
  • Mô phỏng SMTP chậm 5 giây — request đăng ký có bị chậm không?
Gợi ý

Với AFTER_COMMIT, rollback ⇒ listener không chạy. Với @EventListener thường, email đã đi trước khi commit — gửi cho tài khoản không tồn tại. @Async tách khỏi thread request nên không chậm.

Outbox + consumer idempotent (thực hành lớn)

Dựng Kafka (Docker). Khi OrderService.place thành công, ghi sự kiện vào outbox; OutboxRelay đẩy lên orders.placed; một consumer "kho" trừ tồn.

  • Tắt Kafka, đặt 3 đơn, bật lại: sự kiện có tới kho không?
  • Cố ý để relay gửi trùng một sự kiện (kill giữa chừng): tồn kho trừ mấy lần? Cài bảng processed_messages để sửa.
  • Gửi một thông điệp JSON hỏng: nó đi đâu? Cấu hình @RetryableTopic + DLT.
Gợi ý

Outbox giữ sự kiện trong DB khi broker chết ⇒ không mất. Trùng được chặn bởi PRIMARY KEY của processed_messages trong cùng transaction với việc trừ tồn. Thông điệp độc (poison) sau N lần retry vào orders.placed-dlt.

Quiz

Q1

@Cacheable, @CachePut, @CacheEvict khác nhau thế nào?

Xem đáp án
✓ Đáp án

@Cacheable: hit thì bỏ qua method và trả cache; miss thì chạy và lưu. @CachePut: luôn chạy method rồi cập nhật cache (dùng khi ghi). @CacheEvict: xoá entry/cả vùng. Cả ba chạy qua proxy nên gọi từ cùng lớp sẽ không có tác dụng.

Q2

Caffeine và Redis khác nhau thế nào? Khi nào chọn cái nào?

Xem đáp án
✓ Đáp án

Caffeine: trong JVM, nhanh nhất, nhưng mỗi instance một bản (không đồng bộ). Redis: cache chung qua mạng — nhất quán giữa instance, bền hơn, chậm hơn một chút. Một instance/ dữ liệu ít đổi → Caffeine; nhiều instance cần nhất quán → Redis (có thể kết hợp 2 tầng).

Q3

Cache stampede là gì và cách giảm?

Xem đáp án
✓ Đáp án

Khoá nóng hết hạn cùng lúc ⇒ hàng nghìn request cùng miss ⇒ cùng truy vấn DB. Giảm bằng @Cacheable(sync = true) (chỉ một luồng nạp lại), thêm jitter vào TTL, làm nóng cache chủ động, hoặc nạp lại nền trước khi hết hạn.

Q4

Vì sao @Async không đủ cho việc "bắt buộc phải hoàn thành"?

Xem đáp án
✓ Đáp án

@Async chạy trong bộ nhớ của JVM — không bền: tắt/sập giữa chừng thì việc mất; không có retry, không có thứ tự, hàng đợi có thể đầy. Việc bắt buộc hoàn thành cần queue bền (RabbitMQ/Kafka) hoặc bảng outbox + worker.

Q5

Dual-write là gì? Transactional Outbox giải quyết thế nào?

Xem đáp án
✓ Đáp án

Ghi DB rồi gửi broker là hai thao tác không nguyên tử — một thành công một thất bại gây mất/ma sự kiện. Outbox ghi sự kiện vào bảng outbox cùng transaction với dữ liệu nghiệp vụ (nguyên tử); một relay đọc bảng đó và đẩy lên broker ít nhất một lần, nên consumer phải idempotent.

Q6

Vì sao consumer phải idempotent? Cách làm?

Xem đáp án
✓ Đáp án

Broker đảm bảo at-least-once — thông điệp có thể giao lại (retry, relay gửi trùng, rebalance). Idempotent bằng: bảng processed_messages (PK eventId) ghi cùng transaction với hiệu ứng; hoặc thiết kế thao tác tự idempotent (SET thay vì +=); hoặc khoá duy nhất theo nghiệp vụ.

Tổng kết

Sau chương 12, bạn đã nắm:

  • Đo trước, cache sau: @Cacheable/@CachePut/@CacheEvict qua proxy; Caffeine (cục bộ) vs Redis (chung); cache DTO, luôn có TTL.
  • Rủi ro cache: dữ liệu cũ, stampede, penetration, invalidation sai thứ tự — giảm bằng TTL, sync = true, evict sau commit.
  • Redis trực tiếp cho rate limit (INCR+EXPIRE; an toàn hơn với Lua/Bucket4j) và khoá nhẹ — nhưng không thay khoá DB cho tính đúng đắn nghiêm ngặt.
  • **@Async (executor có giới hạn; không bền) và @Scheduled (nhiều instance ⇒ ShedLock); sự kiện** AFTER_COMMIT để tách rời trong một JVM.
  • Message queue: RabbitMQ cho tác vụ/lệnh, Kafka cho luồng sự kiện; key ⇒ partition ⇒ thứ tự.
  • Đáng tin cậy = Outbox (chống dual-write) + consumer idempotent (at-least-once) + retry/backoff + DLQ; chấp nhận eventual consistency.

Chương 13 · Microservices

Microservices & Spring Cloud — khi một ứng dụng không đủ

Microservices là kiến trúc bị đánh giá quá cao: nó giải quyết vấn đề tổ chức và mở rộng của các hệ thống rất lớn, nhưng đổi lại bạn có một hệ phân tán — mạng lỗi, độ trễ, dữ liệu rải rác, debug qua nhiều dịch vụ. Chương này không nhằm "cổ vũ" microservices mà để bạn biết khi nào cần, và nếu cần thì làm đúng: chia theo ranh giới nghiệp vụ, gọi nhau có timeout + circuit breaker, chịu mất đồng bộ bằng Saga, và nhìn thấy mọi thứ bằng metrics/trace.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-12
🎯 Mục tiêu chương
  • Phân tích khi nào nên (và không nên) dùng microservices; biết lựa chọn modular monolith.
  • Phân rã theo bounded context; nguyên tắc mỗi dịch vụ một CSDL.
  • Gọi dịch vụ khác bằng **RestClient và HTTP Interface với timeout** đúng.
  • Áp dụng retry, circuit breaker, bulkhead, rate limiter bằng Resilience4j.
  • Hiểu vai trò API Gateway, discovery và cấu hình tập trung — và khi nào Kubernetes đã làm hộ.
  • Xử lý nhất quán dữ liệu xuyên dịch vụ bằng Saga (choreography/orchestration).
  • Quan sát hệ thống bằng metrics, log có cấu trúc, distributed tracing (Micrometer + OpenTelemetry).
  • Biết virtual threads thay đổi bài toán hiệu năng I/O ra sao.

Dấu hiệu nên cân nhắc tách: nhiều đội cùng sửa một repo giẫm chân nhau; một phần nhỏ chịu tải gấp 50 lần phần còn lại; một phần cần công nghệ/CSDL khác; thời gian build/test/triển khai cả khối quá lâu. Dấu hiệu không nên: đội < 10 người, miền nghiệp vụ chưa ổn định, chưa có CI/CD & giám sát tử tế.

2. Phân rã theo bounded context

Đừng chia theo tầng kỹ thuật (một dịch vụ "database", một dịch vụ "UI"). Chia theo bounded context (DDD): mỗi dịch vụ sở hữu một năng lực nghiệp vụ, có mô hình dữ liệu riêng. Cùng từ "Sản phẩm" nghĩa khác nhau ở các context: Catalog (mô tả, ảnh), Inventory (số tồn, kho), Pricing (giá, khuyến mãi), Order (bản chụp tên + giá tại lúc đặt).

3. Gọi dịch vụ khác

3.1. RestClient (Spring 6.1)

RestClient là client HTTP đồng bộ, API "fluent" hiện đại — thay RestTemplate (ở chế độ bảo trì) cho code mới. Quan trọng nhất: luôn đặt timeout; mặc định là chờ vô hạn — một dịch vụ chậm sẽ giữ thread của bạn cho đến khi cạn pool.

ClientConfig.java
@Configuration
class InventoryClientConfig {

    @Bean
    RestClient inventoryRestClient(RestClient.Builder builder,
                                   @Value("${clients.inventory.base-url}") String baseUrl) {
        var factory = new JdkClientHttpRequestFactory(HttpClient.newBuilder()
                .connectTimeout(Duration.ofMillis(500))                // kết nối TCP
                .build());
        factory.setReadTimeout(Duration.ofSeconds(2));                 // đọc phản hồi

        return builder.baseUrl(baseUrl)
                .requestFactory(factory)
                .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
                .defaultStatusHandler(HttpStatusCode::is5xxServerError,
                        (req, res) -> { throw new UpstreamUnavailableException("inventory", res.getStatusCode().value()); })
                .build();
    }
}
Dùng
@Component
class InventoryClient {
    private final RestClient http;
    InventoryClient(RestClient inventoryRestClient) { this.http = inventoryRestClient; }

    StockResponse stockOf(long productId) {
        return http.get().uri("/api/stock/{id}", productId)
                   .retrieve()
                   .body(StockResponse.class);                         // 4xx → HttpClientErrorException; 5xx → handler ở trên
    }

    void reserve(ReserveRequest req) {
        http.post().uri("/api/stock/reserve")
            .header("Idempotency-Key", req.orderId().toString())       // chương 8: thử lại an toàn
            .body(req).retrieve().toBodilessEntity();
    }
}

4. Khả năng chịu lỗi: timeout, retry, circuit breaker

Trong hệ phân tán, lỗi là chuyện bình thường. Một dịch vụ chậm nguy hiểm hơn một dịch vụ chết: nó giữ thread của người gọi, hàng đợi đầy, và lỗi lan truyền (cascading failure) lên cả chuỗi.

1. Timeout
Không bao giờ chờ vô hạn — giải phóng thread
2. Retry
Thử lại lỗi tạm thời, có backoff + jitter, chỉ với thao tác idempotent
3. Circuit breaker
Thấy lỗi liên tục ⇒ ngắt mạch: thất bại ngay (không gọi) để bên kia kịp hồi phục
4. Bulkhead
Giới hạn số lời gọi đồng thời tới một dịch vụ — một bên chậm không nuốt hết thread
5. Fallback
Giá trị thay thế khi thất bại (cache cũ, mặc định, báo "tạm thời không khả dụng")
Các lớp bảo vệ xếp chồng — mỗi cái chặn một kiểu hỏng.

4.1. Circuit breaker — ba trạng thái

application.yml
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 20                      # xét 20 lời gọi gần nhất
        minimum-number-of-calls: 10                  # cần ≥ 10 lời gọi mới tính tỉ lệ
        failure-rate-threshold: 50                   # ≥ 50% lỗi → OPEN
        slow-call-duration-threshold: 1s             # gọi > 1s coi là "chậm"
        slow-call-rate-threshold: 80
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 3
        ignore-exceptions:
          - vn.itbasic.shop.errors.NotFoundException # lỗi nghiệp vụ KHÔNG nên làm mở mạch
  retry:
    instances:
      inventory:
        max-attempts: 3
        wait-duration: 200ms
        enable-exponential-backoff: true
        exponential-backoff-multiplier: 2
        enable-randomized-wait: true                 # jitter: tránh mọi client thử lại cùng lúc
        retry-exceptions:
          - java.io.IOException
          - vn.itbasic.shop.errors.UpstreamUnavailableException
  bulkhead:
    instances:
      inventory:
        max-concurrent-calls: 20                     # tối đa 20 lời gọi đồng thời tới inventory
Dùng
@Service
class StockService {

    private final InventoryClient inventory;
    // constructor …

    @CircuitBreaker(name = "inventory", fallbackMethod = "stockFallback")
    @Retry(name = "inventory")                                  // retry nằm BÊN TRONG circuit breaker
    @Bulkhead(name = "inventory")
    public StockResponse stockOf(long productId) {
        return inventory.stockOf(productId);
    }

    // Cùng tham số + thêm Throwable; chữ ký khớp
    StockResponse stockFallback(long productId, Throwable ex) {
        log.warn("Inventory không khả dụng ({}), trả 'không rõ'", ex.toString());
        return StockResponse.unknown(productId);                // hạ cấp chức năng thay vì lỗi cả trang
    }
}
⚠️ Retry là con dao hai lưỡi

(1) Chỉ retry thao tác idempotent — POST /charge retry không có Idempotency-Key là trừ tiền hai lần. (2) Retry nhân tải: 3 lần thử × 1.000 client = 3.000 lời gọi đập vào dịch vụ đang yếu — retry storm; luôn có backoff, jitter, giới hạn, và đứng dưới circuit breaker. (3) Chỉ retry lỗi tạm thời (timeout, 503), không retry 400/404/422.

Quy tắc đặt timeout: timeout của người gọi < tổng thời gian chờ của người gọi nó. Gateway timeout 5s, service A timeout 3s gọi B với timeout 1s — để một lời gọi chậm không làm cả chuỗi vượt hạn rồi retry chồng chéo.

5. Gateway, discovery, cấu hình

5.1. API Gateway

Client (web, mobile) không nên biết 12 dịch vụ ở đâu. API Gateway là cổng vào duy nhất: định tuyến, xác thực/phân quyền thô, giới hạn tốc độ, CORS, gom log. Spring Cloud Gateway là lựa chọn trong hệ Spring (cũng có Kong, NGINX, Envoy, AWS API Gateway).

application.yml — Spring Cloud Gateway
spring:
  cloud:
    gateway:
      routes:
        - id: catalog
          uri: http://catalog:8080                  # tên DNS của dịch vụ (trong Kubernetes: tên Service)
          predicates:
            - Path=/api/products/**
          filters:
            - StripPrefix=0
            - name: CircuitBreaker
              args: { name: catalog, fallbackUri: 'forward:/fallback/catalog' }
        - id: orders
          uri: http://order:8080
          predicates:
            - Path=/api/orders/**
          filters:
            - name: RequestRateLimiter               # giới hạn tốc độ (Redis)
              args:
                redis-rate-limiter.replenishRate: 20
                redis-rate-limiter.burstCapacity: 40
      default-filters:
        - AddRequestHeader=X-Gateway, shop
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://keycloak.example.com/realms/shop     # xác thực JWT ở biên (chương 10)
Xác thực ở gateway, nhưng vẫn kiểm ở từng dịch vụ. Gateway kiểm token cho nhanh và từ chối sớm; mỗi dịch vụ vẫn là Resource Server tự kiểm JWT (zero trust) — nếu một dịch vụ bị truy cập trực tiếp từ trong mạng, nó không được mặc nhiên tin tưởng.

6. Dữ liệu xuyên dịch vụ: Saga

Đặt hàng cần: tạo đơn (Order) → giữ tồn kho (Inventory) → thanh toán (Payment). Ba CSDL riêng ⇒ không có transaction bao trùm. Giải pháp: Saga — chuỗi giao dịch cục bộ, mỗi bước có hành động bù trừ (compensating action) để hoàn tác nếu bước sau thất bại.

1. Order
Tạo đơn PENDING → phát OrderCreated
2. Inventory
Giữ hàng → phát StockReserved (hoặc StockFailed)
3. Payment
Trừ tiền → phát PaymentCompleted
4. Order
Nhận → đơn CONFIRMED
✗ Thanh toán thất bại
Phát PaymentFailed ⇒ Inventory nhả hàng (bù trừ) ⇒ Order CANCELLED
Mỗi bước là một transaction cục bộ; lỗi ⇒ chạy ngược các bù trừ, không rollback toàn cục.
Choreography (biên đạo)Orchestration (nhạc trưởng)
Cách điều phốiMỗi dịch vụ nghe sự kiện của dịch vụ khác và phản ứngMột orchestrator ra lệnh từng bước và theo dõi trạng thái
Kết dínhLỏng; không có điểm trung tâmLogic quy trình tập trung ở một chỗ
Khó khănKhó thấy toàn bộ luồng; dễ vòng lặp sự kiệnOrchestrator thêm một thành phần; có thể thành "god service"
Phù hợpQuy trình ngắn, ít bước (2-4)Quy trình dài, nhiều nhánh, cần theo dõi/trực quan hoá
  • Mỗi bước cần idempotent và dùng Outbox (chương 12) để phát sự kiện đáng tin cậy.
  • Hành động bù trừ không phải rollback: không thể "xoá" email đã gửi — bù trừ là gửi email huỷ. Thiết kế nghiệp vụ chấp nhận trạng thái trung gian (PENDING).
  • Lưu trạng thái saga rõ ràng (PENDING → CONFIRMED/CANCELLED) để truy vết và xử lý timeout (PENDING quá 15 phút ⇒ huỷ).

Một request người dùng giờ đi qua 5 dịch vụ. "Chậm" ở đâu? Không có công cụ, bạn mò mẫm bằng log của từng dịch vụ. Observability có ba trụ cột:

RestClient, KafkaTemplate, @Async do Spring cấu hình sẵn tự truyền traceparent (chuẩn W3C) — không cần code.
💡 Bốn con số vàng và probes

Theo dõi cho mỗi dịch vụ: lưu lượng, tỉ lệ lỗi, độ trễ (p95/p99), độ bão hoà (pool, CPU, hàng đợi) — Golden Signals. Liveness probe = "process còn sống không" (restart nếu hỏng); readiness probe = "sẵn sàng nhận request không" (rút khỏi load balancer khi DB mất). Đừng gộp DB vào liveness — DB lỗi mà K8s restart cả dịch vụ chỉ làm tệ thêm.

8. Virtual threads — thay đổi bài toán I/O

Mô hình cổ điển (Tomcat): một thread mỗi request; thread chặn khi chờ DB/HTTP, nên số request đồng thời bị giới hạn bởi pool thread (~200). Để vượt, người ta dùng lập trình phản ứng (WebFlux) — mạnh nhưng khó viết và debug. Java 21 virtual threads cho phép giữ code đồng bộ, đơn giản mà vẫn phục vụ hàng chục nghìn request đồng thời, vì chờ I/O không còn giữ thread hệ điều hành.

9. Bảo mật và kiểm thử giữa các dịch vụ

  • Truyền danh tính: chuyển tiếp JWT của người dùng (Authorization) qua RestClient interceptor; hoặc OAuth2 client credentials khi dịch vụ gọi dịch vụ tự thân (không có người dùng).
  • mTLS ở tầng hạ tầng (service mesh) để mã hoá & xác thực lẫn nhau trong mạng nội bộ.
  • Contract testing (Pact, Spring Cloud Contract): hợp đồng giữa consumer và provider được kiểm tự động trong CI ⇒ đổi API ở một bên không âm thầm làm vỡ bên kia (bổ sung cho OpenAPI — chương 8).
  • Test một dịch vụ bằng WireMock cho các dịch vụ khác + Testcontainers cho DB/broker (chương 11); chỉ có vài test end-to-end xuyên toàn hệ thống vì chúng chậm và mong manh.

Bài tập

Tách một module khỏi monolith

Từ dự án shop (modular monolith), tách inventory thành ứng dụng Boot riêng với CSDL riêng.

  • order gọi inventory qua RestClient có timeout (connect 500ms, read 2s).
  • Dừng inventory: order nhận lỗi gì, sau bao lâu? So sánh khi không đặt timeout.
  • Đã có ArchUnit (chương 8) — module có phụ thuộc ngược nào cản trở việc tách không?
Gợi ý

Không timeout ⇒ chờ rất lâu (hoặc đến khi OS bỏ kết nối) và cạn thread Tomcat. Phụ thuộc ngược (entity Product dùng chung) phải thay bằng bản sao dữ liệu cục bộ hoặc API — đó chính là chi phí của việc tách.

Circuit breaker thực nghiệm

Thêm Resilience4j cho InventoryClient. Viết một dịch vụ giả có endpoint chậm/lỗi theo công tắc.

  • Làm inventory trả 503 liên tục: sau bao nhiêu lời gọi mạch mở? Xem /actuator/circuitbreakers hoặc metric resilience4j.circuitbreaker.state.
  • Ở trạng thái OPEN gọi tiếp: thời gian phản hồi bao nhiêu? (≈ 0 ms) Vì sao đó là điều tốt?
  • Bật lại dịch vụ: mạch về CLOSED qua HALF_OPEN thế nào?
Gợi ý

minimum-number-of-calls: 10, failure-rate-threshold: 50 ⇒ mở sau ≥10 lời gọi với ≥50% lỗi. OPEN ⇒ CallNotPermittedException tức thì, fallback chạy; bên yếu có thời gian hồi phục.

Retry storm

Cho retry max-attempts: 5, không backoff, 200 client đồng thời gọi một dịch vụ đang quá tải.

  • Tính tổng lời gọi tối đa tới dịch vụ đó.
  • Sửa: backoff luỹ thừa + jitter, max-attempts: 3, thêm circuit breaker.
  • Vì sao retry một POST /payments không có Idempotency-Key là nguy hiểm?
Gợi ý

200 × 5 = 1.000 lời gọi dồn dập, đúng lúc dịch vụ yếu nhất ⇒ càng sập. Jitter rải các lần thử theo thời gian. POST không idempotent ⇒ có thể xử lý hai lần dù client chỉ "thử lại".

Saga đặt hàng (choreography)

Cài luồng đặt hàng ba dịch vụ bằng sự kiện (Kafka + Outbox): OrderCreated → StockReserved → PaymentCompleted → OrderConfirmed.

  • Cho Payment thất bại có chủ đích: kiểm tra Inventory nhả hàng và Order thành CANCELLED.
  • Một đơn PENDING quá 15 phút: viết job huỷ nó.
  • Vẽ sơ đồ trạng thái của Order và liệt kê hành động bù trừ của từng bước.
Gợi ý

Bù trừ: ReleaseStock (nhả hàng), RefundPayment (nếu đã trừ), CancelOrder. Mỗi bước phải idempotent vì sự kiện có thể giao lại. Ghi trạng thái saga trong bảng để job timeout và để truy vết.

Nhìn thấy request xuyên dịch vụ

Dựng docker-compose: hai dịch vụ Spring + OpenTelemetry Collector + Grafana Tempo (hoặc Jaeger) + Prometheus.

  • Gọi gateway → order → inventory; tìm trace theo traceId và đọc biểu đồ thác nước.
  • Làm chậm inventory 1,5 giây: nhìn trace thấy span nào dài?
  • Lọc log của cả hai dịch vụ theo cùng traceId.
Gợi ý

logging.pattern.correlation đưa traceId vào log; management.tracing.sampling.probability=1.0 khi thử. Trace cho biết ở đâu chậm; metrics cho biết có chậm thường xuyên không; log cho biết vì sao.

Quiz

Q1

Khi nào nên chọn microservices thay vì modular monolith?

Xem đáp án
✓ Đáp án

Khi có nhu cầu đo được mà monolith không đáp ứng: nhiều đội cần triển khai độc lập, một phần cần scale/công nghệ riêng, hoặc build/triển khai cả khối quá chậm — và đã có nền tảng (CI/CD, giám sát, đội vận hành) để gánh độ phức tạp phân tán. Với đội nhỏ, miền chưa ổn định: modular monolith, tách sau khi ranh giới đã rõ.

Q2

Vì sao mỗi microservice nên có CSDL riêng?

Xem đáp án
✓ Đáp án

Dùng chung CSDL biến ranh giới thành giả: đổi schema vỡ nhiều dịch vụ, không triển khai/scale độc lập, khoá và transaction chéo dịch vụ. CSDL riêng đảm bảo sở hữu dữ liệu — dịch vụ khác chỉ truy cập qua API hoặc sự kiện. Cái giá: mất join/transaction xuyên dịch vụ ⇒ Saga, bản sao cục bộ.

Q3

Circuit breaker hoạt động ra sao và vì sao cần?

Xem đáp án
✓ Đáp án

Theo dõi tỉ lệ lỗi/chậm: CLOSED (bình thường) → vượt ngưỡng ⇒ OPEN (từ chối ngay, không gọi) → sau một khoảng ⇒ HALF_OPEN (thử vài lời gọi) → thành công ⇒ CLOSED. Cần để ngăn lỗi lan truyền: không dồn thêm tải và không giữ thread chờ một dịch vụ đang hỏng, cho nó thời gian hồi phục.

Q4

Khi nào không nên retry? Retry có thể gây hại thế nào?

Xem đáp án
✓ Đáp án

Không retry thao tác không idempotent (trừ khi có idempotency key) và lỗi không tạm thời (4xx, lỗi nghiệp vụ). Retry nhân tải — nhiều client cùng retry gây retry storm làm dịch vụ yếu sập hẳn; cần backoff luỹ thừa + jitter, giới hạn số lần và đặt dưới circuit breaker.

Q5

Saga là gì? Choreography khác orchestration thế nào?

Xem đáp án
✓ Đáp án

Chuỗi giao dịch cục bộ giữa các dịch vụ, mỗi bước có hành động bù trừ khi bước sau thất bại (thay cho transaction phân tán). Choreography: dịch vụ tự phản ứng với sự kiện, không điểm trung tâm (hợp quy trình ngắn). Orchestration: một orchestrator điều khiển và theo dõi từng bước (hợp quy trình dài, nhiều nhánh).

Q6

Ba trụ cột của observability? Trace khác log ở đâu?

Xem đáp án
✓ Đáp án

Metrics (hệ thống có khoẻ không), logs (chuyện gì đã xảy ra), traces (một request đi qua những dịch vụ nào và mất bao lâu). Log là sự kiện rời rạc trong một dịch vụ; trace gắn các span xuyên dịch vụ bằng traceId truyền qua header traceparent, cho thấy chính xác nút thắt ở đâu.

Tổng kết

Sau chương 13, bạn đã nắm:

  • Mặc định modular monolith; chỉ tách microservices khi có nhu cầu đo được và đã có nền tảng vận hành.
  • Chia theo bounded context; database per service; giao tiếp qua API hoặc sự kiện, không qua CSDL.
  • **RestClient/HTTP Interface luôn kèm timeout**; ưu tiên sự kiện cho luồng ghi.
  • Resilience4j: timeout → retry (idempotent, backoff+jitter) → circuit breaker → bulkhead → fallback.
  • API Gateway ở biên; trên Kubernetes dùng DNS/ConfigMap thay Eureka/Config Server; mỗi dịch vụ vẫn kiểm JWT.
  • Saga (bù trừ) + Outbox + idempotent cho nhất quán xuyên dịch vụ.
  • Observability: Prometheus/Grafana, log có traceId, OpenTelemetry tracing; probes liveness/readiness; virtual threads cho I/O chặn.

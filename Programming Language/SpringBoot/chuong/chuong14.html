Chương 14 · Deploy & Capstone

Docker, deploy & dự án thực chiến — đưa Shop API lên chạy thật

Mười ba chương trước dạy bạn viết một backend. Chương cuối dạy phần còn lại để nó sống ngoài máy bạn: đóng gói thành image, dựng môi trường bằng một lệnh, kiểm thử và triển khai tự động, chạy trên Kubernetes mà không rớt request khi cập nhật, và kiểm tra nó đã "sẵn sàng production" chưa. Cuối chương là dự án thực chiến — Shop API — ghép lại toàn bộ 14 chương thành một sản phẩm có đặc tả, tiêu chí nghiệm thu và checklist chất lượng.

Fat JAR (chương 1) đã chạy được bằng java -jar. Container image thêm: JRE đúng phiên bản, hệ điều hành tối giản, và khả năng chạy y hệt ở mọi nơi (máy bạn, CI, staging, production). Ba cách tạo image cho Spring Boot:

1.1. Dockerfile multi-stage, tách lớp để cache

Dockerfile
# ---------- Giai đoạn 1: build ----------
FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace
COPY .mvn .mvn
COPY mvnw pom.xml ./
RUN ./mvnw -B -q dependency:go-offline              # lớp riêng cho dependency → chỉ chạy lại khi pom.xml đổi
COPY src src
RUN ./mvnw -B -q package -DskipTests                # test chạy ở CI, không lặp trong lúc build image
RUN java -Djarmode=layertools -jar target/*.jar extract --destination /layers   # tách JAR thành các lớp

# ---------- Giai đoạn 2: chạy ----------
FROM eclipse-temurin:21-jre
RUN groupadd --system app && useradd --system --gid app --no-create-home app    # KHÔNG chạy bằng root
WORKDIR /app
# Thứ tự từ ít đổi → hay đổi: lớp nào không đổi thì Docker dùng lại cache, push/pull chỉ lớp nhỏ
COPY --from=build /layers/dependencies/ ./
COPY --from=build /layers/spring-boot-loader/ ./
COPY --from=build /layers/snapshot-dependencies/ ./
COPY --from=build /layers/application/ ./           # code của bạn — lớp nhỏ nhất, đổi nhiều nhất
USER app
EXPOSE 8080
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
HEALTHCHECK --interval=30s --timeout=3s --start-period=40s \
  CMD wget -qO- http://localhost:8080/actuator/health/liveness || exit 1
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]
Điểm đáng chú ýVì sao
Multi-stageImage chạy chỉ có JRE + app, không có JDK/Maven/mã nguồn ⇒ nhỏ hơn, ít bề mặt tấn công
**Tách lớp (layertools)**Dependency (chục MB) hiếm đổi; code của bạn (vài trăm KB) đổi mỗi commit ⇒ chỉ lớp nhỏ phải đẩy/kéo lại
**USER app**Process bị khai thác cũng không có quyền root trong container
Tag cụ thể, không dùng latestBuild tái lập; biết chính xác đang chạy phiên bản nào (1.0.0, git-sha)
Bí mật không nằm trong imageTruyền bằng biến môi trường/secret lúc chạy (chương 3); lớp image có thể bị trích ra

Ghi chú về phiên bản công cụ

Từ Spring Boot 3.3, chế độ -Djarmode=tools là cách khuyến nghị thay cho layertools (cú pháp và tên thư mục đầu ra khác một chút). Hãy đối chiếu Spring Boot Reference → Efficient Container Images cho phiên bản Boot bạn dùng; nguyên tắc (tách dependency/application để tận dụng cache lớp) không đổi.

1.2. JVM trong container

  • Bộ nhớ: JVM hiện đại nhận biết giới hạn cgroup. Dùng -XX:MaxRAMPercentage=75 (heap tối đa 75% bộ nhớ container) thay vì -Xmx cứng; chừa chỗ cho metaspace, thread stack, direct buffer. Heap = 100% ⇒ bị OOMKilled bởi kernel.
  • CPU: limits.cpu: 1 làm JVM thấy 1 lõi ⇒ ít thread GC/ForkJoin. Cấp tối thiểu 2 CPU nếu muốn GC hoạt động ổn.
  • -XX:+ExitOnOutOfMemoryError: hết bộ nhớ thì chết hẳn để orchestrator khởi động lại, thay vì sống dở chết dở.
  • Thời gian khởi động: Boot thông thường 2-6 giây; liên quan tới readiness probe (mục 4).

2. docker-compose — môi trường dev một lệnh

3. CI/CD với GitHub Actions

Mục tiêu: mỗi push ⇒ chạy test, build image, đẩy lên registry; merge vào main ⇒ triển khai. Mọi bước tự động và tái lập — không có "build trên máy anh A" (xem DevOps chương 4-5).

.github/workflows/ci.yml
name: ci
on:
  push:
    branches: [ main ]
  pull_request:

permissions:
  contents: read
  packages: write                        # đẩy image lên GitHub Container Registry

jobs:
  test:
    runs-on: ubuntu-latest               # có sẵn Docker ⇒ Testcontainers chạy được
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21
          cache: maven                    # cache ~/.m2 → build nhanh hơn nhiều
      - name: Test (unit + slice + integration)
        run: ./mvnw -B verify
      - name: Báo cáo test khi lỗi
        if: failure()
        uses: actions/upload-artifact@v4
        with: { name: surefire-reports, path: target/surefire-reports }

  image:
    needs: test                           # chỉ build image khi test xanh
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:${{ github.sha }}
            ghcr.io/${{ github.repository }}:latest
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: image
    runs-on: ubuntu-latest
    environment: production               # có thể bật "required reviewers" = phê duyệt thủ công
    steps:
      - name: Cập nhật image trên cluster
        run: |
          kubectl set image deployment/shop-api api=ghcr.io/${{ github.repository }}:${{ github.sha }}
          kubectl rollout status deployment/shop-api --timeout=180s     # lỗi → pipeline đỏ → có thể rollout undo
  • **Tag image bằng git sha** — biết chính xác code nào đang chạy và rollback về sha trước dễ dàng.
  • Bí mật (kubeconfig, token) lưu trong GitHub Secrets/Environments, không bao giờ trong repo.
  • Chia đôi test: unit/slice nhanh chạy trước (phản hồi sớm); integration (Testcontainers) sau — hoặc chạy song song.
  • Thêm bước quét bảo mật: dependency-check/Dependabot (thư viện), Trivy (image) — chương 9, DevOps chương 12.

4. Triển khai lên Kubernetes

k8s/shop-api.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxUnavailable: 0, maxSurge: 1 }          # luôn đủ 3 pod sẵn sàng khi cập nhật
  selector:
    matchLabels: { app: shop-api }
  template:
    metadata:
      labels: { app: shop-api }
    spec:
      terminationGracePeriodSeconds: 45                         # > thời gian shutdown của Spring (mục dưới)
      containers:
        - name: api
          image: ghcr.io/itbasic/shop-api:abc123
          ports: [ { containerPort: 8080 } ]
          envFrom:
            - configMapRef: { name: shop-api-config }           # cấu hình KHÔNG nhạy cảm
          env:
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom: { secretKeyRef: { name: shop-api-secret, key: db-password } }   # bí mật
            - name: JWT_SECRET
              valueFrom: { secretKeyRef: { name: shop-api-secret, key: jwt-secret } }
          resources:
            requests: { cpu: "500m", memory: "768Mi" }
            limits:   { cpu: "2",    memory: "1Gi" }             # JVM: MaxRAMPercentage=75 → heap ~768Mi
          startupProbe:                                          # cho JVM thời gian khởi động
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            failureThreshold: 30
            periodSeconds: 2
          readinessProbe:                                        # "sẵn sàng nhận request?" — false ⇒ rút khỏi Service
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
          livenessProbe:                                         # "process còn sống?" — false ⇒ K8s restart pod
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 10
            failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata: { name: shop-api }
spec:
  selector: { app: shop-api }
  ports: [ { port: 80, targetPort: 8080 } ]

4.1. Graceful shutdown — cập nhật không rớt request

Khi K8s thay pod cũ, nó gửi SIGTERM. Mặc định app có thể bị tắt giữa lúc đang xử lý request ⇒ client nhận lỗi. Bật tắt máy êm:

application.yml
server:
  shutdown: graceful                       # ngừng nhận request MỚI, đợi request đang chạy xong
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s        # tối đa chờ 30s rồi tắt cứng
1. SIGTERM
K8s báo pod cần dừng; đồng thời rút pod khỏi endpoint của Service
2. Readiness = REFUSING_TRAFFIC
Spring chuyển readiness sang false, từ chối kết nối mới
3. Xử lý nốt
Request đang chạy được hoàn thành (≤ 30s)
4. Đóng tài nguyên
@PreDestroy, đóng pool DB, ngắt listener Kafka
5. Thoát
JVM thoát trước terminationGracePeriodSeconds (45s)
Rolling update + readiness + graceful shutdown ⇒ zero-downtime deploy.
⚠️ Tách bạch liveness và readiness

Liveness chỉ trả lời "process có bị treo không?" — nếu gộp kiểm tra DB vào liveness, DB chậm ⇒ K8s restart tất cả pod ⇒ sập cả hệ thống do chính cơ chế tự chữa. Readiness mới là nơi phản ánh phụ thuộc (DB, cache): sai ⇒ chỉ rút khỏi load balancer. Boot management.endpoint.health.probes.enabled=true tự dựng hai nhóm này (chương 13).

4.2. Migration khi triển khai

Với 3 replica khởi động cùng lúc, Flyway dùng khoá bảng để chỉ một instance chạy migration, các instance khác chờ — an toàn. Nhưng nguyên tắc tương thích ngược (chương 7: expand → migrate → contract) là bắt buộc, vì trong lúc rolling update, code cũ và code mới cùng chạy trên cùng schema. Cách thận trọng hơn: chạy migration bằng một Job/initContainer riêng trước khi triển khai code mới.

Chiến lượcCách làmPhù hợp

Blue/GreenDựng bản mới song song (green), kiểm tra, rồi chuyển toàn bộ lưu lượng một lần; giữ blue để quay lại ngayCần rollback tức thì; tốn gấp đôi tài nguyên tạm thời

6. GraalVM native image — khởi động tính bằng mili-giây

Spring Boot 3 hỗ trợ biên dịch ứng dụng thành file thực thi native (AOT — ahead-of-time) bằng GraalVM, không cần JVM lúc chạy.

Build native

📌 Lựa chọn thay thế

Muốn khởi động nhanh mà không đánh đổi nhiều: CRaC (checkpoint/restore — chụp JVM đã "nóng" rồi khôi phục, Boot 3.2+ có hỗ trợ trên JDK build kèm CRaC) và Class Data Sharing/AppCDS (giảm thời gian khởi động JVM thông thường vài chục %). Mặc định: JVM thường, đo trước khi chuyển.

7.5. Checklist chất lượng cuối cùng (14 mục)

  • ☐ Mọi cấu hình/bí mật qua biến môi trường; thiếu bí mật ⇒ fail fast; không bí mật nào trong Git hay image.
  • ☐ Không entity lộ ra response; DTO record; MapStruct báo lỗi biên dịch khi thiếu ánh xạ.
  • ☐ Mọi endpoint ghi có validation @Valid; lỗi trả application/problem+json; không lộ stack trace/SQL.
  • ☐ open-in-view: false; không N+1 (có test đếm câu SQL cho endpoint danh sách).
  • ☐ @Transactional ở service; exception nghiệp vụ unchecked; không gọi mạng chậm trong transaction.
  • ☐ Không mất cập nhật: @Version hoặc khoá bi quan cho tồn kho; test đồng thời.
  • ☐ Mọi tài nguyên của người dùng kiểm sở hữu (IDOR); test phân quyền cho từng endpoint nhạy cảm.
  • ☐ Mật khẩu BCrypt/Argon2; access ngắn hạn, refresh rotation + hash trong DB; đăng nhập có rate limit.
  • ☐ Mọi lời gọi ra ngoài có timeout; retry chỉ cho idempotent; circuit breaker; Idempotency-Key cho POST thanh toán.
  • ☐ Sự kiện đi qua Outbox; consumer idempotent; có DLQ và cảnh báo.
  • ☐ Flyway quản lý schema, tương thích ngược; có sao lưu và đã thử khôi phục.
  • ☐ Test xanh trong CI (unit + slice + Testcontainers); quét phụ thuộc & image.
  • ☐ Image multi-stage, non-root, tag theo sha; graceful shutdown + probes; đã thử rollback.
  • ☐ Có metrics + dashboard + cảnh báo, log JSON có traceId, tracing xuyên dịch vụ.
Dự án chỉ "xong" khi bạn chứng minh được từng mục trong checklist bằng test hoặc bằng một thao tác kiểm chứng — không phải bằng niềm tin. "Chạy được trên máy tôi" chưa phải production-ready.

Bài tập

Container hoá Shop API

Viết Dockerfile multi-stage và docker-compose.yml (app + PostgreSQL + Redis) như mục 1-2.

  • docker images: kích thước image? So với image eclipse-temurin:21-jdk thuần.
  • Sửa một dòng code rồi build lại: lớp nào được build lại, lớp nào dùng cache? Quan sát bằng docker build output.
  • Kiểm tra docker exec <c> whoami — kết quả? Vì sao không được là root?
Gợi ý

Chỉ lớp application (code của bạn) build lại nếu pom.xml không đổi; lớp dependencies dùng cache. whoami phải là app. Image runtime nhỏ hơn nhiều vì không có JDK/Maven/source.

Pipeline CI/CD

Tạo workflow GitHub Actions: test (Testcontainers) → image (đẩy lên GHCR, tag bằng sha) → deploy (có phê duyệt thủ công qua Environment).

  • Làm một test đỏ có chủ đích: pipeline dừng ở đâu, image có được đẩy không?
  • Thêm quét trivy image và cho pipeline đỏ khi gặp lỗ hổng CRITICAL.
  • Giải thích vì sao tag latest đơn lẻ không đủ để rollback.
Gợi ý

needs: test làm job image bị bỏ qua khi test đỏ. latest thay đổi liên tục — không biết phiên bản trước đó là gì; tag sha bất biến cho phép kubectl set image …:<sha_cũ> hoặc rollout undo.

Zero-downtime deploy

Triển khai lên cluster cục bộ (kind/minikube) theo manifest ở mục 4. Dùng k6/hey bắn tải liên tục vào /api/v1/products.

  • Cập nhật image trong lúc đang bắn tải: có request nào lỗi không?
  • Tắt server.shutdown=graceful và readinessProbe, thử lại: so sánh số lỗi.
  • Giải thích vai trò của maxUnavailable: 0, readiness và terminationGracePeriodSeconds.
Gợi ý

Với đủ ba yếu tố (rolling maxUnavailable: 0, readiness, graceful shutdown) số lỗi gần như 0. Thiếu một trong ba, request có thể bị gửi vào pod đang tắt hoặc chưa sẵn sàng ⇒ 502/503 và kết nối bị reset.

Chứng minh M5: không bán quá tồn kho

Viết integration test (Testcontainers) cho kịch bản: sản phẩm còn 10, 50 luồng cùng đặt mua 1 cái.

  • Cài đặt ngây thơ (đọc → trừ → lưu): kết quả? (thường bán > 10.)
  • Sửa bằng @Version + thử lại, rồi bằng SELECT … FOR UPDATE; hoặc UPDATE products SET stock = stock - 1 WHERE id = ? AND stock >= 1.
  • So sánh ba cách về độ phức tạp, thông lượng và khả năng xảy ra deadlock.
Gợi ý

UPDATE … SET stock = stock - 1 WHERE stock >= 1 kiểm tra số dòng bị ảnh hưởng (0 ⇒ hết hàng) là cách nguyên tử và rẻ nhất — không cần khoá phía ứng dụng. @Version đúng nhưng sinh nhiều lần thử lại khi tranh chấp cao; FOR UPDATE tuần tự hoá nhưng có thể nghẽn.

Đánh giá production-readiness

Lấy dự án Shop API của bạn và chấm theo 14 mục checklist (7.5), mỗi mục Đạt / Chưa đạt kèm bằng chứng (tên test, lệnh kiểm tra, ảnh chụp dashboard).

  • Với mỗi mục Chưa đạt, ghi một issue có tiêu chí hoàn thành.
  • Chọn 3 mục rủi ro cao nhất (bảo mật, mất dữ liệu, sập dịch vụ) và sửa trước.
  • Trình bày ngắn (5 phút) cho một người bạn: vì sao hệ thống này an toàn để mở cho người dùng thật?
Gợi ý

Bằng chứng tốt là có thể chạy lại: một test, một lệnh curl, một truy vấn, một biểu đồ. Ưu tiên theo tác hại × khả năng xảy ra: lộ dữ liệu người dùng, mất/hỏng dữ liệu, ngừng dịch vụ đứng đầu.

Quiz

Q1

Vì sao dùng Dockerfile multi-stage và tách lớp (layered JAR)?

Xem đáp án
✓ Đáp án

Multi-stage cho image chạy chỉ có JRE + app (không JDK/Maven/source) ⇒ nhỏ, ít bề mặt tấn công. Tách lớp đưa dependency (to, hiếm đổi) và code (nhỏ, đổi nhiều) vào các lớp khác nhau ⇒ Docker dùng lại cache, mỗi lần build/push/pull chỉ lớp nhỏ thay đổi.

Q2

Liveness và readiness probe khác nhau ra sao? Vì sao không nên đưa DB vào liveness?

Xem đáp án
✓ Đáp án

Liveness: process còn sống không — sai ⇒ K8s restart pod. Readiness: sẵn sàng nhận request không — sai ⇒ rút khỏi Service (không restart). Nếu liveness kiểm DB, DB chậm làm mọi pod bị restart liên tục — sập cả hệ thống do chính cơ chế tự chữa; phụ thuộc phải phản ánh ở readiness.

Q3

Graceful shutdown giúp gì khi triển khai?

Xem đáp án
✓ Đáp án

Khi nhận SIGTERM, Spring ngừng nhận kết nối mới (readiness chuyển sang từ chối), hoàn tất request đang chạy (trong timeout-per-shutdown-phase) rồi mới đóng tài nguyên. Kết hợp rolling update maxUnavailable: 0 và readiness ⇒ cập nhật phiên bản không rớt request.

Q4

Vì sao nên tag image bằng git sha thay vì latest?

Xem đáp án
✓ Đáp án

latest là con trỏ thay đổi — không biết chính xác code nào đang chạy và không có "phiên bản trước" để quay lại. Tag sha bất biến và truy được về commit ⇒ build tái lập, triển khai/rollback chính xác (kubectl set image …:<sha>).

Q5

Khi nào nên cân nhắc GraalVM native image?

Xem đáp án
✓ Đáp án

Khi khởi động nhanh và RAM thấp là sống còn: serverless/scale-to-zero, tác vụ ngắn, mật độ container cao. Đánh đổi: build lâu, hint cho reflection/proxy, ít thư viện tương thích, throughput đỉnh thấp hơn JIT, debug hạn chế. Dịch vụ chạy lâu dài thông thường nên giữ JVM.

Q6

Rolling update khác blue/green và canary thế nào?

Xem đáp án
✓ Đáp án

Rolling: thay dần từng pod (tiết kiệm, cần tương thích ngược giữa hai phiên bản). Blue/Green: dựng bản mới song song, kiểm tra rồi chuyển toàn bộ lưu lượng, giữ bản cũ để quay lại tức thì (tốn gấp đôi tài nguyên tạm). Canary: chuyển tỉ lệ nhỏ lưu lượng (5%→25%→100%) và theo dõi chỉ số trước khi mở rộng — giảm rủi ro cho thay đổi lớn.

Tổng kết

Sau chương 14, bạn đã nắm:

  • Image: multi-stage + layered + non-root, hoặc Buildpacks/Jib; JVM trong container dùng MaxRAMPercentage, cấp ≥ 2 CPU; bí mật không nằm trong image.
  • docker-compose (hoặc spring-boot-docker-compose) dựng dev một lệnh; depends_on với healthcheck.
  • CI/CD: test (Testcontainers) → build/đẩy image tag sha → triển khai có phê duyệt; quét bảo mật trong pipeline.
  • Kubernetes: ConfigMap/Secret, requests/limits, startup/readiness/liveness, graceful shutdown, rolling maxUnavailable: 0 ⇒ zero-downtime.
  • Migration phải tương thích ngược; chọn rolling / blue-green / canary theo rủi ro.
  • Checklist production-readiness (14 mục) là thước đo; mỗi mục cần bằng chứng. Native image chỉ khi khởi động/RAM là sống còn.
  • Shop API ghép cả sub-pillar: từ DI, REST, JPA, bảo mật, JWT, test, cache/queue, chịu lỗi đến CI/CD và vận hành.

IoC & Dependency Injection — trái tim của Spring

Mọi thứ trong Spring xoay quanh một ý tưởng: **đừng tự new những thứ bạn phụ thuộc — hãy khai báo bạn cần gì, và để container đưa cho bạn**. Đó là Inversion of Control (đảo ngược quyền kiểm soát) và hình thức phổ biến nhất của nó, Dependency Injection. Hiểu chương này là hiểu 80% cách Spring vận hành: @Transactional, @Cacheable, security, controller — tất cả đều là bean do container tạo và "bọc" lại.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-1
🎯 Mục tiêu chương
  • Giải thích IoC và DI — vấn đề chúng giải quyết, bằng ví dụ không dùng Spring.
  • Hiểu ApplicationContext và bean là gì.
  • Khai báo bean bằng stereotype (@Component, @Service, @Repository) và bằng @Configuration + @Bean.
  • Chọn đúng kiểu tiêm: constructor (mặc định), setter, field (tránh) — và biết lý do.
  • Xử lý nhiều bean cùng kiểu: @Primary, @Qualifier, tiêm List/Map.
  • Nắm scope (singleton, prototype, request) và cái bẫy thread-safety của singleton.
  • Vẽ được vòng đời bean; dùng @PostConstruct, @PreDestroy.
  • Hiểu phụ thuộc vòng và proxy (nền của @Transactional).

1. Vấn đề: tự tạo phụ thuộc

Xem một service gửi thông báo đơn hàng, không dùng Spring:

DonHangService.java
public class DonHangService {

    // ❌ Tự tạo phụ thuộc → dính chặt vào một cài đặt cụ thể
    private final EmailSender sender = new SmtpEmailSender("smtp.example.com", 587, "user", "pass");

    public void datHang(DonHang dh) {
        // ... lưu đơn ...
        sender.gui(dh.emailKhach(), "Đặt hàng thành công");
    }
}

Ba vấn đề lộ ra ngay:

  • Không test được. Test datHang sẽ gửi email thật. Không có chỗ nào để thay bằng bản giả.
  • Không đổi được. Muốn đổi sang SendGrid? Sửa mọi nơi có new SmtpEmailSender(...).
  • Lộ chi tiết. DonHangService phải biết host, port, mật khẩu SMTP — chuyện không liên quan tới nó.

1.1. Giải pháp: nhận phụ thuộc từ bên ngoài

DonHangService.java
public class DonHangService {

    private final EmailSender sender;                 // phụ thuộc vào GIAO DIỆN, không phải lớp cụ thể

    public DonHangService(EmailSender sender) {       // "đưa" từ ngoài vào qua constructor
        this.sender = sender;
    }
    // ...
}

// Nơi duy nhất biết ghép gì với gì ("composition root"):
EmailSender sender = new SmtpEmailSender("smtp.example.com", 587, "user", "pass");
DonHangService service = new DonHangService(sender);

// Trong test:
DonHangService test = new DonHangService(new FakeEmailSender());
Dependency Injection = một đối tượng nhận phụ thuộc từ ngoài thay vì tự tạo. Inversion of Control = quyền quyết định "dùng cài đặt nào, tạo lúc nào, huỷ lúc nào" chuyển từ code của bạn sang một thành phần khác (container). Bạn đã làm DI ở trên mà không cần framework — Spring chỉ tự động hoá việc ghép.

Với 3 lớp thì ghép tay ổn. Với 300 lớp, mỗi lớp cần 3-5 phụ thuộc, có vòng đời khác nhau, cần bọc transaction/cache/bảo mật — bạn cần một container làm việc đó. Đó là Spring.

2. IoC container và bean

**ApplicationContext là container của Spring. Nó (1) nắm danh sách định nghĩa bean, (2) tạo bean theo đúng thứ tự phụ thuộc, (3) tiêm chúng vào nhau, (4) quản lý vòng đời tới lúc tắt. Bean** đơn giản là một object do container quản lý.

Dùng context thủ công (chỉ để hiểu — ít khi viết thế này)
ConfigurableApplicationContext ctx = SpringApplication.run(DemoApplication.class, args);

DonHangService s = ctx.getBean(DonHangService.class);   // lấy bean theo kiểu
String[] ten = ctx.getBeanDefinitionNames();             // liệt kê mọi bean (hàng trăm do Boot tạo)
System.out.println(ten.length + " bean");
📌 Đừng gọi getBean() trong code nghiệp vụ

Gọi ctx.getBean() là Service Locator — bạn tự đi lấy phụ thuộc, mất lợi ích của DI (phụ thuộc bị giấu, khó test). Hãy khai báo phụ thuộc ở constructor và để Spring tiêm.

3.2. @Configuration + @Bean — cho code bạn không sở hữu

Bạn không thể đặt @Component lên ObjectMapper, RestClient, HikariDataSource… vì đó là lớp của thư viện. Hãy dùng method @Bean:

AppConfig.java
@Configuration
public class AppConfig {

    @Bean
    public RestClient paymentClient(@Value("${payment.base-url}") String baseUrl) {
        return RestClient.builder()
                .baseUrl(baseUrl)
                .defaultHeader("Accept", "application/json")
                .build();
    }

    @Bean
    public Clock clock() {                 // đóng gói thời gian để test được (chương 11)
        return Clock.systemUTC();
    }
}
Dùng @Component/@Service khiDùng @Bean khi
Lớp do bạn viếtLớp của thư viện
Cấu hình đơn giản, cần quét tự độngCần logic tạo phức tạp / tham số tuỳ biến
Mặc định cho 95% trường hợpCấu hình hạ tầng (client, mapper, clock…)

@Configuration được "bọc" (CGLIB) để giữ singleton

Trong lớp @Configuration, nếu method @Bean này gọi method @Bean kia, Spring chặn lời gọi và trả về bean đã có thay vì chạy lại method.

Bean method gọi nhau
@Configuration
class C {
    @Bean A a() { return new A(b()); }   // b() trả về CÙNG bean B với bean "b" bên dưới
    @Bean B b() { return new B(); }
}

Chế độ này tên là full mode. @Configuration(proxyBeanMethods = false) tắt việc bọc để khởi động nhanh hơn — chỉ an toàn khi các method @Bean không gọi nhau (Boot dùng cách này cho auto-config).

4. Ba kiểu tiêm phụ thuộc

Ba cách

    // (3) FIELD — tránh dùng
    @Autowired private B b;                   // ngắn, nhưng nhiều tác hại
}

Mặc định: constructor injection. Nếu constructor có quá nhiều tham số (≥ 5) đó là tín hiệu thiết kế: lớp đang làm quá nhiều việc — hãy tách, đừng chuyển sang field injection để "giấu" nó.

Tuỳ chọn gọn hơn cho lớp có nhiều trường: dùng record cho DTO nhưng với bean thì giữ constructor tường minh. (Lombok @RequiredArgsConstructor cũng sinh constructor cho các trường final; chấp nhận được nếu đội đã dùng Lombok.)

5. Nhiều bean cùng kiểu

Giả sử có hai cài đặt:

Hai cài đặt
public interface ThanhToan { String ten(); void tra(long soTien); }

@Component class ThanhToanMomo  implements ThanhToan { /* ... */ }
@Component class ThanhToanVnPay implements ThanhToan { /* ... */ }

@Service
class DonHangService {
    DonHangService(ThanhToan tt) { }       // 💥 NoUniqueBeanDefinitionException: có 2 ứng viên
}

Lỗi "expected single matching bean but found 2" — Spring không đoán. Ba cách giải:

Giải pháp
// (a) @Primary — "mặc định" khi không chỉ rõ
@Component @Primary class ThanhToanMomo implements ThanhToan { }

// (b) @Qualifier — chọn đích danh theo tên bean
@Service
class DonHangService {
    DonHangService(@Qualifier("thanhToanVnPay") ThanhToan tt) { }
}

// (c) Tiêm TẤT CẢ rồi tự chọn lúc chạy — mẫu Strategy
@Service
class ThanhToanFacade {
    private final Map<String, ThanhToan> theoTen;

    ThanhToanFacade(List<ThanhToan> tatCa) {                       // Spring tiêm mọi bean kiểu ThanhToan
        this.theoTen = tatCa.stream().collect(Collectors.toMap(ThanhToan::ten, t -> t));
    }

    void tra(String phuongThuc, long soTien) {
        ThanhToan t = theoTen.get(phuongThuc);
        if (t == null) throw new IllegalArgumentException("Không hỗ trợ: " + phuongThuc);
        t.tra(soTien);
    }
}
💡 Cách (c) là mẫu Strategy không if/else

Thêm phương thức thanh toán mới = thêm một lớp @Component; không sửa ThanhToanFacade (Open/Closed — SOLID ở sub-pillar OOP). Cũng có thể tiêm Map<String, ThanhToan> trực tiếp: khoá là tên bean. Thứ tự trong List điều khiển bằng @Order.

⚠️ Bẫy lớn nhất của singleton: trạng thái dùng chung

Một bean singleton được mọi request/thread dùng chung. Nếu nó có field thay đổi được, bạn có race condition.

SaiLam.java
@Service
class DemService {
    private int soLanGoi = 0;                    // ❌ trạng thái dùng chung giữa mọi request

    public int tang() { return ++soLanGoi; }     // 2 thread đồng thời → mất cập nhật
}

// ✅ Cách đúng: service KHÔNG giữ trạng thái người dùng. Đếm thật thì:
@Service
class DemService2 {
    private final AtomicInteger soLanGoi = new AtomicInteger();   // thread-safe
    public int tang() { return soLanGoi.incrementAndGet(); }
}

Quy tắc thực dụng: service/repository/controller không có field mutable; mọi dữ liệu theo từng request đi qua tham số và biến cục bộ. (Chương 12 của sub-pillar Java về đa luồng giải thích vì sao.)

@Component
public class CacheLoader {

    private static final Logger log = LoggerFactory.getLogger(CacheLoader.class);
    private final ProductRepository repo;

Hai công cụ liên quan: @Lazy (chỉ tạo bean khi lần đầu cần — giảm thời gian khởi động nhưng đẩy lỗi cấu hình ra lúc chạy) và ApplicationRunner/CommandLineRunner (chạy code sau khi context đã sẵn sàng, hợp với seed dữ liệu).

8. Phụ thuộc vòng

Vòng
@Service class A { A(B b) { } }
@Service class B { B(A a) { } }       // A cần B, B cần A → không thể tạo cái nào trước

Từ Spring Boot 2.6, tham chiếu vòng bị cấm mặc định — khởi động thất bại với thông báo The dependencies of some of the beans in the application context form a cycle. Đừng bật spring.main.allow-circular-references=true để "cho qua": vòng là tín hiệu thiết kế sai. Cách gỡ:

  • Tách một lớp thứ ba C chứa phần chung mà cả A và B cần; A→C, B→C.
  • Đảo hướng bằng sự kiện (ApplicationEventPublisher): A phát sự kiện, B lắng nghe — không còn tham chiếu trực tiếp.
  • Giao diện hẹp: A chỉ cần một khả năng nhỏ của B — định nghĩa interface nhỏ đó.
  • Cách cuối cùng: @Lazy ở một tham số để tiêm proxy trễ — vá, không phải chữa.

9. Proxy — vì sao @Transactional hoạt động (và khi nào không)

Khi bạn viết @Transactional, @Cacheable, @Async, @PreAuthorize…, Spring không sửa code của bạn. Ở bước 5 của vòng đời, nó bọc bean trong một proxy chặn lời gọi method: chạy logic phụ (mở transaction, kiểm quyền…) rồi mới gọi method thật.

Controller
gọi service.chuyenTien()
Proxy (do Spring tạo)
mở transaction, kiểm tra cache/quyền
Bean thật
chạy method của bạn
Proxy
commit / rollback
Controller không giữ bean thật mà giữ proxy — nên mọi lời gọi từ ngoài đều đi qua nó.
⚠️ Self-invocation — bẫy kinh điển

Gọi method @Transactional từ method khác trong cùng lớp (this.chuyenTien()) không qua proxy ⇒ annotation bị bỏ qua.

SelfInvocation.java
@Service
class BaoCaoService {

    public void xuatBaoCao() {
        // ...
        luuKetQua();                       // ❌ gọi qua `this`, KHÔNG qua proxy → không có transaction
    }

    @Transactional
    public void luuKetQua() { /* ... */ }
}

// ✅ Sửa: tách sang bean khác, gọi từ ngoài vào
@Service class BaoCaoService { BaoCaoLuu luu; void xuatBaoCao() { luu.luuKetQua(); } }
@Service class BaoCaoLuu     { @Transactional public void luuKetQua() { /* ... */ } }

Ngoài ra proxy chỉ chặn được method **public và lớp không final** (CGLIB cần kế thừa). Chương 7 sẽ quay lại với @Transactional chi tiết.

Từ new sang DI

Cho đoạn code dưới đây, hãy: (1) viết interface ThongBao và hai cài đặt Email, Sms; (2) refactor DonHangService nhận ThongBao qua constructor; (3) viết unit test không dùng Spring với một ThongBao giả.

Trước
class DonHangService {

    void datHang(DonHang d) { /* ... */ sms.gui(d.sdt(), "Đã đặt hàng"); }

Gợi ý

Test không cần Spring: new DonHangService(daGui::add) nếu ThongBao là interface một method (functional interface) — lambda là bản giả. Đó là lợi ích lớn nhất của constructor injection.

Strategy bằng List/Map

Xây PhiVanChuyenService tính phí theo hãng (GHN, GHTK, VIETTEL). Mỗi hãng là một bean PhiVanChuyen. PhiVanChuyenService.tinh(hang, khoiLuong) chọn đúng bean — **không dùng if/else**.

  • Dùng Map<String, PhiVanChuyen> tiêm trực tiếp.
  • Thêm hãng thứ 4 mà không sửa PhiVanChuyenService.
  • Hãng lạ → ném IllegalArgumentException có thông điệp rõ.
Gợi ý

Tên bean mặc định là tên lớp viết thường chữ đầu (ghn). Muốn khoá khác, @Component("GHN"). Hoặc cho interface một method ma() và tự dựng map từ List.

Tìm và sửa race condition

Viết @Service BoDemTruyCap với field int dem và method tang(). Viết test gọi tang() 10.000 lần từ 8 thread (ExecutorService).

  • Quan sát kết quả cuối — có bằng 10.000 không?
  • Sửa bằng AtomicInteger. Rồi nêu cách khác nếu cần giữ trạng thái theo người dùng.
Gợi ý

Nếu cần trạng thái theo người dùng, đừng giữ trong singleton: lưu ở CSDL/Redis (chương 12) hoặc request/session scope. AtomicInteger chỉ hợp cho bộ đếm toàn cục.

Gỡ phụ thuộc vòng

Tạo UserService (cần OrderService để đếm đơn của user) và OrderService (cần UserService để kiểm tra user tồn tại). Chạy — đọc thông báo lỗi — rồi gỡ vòng bằng hai cách khác nhau.

  • Cách 1: tách UserLookup (chỉ đọc user) dùng chung.
  • Cách 2: OrderService phát OrderCreatedEvent; UserStatsListener lắng nghe.
  • So sánh ưu/nhược.
Gợi ý

Cách 1 đơn giản, giữ gọi đồng bộ. Cách 2 tách rời hẳn nhưng luồng khó theo dõi hơn (ẩn trong listener) và mặc định chạy cùng thread/transaction của bên phát (@TransactionalEventListener nếu cần sau commit).

Bắt tận tay self-invocation

Viết service có public void a() (không @Transactional) gọi b() có @Transactional. In ra TransactionSynchronizationManager.isActualTransactionActive() trong b().

  • Gọi a() từ controller: transaction có bật không?
  • Gọi b() thẳng từ controller: kết quả?
  • Sửa để a() → b() vẫn có transaction (hai cách).
Gợi ý

Gọi qua this ⇒ false; gọi b() từ ngoài ⇒ true. Sửa: chuyển b() sang bean khác; hoặc đặt @Transactional lên a(); (cách thứ ba, ít dùng: tiêm chính nó/AopContext.currentProxy()).

Quiz

Q1

IoC và DI khác nhau thế nào?

Xem đáp án
✓ Đáp án

IoC là nguyên lý rộng: quyền kiểm soát việc tạo & kết nối đối tượng chuyển từ code của bạn sang container. DI là kỹ thuật hiện thực IoC: đối tượng nhận phụ thuộc từ ngoài (qua constructor/setter) thay vì tự new. Spring dùng DI để thực thi IoC.

Q2

Vì sao nên dùng constructor injection thay vì field injection?

Xem đáp án
✓ Đáp án
  • Trường final → bất biến, thread-safe hơn.
  • Phụ thuộc hiện rõ trong chữ ký; quá nhiều tham số lộ ra lớp làm quá nhiều việc.
  • Unit test không cần Spring: new A(fake).
  • Phụ thuộc vòng bị phát hiện ngay lúc khởi động.
Q3

Có hai bean cùng kiểu ThanhToan. Cách nào để Spring biết chọn bean nào?

Xem đáp án
✓ Đáp án

@Primary (bean mặc định), @Qualifier("tên") (chọn đích danh), hoặc tiêm List<ThanhToan>/Map<String, ThanhToan> để tự chọn lúc chạy (mẫu Strategy). Tên tham số trùng tên bean cũng có thể được dùng làm gợi ý nhưng mong manh — không nên dựa vào.

Q4

Vì sao bean singleton không nên giữ trạng thái theo từng người dùng?

Xem đáp án
✓ Đáp án

Singleton chỉ có một instance cho cả ứng dụng, mọi request/thread cùng truy cập. Field thay đổi được ⇒ race condition và rò dữ liệu giữa người dùng. Trạng thái theo request đi qua tham số/biến cục bộ; trạng thái bền lưu ở CSDL/cache.

Q5

@Transactional hoạt động nhờ cơ chế nào? Nêu một trường hợp nó không hoạt động.

Xem đáp án
✓ Đáp án

Spring bọc bean trong proxy (tạo ở BeanPostProcessor); proxy mở/đóng transaction quanh lời gọi method. Không chạy khi self-invocation (gọi this.method() trong cùng lớp — không qua proxy), khi method không public, hoặc lớp final (CGLIB không kế thừa được).

Q6

Phụ thuộc vòng xử lý thế nào? Vì sao không nên bật allow-circular-references?

Xem đáp án
✓ Đáp án

Gỡ bằng thiết kế: tách lớp chung, dùng sự kiện, hoặc interface hẹp. Từ Boot 2.6 vòng bị cấm mặc định vì nó là dấu hiệu thiết kế sai; bật lại chỉ che lỗi (bean có thể được tiêm khi mới khởi tạo dở).

Tổng kết

Sau chương 2, bạn đã nắm:

  • DI: nhận phụ thuộc từ ngoài; IoC: container nắm quyền tạo/nối/huỷ. Ghép tay cũng là DI — Spring chỉ tự động hoá.
  • **ApplicationContext chứa các bean**; stereotype (@Component, @Service, @Repository) cho lớp của bạn, **@Bean** cho lớp thư viện.
  • Constructor injection + trường final là mặc định; field injection nên tránh.
  • Nhiều bean cùng kiểu: **@Primary, @Qualifier**, hoặc tiêm List/Map (Strategy).
  • Singleton là mặc định ⇒ không giữ trạng thái người dùng; prototype/request/session cho nhu cầu riêng.
  • Vòng đời: constructor → tiêm → @PostConstruct → dùng → @PreDestroy.
  • Phụ thuộc vòng là lỗi thiết kế; proxy là nền của @Transactional/@Cacheable — và self-invocation là bẫy.

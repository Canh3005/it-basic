Cấu hình & Profiles — một bản build, nhiều môi trường

Cùng một file JAR phải chạy được ở máy bạn (H2, log chi tiết), ở staging (PostgreSQL test) và ở production (PostgreSQL thật, log gọn, mật khẩu từ vault) — không build lại. Đó là nguyên tắc externalized configuration (yếu tố III của Twelve-Factor App). Spring Boot cung cấp một hệ thống cấu hình nhiều tầng, có thứ tự ưu tiên rõ ràng; hiểu nó là hiểu vì sao "trên máy tôi chạy được" lại có thể sai.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-2
🎯 Mục tiêu chương
  • Viết cấu hình bằng **application.properties và YAML**; biết khi nào chọn cái nào.
  • Thuộc thứ tự ưu tiên của các nguồn cấu hình (dòng lệnh > biến môi trường > file profile > file mặc định).
  • Dùng **@Value** và biết giới hạn của nó.
  • Dùng **@ConfigurationProperties** (có record, validation) cho cấu hình có cấu trúc — cách làm chuẩn.
  • Tách môi trường bằng profiles (dev, test, prod) và @Profile.
  • Quản lý bí mật (mật khẩu, API key) mà không commit vào Git.
  • Hiểu relaxed binding giữa my.app-name, MY_APP_NAME, myAppName.

1. application.properties và YAML

Đa số dự án thực tế chọn YAML. Chọn gì cũng được — nhưng đừng để cả hai cùng tồn tại trong một dự án: nếu cả hai có mặt, .properties thắng .yml, rất dễ gây nhầm.

2. Thứ tự ưu tiên — nguồn nào thắng?

Cùng một key có thể xuất hiện ở nhiều nơi. Boot gộp tất cả; nguồn ưu tiên cao hơn ghi đè nguồn thấp hơn. Rút gọn từ cao xuống thấp:

3. @Value — tiêm từng giá trị

MailService.java
@Service
public class MailService {

    private final String from;
    private final int timeoutMs;
    private final List<String> bcc;

    public MailService(
            @Value("${app.mail.from}") String from,                       // bắt buộc có, thiếu → lỗi khởi động
            @Value("${app.mail.timeout-ms:3000}") int timeoutMs,          // có mặc định sau dấu :
            @Value("${app.mail.bcc:}") List<String> bcc)        // mặc định rỗng → danh sách rỗng {
        this.from = from;
        this.timeoutMs = timeoutMs;
        this.bcc = bcc;
    }
}

@Value hợp cho một-hai giá trị lẻ. Nhược điểm khi dùng rộng:

  • Key là chuỗi rải rác trong code — đổi tên key thì không compiler nào báo lỗi.
  • Không có cấu trúc: 10 giá trị liên quan là 10 @Value.
  • Không validation, không IDE auto-complete, không tài liệu tự sinh.

Với nhóm cấu hình liên quan — hãy dùng @ConfigurationProperties.

4. @ConfigurationProperties — cách làm chuẩn

Gom một nhánh cấu hình vào một lớp có kiểu rõ ràng. Với Spring Boot 3 và Java 21, **record** là lựa chọn tự nhiên (bất biến, gọn):

application.yml
app:
  jwt:
    secret: ${JWT_SECRET}            # lấy từ biến môi trường
    expiry: 30m                      # Duration — Boot hiểu 30m, 2h, PT30M
    issuer: shop-api
  upload:
    max-size: 5MB                    # DataSize
    allowed-types:
      - image/png
      - image/jpeg
AppProperties.java
@ConfigurationProperties(prefix = "app")
@Validated                                          // bật kiểm tra ràng buộc
public record AppProperties(Jwt jwt, Upload upload) {

    public record Jwt(
            @NotBlank String secret,
            @DefaultValue("30m") Duration expiry,   // giá trị mặc định nếu không cấu hình
            @NotBlank String issuer) { }

    public record Upload(
            @DefaultValue("5MB") DataSize maxSize,
            @NotEmpty List<String> allowedTypes) { }
}
Đăng ký & dùng
@SpringBootApplication
@ConfigurationPropertiesScan                        // tự tìm mọi @ConfigurationProperties
public class ShopApplication { ... }

@Service
class TokenService {
    private final AppProperties props;
    TokenService(AppProperties props) { this.props = props; }   // tiêm như bean bình thường

    Instant hetHan() { return Instant.now().plus(props.jwt().expiry()); }
}
Lợi íchGiải thích
Kiểu mạnhDuration, DataSize, List<String>, enum, Path… tự chuyển từ chuỗi
Validation lúc khởi độngThiếu app.jwt.secret ⇒ fail fast ngay lúc boot, không phải lúc có người đăng nhập
Một nơi duy nhấtMọi key app.* nằm trong một lớp — dễ tìm, dễ đổi tên (IDE refactor)
Dễ testnew AppProperties(...) — không cần Spring

📌 Binding bằng constructor

Với record hoặc lớp có đúng một constructor có tham số, Boot 3 tự dùng constructor binding (không cần @ConstructorBinding). Lớp thường có setter vẫn dùng được (JavaBean binding). Ưu tiên record: không thể bị sửa sau khi khởi tạo.

5. Profiles — cấu hình theo môi trường

Profile là một nhãn (dev, test, prod…). Khi bật, Boot nạp thêm application-{profile}.yml (ghi đè file chung) và bật các bean @Profile("…").

src/main/resources/
├── application.yml            ← chung cho mọi môi trường
├── application-dev.yml        ← chỉ khi profile "dev"
├── application-test.yml       ← chỉ khi profile "test"
└── application-prod.yml       ← chỉ khi profile "prod"
application.yml
spring:
  application:
    name: shop-api
  profiles:
    default: dev                    # nếu không chỉ định, dùng dev
app:
  mail:
    from: no-reply@shop.example.com
application-dev.yml
spring:
  datasource:
    url: jdbc:h2:mem:shop;MODE=PostgreSQL
  h2:
    console:
      enabled: true
logging:
  level:
    vn.itbasic: DEBUG
    org.hibernate.SQL: DEBUG        # in câu SQL
application-prod.yml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USER}
    password: ${DB_PASSWORD}
logging:
  level:
    root: WARN
    vn.itbasic: INFO
management:
  endpoints:
    web:
      exposure:
        include: health,info

5.1. Bật profile

Bốn cách
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev     # Maven
java -jar app.jar --spring.profiles.active=prod              # dòng lệnh
SPRING_PROFILES_ACTIVE=prod java -jar app.jar                # biến môi trường — chuẩn trên server/Docker
# trong test:  @ActiveProfiles("test")

5.2. @Profile trên bean

ProfileBeans.java
public interface EmailSender { void gui(String den, String noiDung); }

@Service @Profile("prod")
class SmtpEmailSender implements EmailSender { /* gửi thật */ }

@Service @Profile("!prod")                          // mọi profile trừ prod
class LogEmailSender implements EmailSender {
    private static final Logger log = LoggerFactory.getLogger(LogEmailSender.class);
    public void gui(String den, String noiDung) { log.info("[GIẢ LẬP] gửi tới {}: {}", den, noiDung); }
}

Dev/test dùng bản giả không gửi email thật; prod dùng bản thật — cùng code, khác cấu hình. Biểu thức hợp lệ: "dev", "!prod", "dev | test", "cloud & eu".

5.3. Nhiều profile trong một file YAML

application.yml
app:
  mail:
    from: no-reply@shop.example.com
---
spring:
  config:
    activate:
      on-profile: dev
app:
  mail:
    from: dev@localhost
---
spring:
  config:
    activate:
      on-profile: prod
logging:
  level:
    root: WARN
⚠️ Đừng lạm dụng profile cho logic

Profile để đổi cấu hình và hạ tầng (DB, email giả/thật). Đừng viết if (profile == "prod") trong nghiệp vụ: nó khiến code chạy ở prod khác code bạn đã test. Nếu hành vi khác nhau, hãy biểu diễn nó bằng một property rõ nghĩa (ví dụ app.feature.new-checkout=true).

6. Bí mật — đừng bao giờ commit

Mật khẩu, API key, JWT secret không bao giờ nằm trong Git — kể cả repo riêng tư, kể cả "chỉ tạm thời". Lịch sử Git là vĩnh viễn; bí mật lộ một lần phải coi như đã mất và đổi ngay.

⚠️ Cả ${X:mặc-định} cũng có thể rò rỉ

Viết password: ${DB_PASSWORD:changeme} nghĩa là *thiếu biến môi trường thì dùng changeme* — ứng dụng khởi động "thành công" với mật khẩu yếu thay vì fail fast. Với bí mật: không đặt giá trị mặc định.

Ngoài ra: đừng log Environment/properties; endpoint /actuator/env che các key chứa password, secret, key, token nhưng đừng dựa vào đó — chỉ mở khi cần và sau xác thực.

7. Bức tranh lớn: Twelve-Factor

Hệ thống cấu hình của Boot hiện thực hoá yếu tố III — Config: cấu hình thay đổi giữa các môi trường phải ở ngoài code. Dấu hiệu bạn làm đúng:

  • Một artifact duy nhất (JAR/image) được promote từ dev → staging → prod; môi trường khác nhau chỉ ở biến môi trường/file cấu hình.
  • Có thể mở mã nguồn công khai ngay hôm nay mà không lộ bí mật nào.
  • Mọi cài đặt có thể đổi bằng biến môi trường — đúng thứ Docker Compose và Kubernetes cung cấp.

Bài tập

Bảng ưu tiên bằng thực nghiệm

Tạo property app.greeting ở bốn nơi với giá trị khác nhau: application.yml, application-dev.yml, biến môi trường, tham số dòng lệnh. Viết endpoint /greeting trả về @Value của nó.

  • Bật dần từng nguồn và ghi lại thứ tự nguồn nào thắng.
  • Đối chiếu với bảng ở mục 2. Có chỗ nào khác với dự đoán của bạn?
Gợi ý

Dự kiến: dòng lệnh > biến môi trường (APP_GREETING) > application-dev.yml > application.yml. Nhớ rằng profile dev chỉ được nạp khi bật (hoặc là default).

Chuyển @Value sang @ConfigurationProperties

Có sẵn năm @Value trong MailService (host, port, from, timeout, retries).

  • Gom thành record MailProperties với prefix app.mail.
  • Thêm validation: host không rỗng, port 1-65535, retries ≥ 0.
  • Xoá app.mail.host khỏi cấu hình ⇒ quan sát lỗi khởi động. Lỗi đó nói gì?
Gợi ý

@NotBlank, @Min(1) @Max(65535), @PositiveOrZero. Lỗi sẽ là BindValidationException / Binding to target … failed nêu rõ Property: app.mail.host, Reason: must not be blank — fail fast.

Ba profile, ba hành vi

Tạo interface Notifier với 3 bean: ConsoleNotifier (profile dev), FakeNotifier (profile test, ghi vào List để test kiểm tra), SlackNotifier (profile prod).

  • Chạy từng profile, kiểm tra log.
  • Không bật profile nào ⇒ điều gì xảy ra? Sửa bằng spring.profiles.default.
  • Thử @Profile("!prod") để gộp dev & test.
Gợi ý

Không profile nào ⇒ NoSuchBeanDefinitionException nếu không có bean nào khớp. spring.profiles.default: dev chỉ áp dụng khi chưa đặt spring.profiles.active.

Thợ săn bí mật

Cho file YAML bên dưới. Hãy chỉ ra ít nhất 4 vấn đề về quản lý bí mật và viết lại cho đúng.

application-prod.yml
spring:
  datasource:
    url: jdbc:postgresql://prod-db.internal:5432/shop
    username: admin
    password: P@ssw0rd123
app:
  jwt:
    secret: ${JWT_SECRET:my-super-secret}
management:
  endpoints:
    web:
      exposure:
        include: "*"
Gợi ý

(1) mật khẩu thật trong file; (2) username admin (nên có tài khoản ít quyền); (3) JWT_SECRET có default ⇒ thiếu env vẫn chạy với khoá yếu, công khai; (4) include: "*" lộ env, heapdump…; (5) nên @Validated bắt secret rỗng và độ dài tối thiểu. Viết lại: ${DB_PASSWORD} không default, include chỉ health,info.

Tự dựng Twelve-Factor

Build một JAR duy nhất. Không sửa file nào, chạy nó ba lần với ba cấu hình khác nhau (cổng, tên ứng dụng, profile) chỉ bằng biến môi trường.

  • Viết script run.sh nhận tên môi trường và export biến phù hợp.
  • Thêm một docker-compose.yml nhỏ có phần environment: cho cùng việc đó.
Gợi ý

Biến cần dùng: SERVER_PORT, SPRING_APPLICATION_NAME, SPRING_PROFILES_ACTIVE. Chú ý quy tắc relaxed binding cho biến môi trường: dấu . và - thành _, viết HOA.

Quiz

Q1

Thứ tự ưu tiên cấu hình trong Spring Boot (rút gọn) là gì và vì sao quan trọng?

Xem đáp án
✓ Đáp án

Cao → thấp: dòng lệnh > biến môi trường > application-{profile} > application.yml > mặc định. Quan trọng vì cho phép ops đổi cấu hình không build lại — một artifact chạy nhiều môi trường.

Q2

Khi nào chọn @Value, khi nào chọn @ConfigurationProperties?

Xem đáp án
✓ Đáp án

@Value cho một-hai giá trị lẻ. @ConfigurationProperties cho nhóm có cấu trúc: kiểu mạnh, validation fail-fast, một nơi duy nhất, IDE hỗ trợ, dễ test. Từ nhóm ≥ 3 giá trị liên quan, nên dùng @ConfigurationProperties.

Q3

Profile dùng để làm gì? Nêu một lạm dụng cần tránh.

Xem đáp án
✓ Đáp án

Đổi cấu hình/hạ tầng theo môi trường (DB, email giả/thật, log level) bằng application-{profile}.yml và @Profile. Tránh: if (isProd) trong nghiệp vụ — code ở prod khác code đã test. Hành vi khác nhau nên là một property tính năng rõ nghĩa.

Q4

Vì sao ${DB_PASSWORD:changeme} là ý tưởng tệ?

Xem đáp án
✓ Đáp án

Thiếu biến môi trường thì ứng dụng vẫn khởi động với mật khẩu yếu, công khai thay vì fail fast. Với bí mật: không có default ⇒ thiếu là lỗi khởi động ngay.

Q5

Relaxed binding là gì? APP_JWT_EXPIRYMINUTES bind vào đâu?

Xem đáp án
✓ Đáp án

Boot chấp nhận nhiều cách viết cho cùng một key. Biến môi trường APP_JWT_EXPIRYMINUTES (HOA, _ thay ./-, bỏ dấu gạch) bind vào app.jwt.expiry-minutes ⇒ thuộc tính expiryMinutes của lớp cấu hình. File chuẩn dùng kebab-case.

Q6

@ConfigurationProperties với record có lợi gì so với lớp có setter?

Xem đáp án
✓ Đáp án

Bất biến (không ai đổi cấu hình lúc chạy), gọn, constructor binding tự động ở Boot 3, dễ khởi tạo trong test (new AppProperties(...)), cho phép @DefaultValue ngay trên thành phần.

Tổng kết

Sau chương 3, bạn đã nắm:

  • Cấu hình nằm ở **application.yml/.properties**; chọn một định dạng và giữ nhất quán.
  • Dòng lệnh > biến môi trường > file profile > file chung — quy tắc ưu tiên cho phép một JAR chạy mọi nơi.
  • **@Value cho giá trị lẻ; @ConfigurationProperties + record + @Validated** cho cấu hình có cấu trúc, fail fast.
  • Profile đổi cấu hình/hạ tầng, không đổi logic; bật bằng SPRING_PROFILES_ACTIVE.
  • Bí mật qua biến môi trường/secret manager; không commit, không default.
  • Relaxed binding: kebab-case trong file, UPPER_SNAKE trong biến môi trường, camelCase trong Java.

Kết nối

  • Chương 1 — application.properties là nơi đặt server.port, logging.*, management.*.
  • Chương 2 — @Value/@ConfigurationProperties tiêm cấu hình vào bean; @Profile điều khiển bean nào được tạo.
  • Chương 6 — spring.datasource.*, spring.jpa.* cho CSDL.
  • Chương 10 — app.jwt.* (secret, thời hạn) là ví dụ điển hình của @ConfigurationProperties.
  • Chương 11 — @ActiveProfiles("test"), @TestPropertySource, Testcontainers qua @DynamicPropertySource.
  • Chương 14 & DevOps chương 9 — Docker/K8s truyền cấu hình & bí mật bằng biến môi trường.

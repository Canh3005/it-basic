Chương 05 · Validation & Lỗi

Validation & xử lý lỗi — API không bao giờ "nổ" thô

Mọi dữ liệu từ ngoài vào đều không đáng tin. Và mọi API rồi cũng có lỗi — câu hỏi là client nhận được gì: một stack trace dài 200 dòng, hay một JSON gọn nói rõ trường nào sai, vì sao? Chương này dựng hai hàng rào: validation ở cửa vào (Bean Validation), và xử lý lỗi tập trung ở cửa ra (@RestControllerAdvice + ProblemDetail chuẩn RFC 9457).

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-4
🎯 Mục tiêu chương
  • Dùng Bean Validation (@Valid, @NotBlank, @Size, @Email…) trên DTO dạng record.
  • Validate cả tham số đơn (@RequestParam, @PathVariable), DTO lồng nhau và danh sách.
  • Viết ràng buộc tuỳ biến (mức trường và mức lớp).
  • Thiết kế hệ thống exception nghiệp vụ nhỏ, rõ nghĩa.
  • Xử lý lỗi tập trung bằng **@RestControllerAdvice và ProblemDetail**.
  • Ánh xạ exception → mã HTTP đúng; không rò rỉ chi tiết nội bộ.
  • Phân biệt lỗi validation (cú pháp/format) và lỗi nghiệp vụ (luật kinh doanh).

1. Validate ở đâu, và tin ai?

Một request đi qua ba lớp kiểm tra khác nhau, mỗi lớp trả lời một câu hỏi khác:

LớpCâu hỏiVí dụCông cụ
Cú pháp / định dạngDữ liệu có đúng dạng không?Email hợp lệ, tên không rỗng, tuổi ≥ 0Bean Validation trên DTO
Nghiệp vụCó được phép theo luật không?Email đã tồn tại, hết hàng, vượt hạn mứcService + exception nghiệp vụ
Toàn vẹn dữ liệuCSDL có chấp nhận không?UNIQUE, NOT NULL, khoá ngoạiRàng buộc CSDL (lưới an toàn cuối)
Validate ở biên (boundary), lặp lại ở tầng cần thiết. Bean Validation ở controller chặn rác sớm và cho message tốt; nhưng không bao giờ thay thế kiểm tra nghiệp vụ trong service hay ràng buộc trong CSDL — client có thể là script, không phải form của bạn. Validation phía frontend chỉ phục vụ trải nghiệm, không phải bảo mật.

2. Bean Validation với @Valid

Từ Boot 2.3, spring-boot-starter-web không còn kéo theo thư viện validation. Thêm riêng:

pom.xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
CreateUserRequest.java
public record CreateUserRequest(

        @NotBlank(message = "Tên không được để trống")
        @Size(max = 100, message = "Tên tối đa 100 ký tự")
        String name,

        @NotBlank @Email
        String email,

        @NotBlank
        @Size(min = 8, max = 72, message = "Mật khẩu 8-72 ký tự")   // 72 = giới hạn của BCrypt (chương 9)
        String password,

        @NotNull @Past
        LocalDate birthDate,

        @Valid @NotNull                                            // @Valid: kiểm tra CẢ bên trong Address
        Address address,

        @Size(max = 5)
        List<@NotBlank @Size(max = 30) String> tags) { }          // kiểm tra từng phần tử trong list

public record Address(
        @NotBlank String street,
        @NotBlank String city,
        @Pattern(regexp = "\\d{5,6}", message = "Mã bưu chính 5-6 chữ số") String postalCode) { }
Controller
@PostMapping("/api/users")
public ResponseEntity<UserResponse> create(@Valid @RequestBody CreateUserRequest req) {   // @Valid kích hoạt kiểm tra
    return ResponseEntity.status(HttpStatus.CREATED).body(service.create(req));
}

Nếu có ràng buộc bị vi phạm, Spring không gọi method của bạn mà ném MethodArgumentNotValidException ⇒ mặc định trả 400 (nội dung thô — mục 6 sẽ chuẩn hoá).

2.2. Validate tham số đơn (query, path)

ProductController.java
@RestController
@RequestMapping("/api/products")
@Validated                                              // cần cho Spring < 6.1; từ 6.1 có sẵn method validation
class ProductController {

    @GetMapping("/{id}")
    Product get(@PathVariable @Positive long id) { ... }

    @GetMapping
    List<Product> search(@RequestParam(defaultValue = "0")  @PositiveOrZero int page,
                         @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size) { ... }
}

Từ Spring 6.1 / Boot 3.2, ràng buộc trên tham số controller được kiểm tra sẵn và ném HandlerMethodValidationException (trước đó là ConstraintViolationException và phải có @Validated ở lớp). Dù phiên bản nào, bạn nên bắt cả hai trong handler tập trung.

2.3. Cùng DTO, luật khác nhau? Dùng DTO riêng

Bean Validation có validation groups (@NotNull(groups = OnUpdate.class)), nhưng nó khiến DTO rối. Cách sạch hơn: hai record riêng — CreateUserRequest (mọi trường bắt buộc) và UpdateUserRequest (phần lớn tuỳ chọn). Mỗi use case một hợp đồng rõ ràng.

3. Ràng buộc tuỳ biến

3.1. Mức trường: @StrongPassword

StrongPassword.java
@Documented
@Constraint(validatedBy = StrongPasswordValidator.class)
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.RECORD_COMPONENT})
@Retention(RetentionPolicy.RUNTIME)
public @interface StrongPassword {
    String message() default "Mật khẩu phải có chữ hoa, chữ thường và chữ số";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class StrongPasswordValidator implements ConstraintValidator<StrongPassword, String> {

    @Override
    public boolean isValid(String value, ConstraintValidatorContext ctx) {
        if (value == null) return true;                  // để @NotBlank lo chuyện null — mỗi ràng buộc một việc
        return value.chars().anyMatch(Character::isUpperCase)
            && value.chars().anyMatch(Character::isLowerCase)
            && value.chars().anyMatch(Character::isDigit);
    }
}

// Dùng:  @NotBlank @Size(min = 8, max = 72) @StrongPassword String password

3.2. Mức lớp: ràng buộc chéo trường

DateRange.java
@Constraint(validatedBy = DateRangeValidator.class)
@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)
public @interface ValidDateRange {
    String message() default "Ngày kết thúc phải sau ngày bắt đầu";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public interface HasDateRange { LocalDate from(); LocalDate to(); }

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, HasDateRange> {
    @Override
    public boolean isValid(HasDateRange v, ConstraintValidatorContext ctx) {
        return v == null || v.from() == null || v.to() == null || !v.to().isBefore(v.from());
    }
}

@ValidDateRange
public record ReportRequest(@NotNull LocalDate from, @NotNull LocalDate to) implements HasDateRange { }
💡 Validator có thể là bean Spring

Lớp ConstraintValidator được Spring tạo nên có thể tiêm bean (ví dụ UserRepository để kiểm tra email chưa tồn tại). Nhưng cẩn thận: kiểm tra "đã tồn tại" bằng validator vẫn có race condition — hai request cùng lúc cùng qua. Ràng buộc UNIQUE của CSDL là chốt chặn thật (bắt DataIntegrityViolationException, mục 7).

4. Thiết kế exception nghiệp vụ

Thay vì ResponseStatusException rải khắp nơi, định nghĩa một nhóm exception nhỏ, đặt tên theo ý nghĩa nghiệp vụ (không theo mã HTTP):

Exceptions.java
public abstract class AppException extends RuntimeException {
    private final String code;                         // mã lỗi ổn định cho client xử lý: "USER_NOT_FOUND"
    protected AppException(String code, String message) { super(message); this.code = code; }
    public String code() { return code; }
}

public class NotFoundException extends AppException {
    public NotFoundException(String resource, Object id) {
        super(resource.toUpperCase() + "_NOT_FOUND", resource + " không tồn tại: " + id);
    }
}

public class ConflictException extends AppException {          // trùng dữ liệu, sai trạng thái
    public ConflictException(String code, String message) { super(code, message); }
}

public class BusinessRuleException extends AppException {      // vi phạm luật kinh doanh
    public BusinessRuleException(String code, String message) { super(code, message); }
}
UserService.java
@Service
class UserService {
    User getOrThrow(long id) {
        return repo.findById(id).orElseThrow(() -> new NotFoundException("user", id));
    }

    void rutTien(long userId, long soTien) {
        if (soTien > soDu(userId))
            throw new BusinessRuleException("INSUFFICIENT_BALANCE", "Số dư không đủ");
    }
}
*Dùng exception *unchecked (RuntimeException) cho lỗi nghiệp vụ.* Spring rollback transaction mặc định chỉ với unchecked (chương 7). Và tầng service không nên biết "404/409" là gì — nó nói *chuyện gì sai, tầng web quyết định mã nào.

5. @RestControllerAdvice — một nơi bắt mọi lỗi

@RestControllerAdvice là bean toàn cục; các method @ExceptionHandler bên trong bắt exception ném ra từ bất kỳ controller nào:

GlobalExceptionHandler.java
@RestControllerAdvice
class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(NotFoundException.class)
    ResponseEntity<ProblemDetail> notFound(NotFoundException ex) {
        return problem(HttpStatus.NOT_FOUND, ex);
    }

    @ExceptionHandler(ConflictException.class)
    ResponseEntity<ProblemDetail> conflict(ConflictException ex) {
        return problem(HttpStatus.CONFLICT, ex);
    }

    @ExceptionHandler(BusinessRuleException.class)
    ResponseEntity<ProblemDetail> business(BusinessRuleException ex) {
        return problem(HttpStatus.UNPROCESSABLE_ENTITY, ex);
    }

    private ResponseEntity<ProblemDetail> problem(HttpStatus status, AppException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, ex.getMessage());
        pd.setTitle(status.getReasonPhrase());
        pd.setProperty("code", ex.code());                  // trường mở rộng cho client
        return ResponseEntity.status(status).body(pd);
    }

    /** Lưới an toàn cuối: bất cứ thứ gì chưa được xử lý. */
    @ExceptionHandler(Exception.class)
    ResponseEntity<ProblemDetail> unexpected(Exception ex) {
        String errorId = UUID.randomUUID().toString();
        log.error("Lỗi không lường trước [errorId={}]", errorId, ex);            // chi tiết vào LOG
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR,
                "Đã có lỗi xảy ra. Vui lòng liên hệ hỗ trợ kèm mã lỗi.");           // client: thông điệp chung
        pd.setProperty("errorId", errorId);
        return ResponseEntity.internalServerError().body(pd);
    }
}

5.1. ProblemDetail — định dạng lỗi chuẩn

RFC 9457 (trước đó là RFC 7807) định nghĩa media type application/problem+json với các trường chuẩn. Spring 6 hỗ trợ sẵn qua lớp ProblemDetail:

Phản hồi
HTTP/1.1 404
Content-Type: application/problem+json

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "detail": "user không tồn tại: 42",
  "instance": "/api/users/42",
  "code": "USER_NOT_FOUND"
}
TrườngÝ nghĩa
typeURI mô tả loại lỗi (mặc định about:blank)
titleTóm tắt ngắn, không đổi theo từng lần
statusMã HTTP
detailGiải thích cụ thể cho lần lỗi này
instanceĐường dẫn request gây lỗi
(tuỳ ý) code, errors…Trường mở rộng của bạn qua pd.setProperty(...)
📌 Bật định dạng chuẩn cho lỗi có sẵn của Spring

spring.mvc.problemdetails.enabled=true làm các exception nội bộ của MVC (404 route, 405, 415, 400…) cũng trả application/problem+json thay vì định dạng riêng của Boot — để mọi lỗi trong API cùng một khuôn.

6. Chuẩn hoá lỗi validation

Mặc định MethodArgumentNotValidException cho client rất ít thông tin dễ dùng. Ta mở rộng ResponseEntityExceptionHandler (đã có sẵn handler cho ~20 exception của MVC) và ghi đè xử lý validation:

ValidationHandler.java
@RestControllerAdvice
class ApiExceptionHandler extends ResponseEntityExceptionHandler {

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers, HttpStatusCode status, WebRequest request) {

        Map<String, List<String>> errors = ex.getBindingResult().getFieldErrors().stream()
                .collect(Collectors.groupingBy(
                        FieldError::getField,                                   // "address.city", "tags[2]"
                        TreeMap::new,
                        Collectors.mapping(fe -> Objects.requireNonNullElse(fe.getDefaultMessage(), "không hợp lệ"),
                                           Collectors.toList())));

        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Dữ liệu gửi lên không hợp lệ");
        pd.setTitle("Validation failed");
        pd.setProperty("code", "VALIDATION_FAILED");
        pd.setProperty("errors", errors);
        return handleExceptionInternal(ex, pd, headers, HttpStatus.BAD_REQUEST, request);
    }

    // Tham số đơn (@RequestParam/@PathVariable) vi phạm ràng buộc — Spring 6.1+
    @Override
    protected ResponseEntity<Object> handleHandlerMethodValidationException(
            HandlerMethodValidationException ex, HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Tham số không hợp lệ");
        pd.setProperty("code", "VALIDATION_FAILED");
        return handleExceptionInternal(ex, pd, headers, HttpStatus.BAD_REQUEST, request);
    }

    // JSON sai cú pháp hoặc sai kiểu: {"birthDate": "hôm qua"}
    @Override
    protected ResponseEntity<Object> handleHttpMessageNotReadable(
            HttpMessageNotReadableException ex, HttpHeaders headers, HttpStatusCode status, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Body không phải JSON hợp lệ");
        pd.setProperty("code", "MALFORMED_JSON");
        return handleExceptionInternal(ex, pd, headers, HttpStatus.BAD_REQUEST, request);
    }
}
Phản hồi khi gửi dữ liệu sai
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "detail": "Dữ liệu gửi lên không hợp lệ",
  "instance": "/api/users",
  "code": "VALIDATION_FAILED",
  "errors": {
    "email":        ["must be a well-formed email address"],
    "name":         ["Tên không được để trống"],
    "address.city": ["must not be blank"],
    "password":     ["Mật khẩu 8-72 ký tự", "Mật khẩu phải có chữ hoa, chữ thường và chữ số"]
  }
}

Frontend có thể gắn trực tiếp errors["email"] vào đúng ô nhập — đó là mục đích của việc có cấu trúc thay vì một chuỗi lỗi.

Đa ngôn ngữ cho message

Thay vì viết cứng tiếng Việt, đặt message = "{user.name.blank}" và khai báo trong ValidationMessages.properties / ValidationMessages_vi.properties; Hibernate Validator chọn theo Accept-Language. Với dự án một thị trường, message cứng là đủ.

@ExceptionHandler(DataIntegrityViolationException.class)
ResponseEntity<ProblemDetail> integrity(DataIntegrityViolationException ex) {
    log.warn("Vi phạm toàn vẹn dữ liệu", ex);                       // chi tiết SQL ở log, KHÔNG ra client
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
            "Dữ liệu bị trùng hoặc vi phạm ràng buộc.");
    pd.setProperty("code", "DATA_CONFLICT");
    return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
}

8. Không rò rỉ thông tin nội bộ

🔒 Thông báo lỗi là bề mặt tấn công

Stack trace, tên bảng/cột, câu SQL, đường dẫn file, phiên bản thư viện… đều giúp kẻ tấn công. Chi tiết vào log, thông điệp chung ra client — kèm errorId để đội hỗ trợ tra log.

application.yml
server:
  error:
    include-message: never          # mặc định đã là never từ Boot 2.3
    include-stacktrace: never
    include-binding-errors: never   # lỗi mặc định của Boot không kèm chi tiết (ta dùng handler riêng)
  • Đừng return ResponseEntity.status(500).body(ex.getMessage()) — message của exception bất kỳ có thể chứa SQL hay đường dẫn.
  • Đừng phân biệt "email không tồn tại" với "mật khẩu sai" ở màn đăng nhập (lộ danh sách tài khoản) — trả cùng một thông điệp.
  • Hãy log lỗi 5xx ở mức ERROR kèm stack trace + errorId + requestId (chương 4); lỗi 4xx ở mức WARN/INFO (đó là lỗi của client, đừng làm ngập alert).

Bài tập

Đăng ký người dùng

Viết POST /api/register nhận RegisterRequest(username, email, password, age, interests):

  • username: 3-20 ký tự, chỉ chữ/số/_; email hợp lệ; password 8-72 + @StrongPassword tự viết.
  • age ≥ 13; interests tối đa 5 phần tử, mỗi phần tử không rỗng.
  • Gửi dữ liệu sai nhiều chỗ cùng lúc — response phải liệt kê tất cả lỗi, không chỉ lỗi đầu tiên.
Gợi ý

@Pattern(regexp = "^[A-Za-z0-9_]{3,20}$") (Java string cần \\w...). Bean Validation luôn gom mọi vi phạm vào một MethodArgumentNotValidException — nên errors là map nhiều khoá.

Ràng buộc chéo trường

Tạo @PasswordsMatch mức lớp cho ChangePasswordRequest(oldPassword, newPassword, confirmPassword): newPassword phải bằng confirmPassword và khác oldPassword.

  • Lỗi nên gắn vào trường confirmPassword, không phải toàn đối tượng.
  • Gợi ý: trong isValid, dùng ctx.disableDefaultConstraintViolation() và ctx.buildConstraintViolationWithTemplate(...).addPropertyNode("confirmPassword").addConstraintViolation().
Gợi ý

Không gắn addPropertyNode, lỗi nằm ở khoá rỗng/ChangePasswordRequest và frontend không biết tô đỏ ô nào. Nhớ trả false sau khi build violation tuỳ biến.

Cây exception và handler

Xây AppException → NotFoundException, ConflictException, BusinessRuleException và GlobalExceptionHandler như mục 4-5.

  • Thêm API POST /api/transfer ném BusinessRuleException("INSUFFICIENT_BALANCE").
  • Viết test (MockMvc, chương 11 sẽ học kỹ — thử trước bằng curl) kiểm tra status=422 và code.
  • Cố tình ném NullPointerException — client nhận gì? Log có gì?
Gợi ý

NPE đi vào @ExceptionHandler(Exception.class): client thấy 500 + errorId; log có stack trace đầy đủ cùng errorId. Đó là hợp đồng lỗi 5xx đúng.

Race condition của "email đã tồn tại"

Cài đặt đăng ký với kiểm tra repo.existsByEmail(email) rồi save. Dùng 2 thread (hoặc curl song song) gửi cùng email.

  • Quan sát: có thể cả hai cùng qua existsByEmail?
  • Thêm ràng buộc UNIQUE(email) ở CSDL và bắt DataIntegrityViolationException → 409.
  • Kết luận: validator/exists-check chỉ là tối ưu trải nghiệm, ràng buộc CSDL mới là đảm bảo.
Gợi ý

(Làm sau chương 6 nếu chưa có JPA — có thể mô phỏng bằng ConcurrentHashMap + Thread.sleep giữa check và put.) Mẫu đúng: thử ghi trước, bắt lỗi trùng thay vì hỏi rồi mới ghi.

Kiểm tra rò rỉ

Gửi các request lỗi sau và đọc kỹ response: JSON thiếu dấu }; GET /api/users/abc; POST với Content-Type: text/plain; một endpoint cố tình ném new RuntimeException("jdbc:postgresql://prod-db:5432 password=...").

  • Có response nào để lộ nội bộ không?
  • Sửa để tất cả cùng định dạng application/problem+json, không lộ gì.
Gợi ý

Bật spring.mvc.problemdetails.enabled=true, extend ResponseEntityExceptionHandler, và đảm bảo @ExceptionHandler(Exception.class) trả thông điệp chung. Đừng bao giờ đưa ex.getMessage() của exception không phải của bạn ra ngoài.

Quiz

Q1

@NotNull, @NotEmpty, @NotBlank khác nhau thế nào?

Xem đáp án
✓ Đáp án

@NotNull: không null (chuỗi rỗng vẫn qua). @NotEmpty: không null và độ dài > 0 (chuỗi " " vẫn qua). @NotBlank: không null, không rỗng, không toàn khoảng trắng — chỉ dùng cho String. Với input người dùng, @NotBlank là lựa chọn thường đúng.

Q2

Vì sao @Size(min = 3) không bắt buộc trường có giá trị?

Xem đáp án
✓ Đáp án

Phần lớn ràng buộc Bean Validation coi null là hợp lệ (để mỗi ràng buộc làm một việc). Muốn bắt buộc phải thêm @NotNull/@NotBlank.

Q3

@Valid đặt ở đâu và vì sao cần ở trường lồng nhau?

Xem đáp án
✓ Đáp án

Đặt trước @RequestBody để kích hoạt kiểm tra DTO; và đặt trên trường là đối tượng/danh sách lồng nhau để Hibernate Validator đi sâu vào. Thiếu @Valid ở trường ⇒ ràng buộc bên trong đối tượng đó bị bỏ qua.

Q4

Vì sao nên có exception nghiệp vụ riêng thay vì ném ResponseStatusException khắp nơi?

Xem đáp án
✓ Đáp án

Tầng service chỉ nên diễn đạt chuyện gì sai (NotFoundException, BusinessRuleException) chứ không biết HTTP. Tầng web (@RestControllerAdvice) quyết định mã và định dạng — một nơi duy nhất, nhất quán, dễ đổi. Service cũng tái dùng được ngoài ngữ cảnh web (job, message listener).

Q5

ProblemDetail / RFC 9457 mang lại gì?

Xem đáp án
✓ Đáp án

Một khuôn lỗi chuẩn (type, title, status, detail, instance + trường mở rộng) với media type application/problem+json. Client/ thư viện nhiều ngôn ngữ đã hiểu sẵn; Spring 6 hỗ trợ trực tiếp bằng lớp ProblemDetail.

Q6

Vì sao kiểm tra "email chưa tồn tại" ở validator vẫn chưa đủ?

Xem đáp án
✓ Đáp án

Có race condition: hai request cùng lúc cùng thấy "chưa tồn tại" rồi cùng ghi. Chỉ **ràng buộc UNIQUE của CSDL** mới đảm bảo; code nên bắt DataIntegrityViolationException và dịch thành 409. Kiểm tra trước chỉ để cho thông báo sớm và đẹp.

Tổng kết

Sau chương 5, bạn đã nắm:

  • Ba lớp kiểm tra: cú pháp (Bean Validation), nghiệp vụ (service), toàn vẹn (CSDL). Frontend validate không phải bảo mật.
  • **@Valid @RequestBody** + ràng buộc trên record; @NotBlank cho chuỗi bắt buộc; @Valid ở trường lồng nhau.
  • Ràng buộc tuỳ biến (@Constraint + ConstraintValidator) ở mức trường và mức lớp.
  • Exception nghiệp vụ unchecked, có code; service không biết HTTP.
  • **@RestControllerAdvice + ProblemDetail** cho một khuôn lỗi duy nhất; lỗi validation trả errors theo từng trường.
  • Không rò rỉ: chi tiết vào log kèm errorId, client nhận thông điệp chung; bắt DataIntegrityViolationException → 409.

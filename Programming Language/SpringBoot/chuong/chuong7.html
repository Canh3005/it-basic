Chương 07 · JPA nâng cao

JPA nâng cao & Transaction — nơi 80% bug dữ liệu sinh ra

CRUD đơn bảng thì JPA hiền. Rắc rối bắt đầu khi có quan hệ (đơn hàng → dòng hàng → sản phẩm) và transaction (chuyển tiền: trừ bên này, cộng bên kia, hoặc cả hai hoặc không gì cả). Đây là chương "khó" nhất của phần dữ liệu: hầu hết sự cố production liên quan JPA — truy vấn chậm bất thường, LazyInitializationException, dữ liệu ghi đè lẫn nhau — đều bắt nguồn từ việc không hiểu persistence context và ranh giới transaction.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-6
🎯 Mục tiêu chương
  • Hiểu persistence context, vòng đời entity và dirty checking (vì sao đổi field mà không gọi save vẫn được lưu).
  • Ánh xạ quan hệ @ManyToOne, @OneToMany, @ManyToMany; hiểu owning side, cascade, orphanRemoval.
  • Giải thích và sửa **LazyInitializationException**.
  • Phát hiện và sửa bài toán N+1 query (join fetch, @EntityGraph, batch fetch, DTO projection).
  • Dùng **@Transactional** đúng: vị trí, readOnly, propagation, rollback rule, các bẫy.
  • Chống lost update bằng khoá lạc quan @Version (và biết khoá bi quan).
  • Quản lý schema bằng Flyway migration.

1. Persistence context — bộ nhớ làm việc của JPA

Khi bạn tải một entity, Hibernate không chỉ trả về object — nó ghi nhớ object đó trong một "vùng làm việc" gọi là persistence context (còn gọi first-level cache, gắn với EntityManager/Session, và trong Spring thường gắn với một transaction). Mọi thứ sau đây đều hệ quả từ đó.

Transient
new Product(…) — JPA chưa biết gì
persist / save
Trở thành managed
Managed
Nằm trong context; mọi thay đổi được theo dõi
Commit / flush
Hibernate so sánh trạng thái → sinh UPDATE
Detached
Context đóng (hết transaction) — object vẫn còn nhưng không được theo dõi
remove
Đánh dấu xoá → DELETE lúc flush
Chỉ entity ở trạng thái managed mới được tự động lưu thay đổi.

1.1. Dirty checking — đổi field là đủ

ProductService.java
@Transactional
public void doiGia(long id, BigDecimal giaMoi) {
    Product p = repo.findById(id).orElseThrow();   // SELECT — p trở thành MANAGED
    p.changePrice(giaMoi);                          // chỉ đổi field trong bộ nhớ
    // KHÔNG gọi repo.save(p)!
}                                                   // commit → Hibernate thấy p "bẩn" → UPDATE products SET price=? WHERE id=?

Đây là điều gây ngạc nhiên nhất với người mới: **không có save() vẫn lưu**. Ngược lại, quên @Transactional thì entity không được theo dõi và thay đổi mất tăm. Hệ quả hữu ích: cũng đừng gọi save() thừa trên entity đã managed — vô hại nhưng gây hiểu nhầm.

1.2. Bộ nhớ đệm cấp 1

Trong cùng một transaction
@Transactional
void demo() {
    Product a = repo.findById(1L).get();     // SELECT
    Product b = repo.findById(1L).get();     // KHÔNG có SELECT thứ hai — lấy từ context
    System.out.println(a == b);              // true: cùng một instance
}

Trong một persistence context, mỗi dòng DB chỉ có một object duy nhất. Tiện (nhất quán trong transaction) nhưng cũng có bẫy: câu @Modifying UPDATE hàng loạt bỏ qua context ⇒ entity trong bộ nhớ lỗi thời — vì vậy ta dùng clearAutomatically = true ở chương 6.

2. Quan hệ giữa các entity

Mô hình: Customer 1—N Order 1—N OrderItem N—1 Product.

Order.java
@Entity
@Table(name = "orders")                                    // "order" là từ khoá SQL → đặt tên bảng khác
public class Order {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)   // nhiều đơn → một khách; LUÔN đặt LAZY
    @JoinColumn(name = "customer_id")                      // cột khoá ngoại nằm ở bảng orders
    private Customer customer;

    @OneToMany(mappedBy = "order",                         // mappedBy = phía KHÔNG giữ khoá ngoại
               cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    @Enumerated(EnumType.STRING)
    private OrderStatus status = OrderStatus.NEW;

    @Version
    private long version;                                  // khoá lạc quan (mục 5)

    protected Order() { }
    public Order(Customer customer) { this.customer = customer; }

    // Đồng bộ CẢ HAI chiều của quan hệ trong một method
    public void addItem(Product product, int quantity) {
        items.add(new OrderItem(this, product, quantity, product.getPrice()));
    }
    public List<OrderItem> getItems() { return Collections.unmodifiableList(items); }
}

@Entity
public class OrderItem {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false) @JoinColumn(name = "order_id")
    private Order order;                                   // ← đây là OWNING SIDE (giữ cột order_id)

    @ManyToOne(fetch = FetchType.LAZY, optional = false) @JoinColumn(name = "product_id")
    private Product product;

    private int quantity;
    @Column(precision = 12, scale = 2) private BigDecimal unitPrice;   // chụp giá TẠI THỜI ĐIỂM đặt

    protected OrderItem() { }
    OrderItem(Order o, Product p, int q, BigDecimal price) { order = o; product = p; quantity = q; unitPrice = price; }
}

⚠️ Mặc định @ManyToOne là EAGER — hãy đổi thành LAZY

@ManyToOne và @OneToOne mặc định FetchType.EAGER: tải Order là tự động tải luôn Customer (kèm các quan hệ EAGER của Customer…) dù bạn không cần. @OneToMany/@ManyToMany mặc định LAZY. Quy tắc: **đặt mọi quan hệ LAZY** và chủ động nạp (join fetch/@EntityGraph) ở nơi cần.

2.1. @ManyToMany — ít khi đủ dùng

Quan hệ N-N (sinh viên ↔ môn học) có thể dùng @ManyToMany @JoinTable. Nhưng bảng nối hầu như luôn cần thêm cột (ngày đăng ký, điểm) ⇒ tạo entity trung gian (Enrollment) với hai @ManyToOne — chính là mẫu OrderItem ở trên. Chỉ dùng @ManyToMany thuần cho trường hợp thật sự không có dữ liệu gì thêm (nhãn/tag).

equals/hashCode cho entity

Hibernate đặt entity vào Set, so sánh chúng… nên equals/hashCode quan trọng. Cạm bẫy: dùng id (tự sinh) thì **id là null trước khi lưu**, làm hashCode đổi giữa chừng.

  • Có business key bất biến (ISBN, email, mã vạch)? Dùng nó.
  • Không có? equals theo id (so sánh khi cả hai khác null), hashCode hằng số (getClass().hashCode()).
  • Không dùng @Data/@EqualsAndHashCode của Lombok trên entity — nó đưa cả quan hệ vào hashCode, dễ vòng lặp vô tận và kích hoạt lazy loading.

3. Lazy loading và LazyInitializationException

Quan hệ LAZY không tải ngay: Hibernate đặt một proxy thay chỗ, chỉ chạy SELECT khi bạn chạm vào dữ liệu thật. Vì cần persistence context (kết nối DB), nếu bạn chạm vào sau khi transaction đã đóng:

Lỗi kinh điển
@Service
class OrderService {
    Order get(long id) { return orderRepo.findById(id).orElseThrow(); }    // transaction kết thúc ở đây
}

@RestController
class OrderController {
    @GetMapping("/orders/{id}")
    OrderDto get(@PathVariable long id) {
        Order o = service.get(id);
        return new OrderDto(o.getId(), o.getItems().size());               // 💥 LazyInitializationException:
    }                                                                      //    could not initialize proxy - no Session
}

3.1. Vì sao open-in-view: false

Mặc định Boot bật Open Session In View (OSIV): giữ persistence context mở suốt request — kể cả lúc controller serialize JSON — nên lỗi trên không xảy ra. Nghe tiện nhưng đánh đổi:

  • Lazy loading âm thầm chạy ở tầng web (lúc serialize) ⇒ các câu SELECT ẩn, N+1 khó thấy.
  • Kết nối DB bị giữ lâu hơn cần thiết (suốt request, gồm cả ghi response) ⇒ cạn pool.
  • Che lấp lỗi thiết kế: service trả entity nửa vời cho controller.
**Tắt OSIV (spring.jpa.open-in-view=false) và nạp đủ dữ liệu cần thiết bên trong tầng service, rồi trả DTO** ra ngoài. Lỗi LazyInitializationException khi đó là chỉ dẫn hữu ích: bạn chưa quyết định rõ cần nạp gì.
Cách đúng
@Service
class OrderService {

    @Transactional(readOnly = true)
    OrderDto get(long id) {                                               // map sang DTO TRONG transaction
        Order o = orderRepo.findWithItemsById(id).orElseThrow(() -> new NotFoundException("order", id));
        return OrderDto.from(o);
    }
}

4. Bài toán N+1

Lấy 20 đơn hàng rồi in số dòng hàng của mỗi đơn:

Mã trông vô hại
@Transactional(readOnly = true)
void in() {
    List<Order> orders = orderRepo.findAll();                  // 1 câu: SELECT * FROM orders
    for (Order o : orders) {
        System.out.println(o.getItems().size());               // mỗi đơn 1 câu: SELECT * FROM order_item WHERE order_id = ?
    }
}                                                              // → 1 + 20 = 21 câu SQL; với 10.000 đơn là 10.001 câu
Log SQL
select o.id, o.status, o.customer_id from orders o
select i.id, i.quantity from order_item i where i.order_id = 1
select i.id, i.quantity from order_item i where i.order_id = 2
select i.id, i.quantity from order_item i where i.order_id = 3
-- ... lặp lại N lần
N+1 = 1 câu lấy danh sách cha + N câu lấy con của từng cha. Mỗi câu rất nhanh nhưng tổng làm chậm đều đặn và khó nhận ra trong dev (dữ liệu ít). Đây là nguyên nhân số một khiến API Spring+JPA "chậm không rõ lý do".

4.2. Bốn cách sửa

OrderRepository.java
public interface OrderRepository extends JpaRepository<Order, Long> {

    // (1) JOIN FETCH — nạp con trong CÙNG câu SQL (Hibernate 6 tự loại bản ghi trùng)
    @Query("select o from Order o join fetch o.items where o.status = :status")
    List<Order> findWithItems(@Param("status") OrderStatus status);

    // (2) @EntityGraph — khai báo "nạp những gì" mà không viết JPQL; lồng nhiều cấp
    @EntityGraph(attributePaths = {"items", "items.product", "customer"})
    Optional<Order> findWithItemsById(Long id);

    // (3) DTO projection — chỉ lấy cột cần, không tải entity
    @Query("""
           select new vn.itbasic.shop.OrderRow(o.id, c.name, count(i), sum(i.unitPrice * i.quantity))
           from Order o join o.customer c left join o.items i
           group by o.id, c.name
           """)
    List<OrderRow> findRows();
}

⚠️ Phân trang + join fetch collection

Page<Order> kèm join fetch o.items khiến Hibernate cảnh báo "firstResult/maxResults specified with collection fetch; applying in memory" (HHH90003004): nó tải toàn bộ bảng vào RAM rồi cắt trang. Giải pháp: phân trang trên bảng cha trước (chỉ lấy id), rồi nạp con theo danh sách id — hoặc dùng default_batch_fetch_size. Và fetch hai List cùng lúc ném MultipleBagFetchException (dùng Set hoặc tách query).

5. @Transactional — ranh giới của sự toàn vẹn

Transaction gom nhiều thao tác thành một đơn vị nguyên tử: hoặc tất cả thành công (commit), hoặc không gì cả (rollback) — nền tảng ACID (xem Database chương 6). Ví dụ kinh điển:

ChuyenTienService.java
@Service
class ChuyenTienService {

    private final TaiKhoanRepository repo;
    ChuyenTienService(TaiKhoanRepository repo) { this.repo = repo; }

    @Transactional                                       // toàn bộ method = 1 transaction
    public void chuyen(long tuId, long denId, BigDecimal soTien) {
        TaiKhoan tu  = repo.findById(tuId).orElseThrow(() -> new NotFoundException("account", tuId));
        TaiKhoan den = repo.findById(denId).orElseThrow(() -> new NotFoundException("account", denId));

        tu.rut(soTien);                                  // ném BusinessRuleException nếu không đủ số dư
        den.nap(soTien);
    }   // thành công → COMMIT cả hai UPDATE. Có exception unchecked → ROLLBACK cả hai: không ai mất tiền oan
}

5.1. Đặt ở đâu?

**@Transactional đặt ở tầng service, ở method thể hiện một use case trọn vẹn.** Không đặt ở controller (kéo transaction ra tầng web, giữ kết nối lâu), không đặt ở từng repository method (mỗi lệnh một transaction ⇒ mất tính nguyên tử của cả use case). Các method đọc thuần: @Transactional(readOnly = true).

5.2. Quy tắc rollback — cạm bẫy số một

⚠️ Checked exception KHÔNG làm rollback

Mặc định Spring chỉ rollback khi gặp unchecked exception. IOException, SQLException, exception checked của bạn ⇒ transaction vẫn commit những gì đã ghi trước đó. Hoặc dùng exception unchecked cho lỗi nghiệp vụ (đúng như chương 5), hoặc khai báo rõ @Transactional(rollbackFor = Exception.class).

Hai bẫy khác
@Transactional
public void xuLy() {
    try {
        repo.save(a);
        riskyCall();                 // ném RuntimeException
    } catch (RuntimeException e) {
        log.warn("bỏ qua", e);       // ❌ NUỐT exception ⇒ Spring không biết ⇒ COMMIT dữ liệu nửa vời
    }                                // (và transaction có thể đã bị đánh dấu rollback-only ⇒ UnexpectedRollbackException)
}

@Transactional
public void guiMailRoiLuu() {
    repo.save(order);
    mailApi.send(order);             // ❌ gọi mạng CHẬM trong transaction ⇒ giữ kết nối DB suốt thời gian chờ ⇒ cạn pool
}

5.4. Việc phụ chỉ làm sau khi commit

Gửi email xác nhận đơn khi transaction chưa commit là sai: nếu commit thất bại, khách nhận email về đơn không tồn tại. Dùng sự kiện gắn với pha commit:

TransactionalEventListener
@Transactional
public Order datHang(...) {
    Order o = orderRepo.save(...);
    events.publishEvent(new OrderPlacedEvent(o.getId()));      // chưa gửi gì cả
    return o;
}

@Component
class MailListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)    // chỉ chạy khi commit THÀNH CÔNG
    @Async                                                                  // và không chặn request (chương 12)
    void onOrderPlaced(OrderPlacedEvent e) { mail.guiXacNhan(e.orderId()); }
}

6. Hai người sửa cùng một dòng — khoá lạc quan

Hai nhân viên cùng mở sản phẩm X (số lượng 10). A bán 3 và lưu (7). B — vẫn thấy 10 — bán 2 và lưu (8). Kết quả 8 thay vì 5: lost update, bản ghi của A bị ghi đè lặng lẽ.

Khoá lạc quan với @Version
@Entity
public class Product {
    // ...
    @Version
    private long version;           // Hibernate tự tăng mỗi lần UPDATE
}
// Mỗi UPDATE do Hibernate sinh ra có thêm điều kiện:
//   UPDATE products SET quantity=?, version=2 WHERE id=? AND version=1
// Nếu 0 dòng bị ảnh hưởng (ai đó đã đổi version) → ném ObjectOptimisticLockingFailureException
Dịch thành 409 (chương 5)
@ExceptionHandler(ObjectOptimisticLockingFailureException.class)
ResponseEntity<ProblemDetail> staleData(ObjectOptimisticLockingFailureException ex) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT,
            "Dữ liệu đã bị người khác thay đổi. Hãy tải lại rồi thử lại.");
    pd.setProperty("code", "STALE_DATA");
    return ResponseEntity.status(HttpStatus.CONFLICT).body(pd);
}

public interface TaiKhoanRepository extends JpaRepository<TaiKhoan, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select t from TaiKhoan t where t.id = :id")
    Optional<TaiKhoan> findByIdForUpdate(@Param("id") long id);      // SELECT … FOR UPDATE
}
// Chuyển tiền giữa hai tài khoản: LUÔN khoá theo thứ tự id tăng dần để tránh deadlock (A→B và B→A cùng lúc)

Với khoá lạc quan, thông thường client sẽ gửi kèm version (hoặc dùng ETag/If-Match) để phát hiện cả xung đột giữa các request HTTP khác nhau, không chỉ trong một transaction.

💡 Thay đổi phá vỡ: expand → migrate → contract

Đổi tên cột name → full_name không nên làm một bước (bản code cũ đang chạy vẫn đọc name). Làm ba bản phát hành: (1) thêm full_name, code ghi cả hai; (2) chuyển dữ liệu & code đọc full_name; (3) bỏ name. Đây là cách triển khai zero-downtime.

Bài tập

Quan sát dirty checking

Viết doiTen(long id, String ten) đổi tên sản phẩm không gọi save().

  • Thử có @Transactional và không có — chuyện gì xảy ra với DB? Giải thích bằng persistence context.
  • Bật log SQL: có mấy câu UPDATE? Gọi changePrice với cùng giá trị cũ — có UPDATE không?
  • Thêm @Transactional(readOnly = true) rồi đổi field — kết quả?
Gợi ý

Không có transaction: entity detached, không UPDATE. Cùng giá trị: Hibernate so sánh snapshot ⇒ không có thay đổi ⇒ không UPDATE. readOnly = true: Hibernate bỏ dirty checking ⇒ thay đổi không được lưu (và một số cấu hình còn chặn ghi).

Dựng, đo, sửa N+1

Tạo 50 Order, mỗi đơn 5 OrderItem. Viết GET /api/orders trả danh sách OrderDto(id, customerName, itemCount).

  • Phiên bản ngây thơ: đếm số câu SQL.
  • Sửa bằng bốn cách ở mục 4.2 và đếm lại từng cách.
  • Cách nào cho DTO danh sách? Vì sao?
Gợi ý

Ngây thơ: 1 + 50 (items) + có thể thêm 50 (customer nếu EAGER). @EntityGraph/join fetch: 1. Batch size 50: 2-3. DTO projection (count(i) + group by): 1 và ít dữ liệu nhất — hợp danh sách chỉ đọc.

Rollback rule

Viết service luuRoiBaoLoi ghi một bản ghi rồi ném: (a) RuntimeException, (b) Exception checked tự định nghĩa.

  • Bản ghi có còn trong DB không ở mỗi trường hợp?
  • Sửa (b) để rollback bằng 2 cách.
  • Thử try/catch nuốt exception trong (a): kết quả? Vì sao?
Gợi ý

(a) rollback; (b) commit (!). Sửa: @Transactional(rollbackFor = Exception.class) hoặc đổi sang unchecked. Nuốt exception ⇒ Spring không thấy ⇒ commit (nếu exception không đến từ ranh giới proxy), hoặc UnexpectedRollbackException nếu một transaction lồng đã đánh dấu rollback-only.

Lost update

Viết test dùng hai thread cùng đọc sản phẩm có quantity=10, một thread trừ 3, một thread trừ 2, cùng lưu (dùng CountDownLatch để chúng đọc trước rồi mới ghi).

  • Không có @Version: số cuối là bao nhiêu?
  • Thêm @Version: một thread nhận exception gì? Viết handler → 409.
  • Viết logic thử lại tối đa 3 lần cho thread thua cuộc.
Gợi ý

Không @Version: 7 hoặc 8 (mất một cập nhật). Có @Version: ObjectOptimisticLockingFailureException. Thử lại phải đọc lại entity (dữ liệu mới) trong transaction mới — không dùng lại object cũ.

Migration đầu tiên

Thêm Flyway; viết V1 tạo bảng products, V2 thêm cột sku (not null, unique, điền dữ liệu cho dòng cũ).

  • Chuyển ddl-auto sang validate; khởi động trên DB trống.
  • Sửa nội dung V1 rồi khởi động lại — lỗi gì? Vì sao đó là điều tốt?
  • Viết kế hoạch 3 bản phát hành để đổi tên cột name → full_name không downtime.
Gợi ý

Lỗi Validate failed: Migration checksum mismatch for migration version 1. Tốt vì đảm bảo mọi môi trường có lịch sử schema giống hệt nhau. Kế hoạch 3 bước: expand (thêm cột, ghi cả hai) → migrate (backfill, đọc cột mới) → contract (bỏ cột cũ).

Quiz

Q1

Persistence context là gì? Vì sao đổi field của entity managed không cần save()?

Xem đáp án
✓ Đáp án

Là vùng bộ nhớ (gắn với một transaction/EntityManager) giữ các entity đã tải cùng snapshot trạng thái ban đầu. Lúc commit/flush, Hibernate so sánh trạng thái hiện tại với snapshot (dirty checking) và tự sinh UPDATE cho entity thay đổi. Vì vậy cần entity ở trạng thái managed (trong transaction).

Q2

Owning side và mappedBy nghĩa là gì?

Xem đáp án
✓ Đáp án

Trong quan hệ hai chiều, owning side là phía giữ cột khoá ngoại (có @JoinColumn, thường là @ManyToOne) — chỉ phía này quyết định giá trị FK khi ghi. Phía còn lại (@OneToMany(mappedBy="order")) chỉ là bản đồ ngược. Thiếu mappedBy ⇒ Hibernate tạo bảng nối thừa.

Q3

LazyInitializationException do đâu? Cách sửa đúng?

Xem đáp án
✓ Đáp án

Chạm vào quan hệ LAZY sau khi persistence context đã đóng (hết transaction). Sửa đúng: nạp dữ liệu cần thiết trong service (@EntityGraph, join fetch, hoặc DTO projection) và trả DTO; tắt OSIV. Không sửa bằng cách đổi sang EAGER toàn cục — đó là kéo thêm vấn đề hiệu năng.

Q4

N+1 query là gì? Nêu các cách khắc phục và chọn cách cho API trả danh sách.

Xem đáp án
✓ Đáp án

1 câu lấy N cha + N câu lấy con. Cách sửa: join fetch/@EntityGraph (1 câu, nạp cả hai), default_batch_fetch_size (gom IN (…)), DTO projection (1 câu, ít dữ liệu nhất). Cho danh sách chỉ đọc: DTO projection thường tốt nhất; cẩn thận phân trang + join fetch collection (phân trang trong bộ nhớ).

Q5

Khi nào @Transactional không rollback? Nêu ít nhất ba tình huống.

Xem đáp án
✓ Đáp án
  • Exception là checked và không khai rollbackFor.
  • Exception bị catch và nuốt trong method.
  • Self-invocation hoặc method không public — proxy không chặn nên không có transaction.
  • Đặt trên lớp/final mà proxy không tạo được.
Q6

Khoá lạc quan hoạt động ra sao và khi nào dùng khoá bi quan?

Xem đáp án
✓ Đáp án

@Version thêm cột phiên bản; UPDATE … WHERE id=? AND version=? — nếu không dòng nào được cập nhật, nghĩa là ai đó đã sửa trước ⇒ ném ObjectOptimisticLockingFailureException (dịch thành 409). Không giữ khoá nên mở rộng tốt. Dùng khoá bi quan (SELECT … FOR UPDATE) khi xung đột thường xuyên (số dư, tồn kho nóng) và chấp nhận chi phí chờ/deadlock.

Tổng kết

Sau chương 7, bạn đã nắm:

  • Persistence context theo dõi entity managed; dirty checking tự UPDATE lúc commit — cần @Transactional.
  • Quan hệ: owning side giữ FK, mappedBy ở phía kia; cascade/orphanRemoval chỉ cho cha-con; **mọi quan hệ đặt LAZY**; N-N có dữ liệu ⇒ entity trung gian.
  • Tắt OSIV, nạp đủ dữ liệu trong service, trả DTO ⇒ không còn LazyInitializationException bất ngờ.
  • N+1: đếm câu SQL trong log; sửa bằng DTO projection / @EntityGraph / default_batch_fetch_size.
  • **@Transactional** ở service, theo use case; readOnly cho đọc; chỉ rollback với unchecked (hoặc rollbackFor); không nuốt exception; không gọi mạng chậm trong transaction.
  • **@Version** chống lost update → 409; khoá bi quan cho tranh chấp cao, khoá theo thứ tự cố định.
  • Flyway: schema có phiên bản, không sửa migration đã chạy, ddl-auto: validate; thay đổi phá vỡ theo expand-migrate-contract.

Chương 08 · Kiến trúc & API

Kiến trúc tầng, DTO & OpenAPI — code lớn mà không rối

Sáu chương đầu cho bạn đủ công cụ để viết một API chạy được. Chương này trả lời câu hỏi khác: làm sao để nó vẫn dễ sửa khi có 50 endpoint và 5 người cùng làm? Đó là chuyện ranh giới: mỗi lớp chịu trách nhiệm gì, dữ liệu đi qua ranh giới dưới dạng nào (DTO), và hợp đồng giữa backend với frontend được ghi ở đâu (OpenAPI).

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-7
🎯 Mục tiêu chương
  • Phân chia trách nhiệm controller / service / repository và hướng phụ thuộc đúng.
  • Chọn cách tổ chức package: theo tầng hay theo tính năng (khuyến nghị).
  • Thiết kế DTO (request/response) bằng record và ánh xạ bằng MapStruct.
  • Quyết định logic nằm ở entity hay service; ranh giới transaction.
  • Áp dụng quy ước thiết kế API: tên tài nguyên, lọc/sắp xếp/phân trang, versioning, idempotency.
  • Tự sinh tài liệu OpenAPI/Swagger UI bằng springdoc và biết dùng nó như hợp đồng với frontend.
  • Bảo vệ kiến trúc bằng test với ArchUnit.

⚠️ Ba mùi code kinh điển

Fat controller: 80 dòng if/else nghiệp vụ trong controller — không tái dùng, không test được nếu không dựng web. God service: một UserService 2.000 dòng làm mọi thứ liên quan đến user — tách theo use case/khả năng. Anemic pass-through: service chỉ gọi repo.findById() rồi trả lại — chấp nhận được lúc đầu, nhưng đừng bịa lớp "cho đủ tầng" nếu nó không thêm giá trị.

Mặc định: package-by-feature. Nó biến ranh giới giữa các tính năng thành ranh giới của package — và khi đó bạn có thể dùng package-private để cấm tính năng này chọc vào ruột tính năng kia. (Nếu cần, mỗi feature vẫn có thể chia thêm web/, domain/, persistence/ bên trong.)

3. DTO — hợp đồng tách khỏi mô hình dữ liệu

DTO (Data Transfer Object) là đối tượng chỉ để mang dữ liệu qua ranh giới. Ba lý do không trả entity ra ngoài:

  • Bảo mật/mass assignment: client không nên ghi được id, role, version, createdAt (chương 4); và không nên đọc được passwordHash, internalNote.
  • Ổn định hợp đồng: đổi tên cột hoặc tách bảng không được làm vỡ API; DTO là lớp đệm.
  • Tránh lỗi JPA: serialize entity kích hoạt lazy loading, vòng lặp Order ↔ OrderItem, LazyInitializationException (chương 7).
DTO bằng record — mỗi use case một hợp đồng
public record CreateOrderRequest(
        @NotNull Long customerId,
        @NotEmpty @Valid List<Line> lines) {

    public record Line(@NotNull Long productId, @Positive int quantity) { }
}

public record OrderResponse(
        Long id,
        String status,
        BigDecimal total,
        Instant createdAt,
        List<LineResponse> lines) {

    public record LineResponse(Long productId, String productName, int quantity, BigDecimal unitPrice) { }
}
💡 Đặt tên: theo vai trò, không theo bảng

CreateOrderRequest, UpdateOrderRequest, OrderResponse, OrderSummary (cho danh sách) — tốt hơn OrderDto dùng cho mọi thứ. Một DTO "vạn năng" dần chứa trường tuỳ chọn tuỳ lúc, mất khả năng validate chặt.

3.1. MapStruct — ánh xạ sinh lúc biên dịch

Viết tay OrderResponse.from(order) ổn khi ít. Với nhiều DTO lồng nhau, MapStruct sinh mã ánh xạ lúc biên dịch — nhanh như viết tay, không reflection, lỗi thiếu trường được báo ngay.

OrderMapper.java
@Mapper(componentModel = "spring")                      // sinh bean Spring → tiêm được
public interface OrderMapper {

    @Mapping(target = "total", expression = "java(order.total())")        // trường tính toán
    @Mapping(target = "status", source = "status")                         // enum → String tự động
    OrderResponse toResponse(Order order);

    @Mapping(target = "productName", source = "product.name")              // đi sâu vào quan hệ
    OrderResponse.LineResponse toLine(OrderItem item);

    List<OrderResponse> toResponses(List<Order> orders);

    // Cập nhật entity có sẵn từ DTO — bỏ qua null (PATCH-style)
    @BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
    void update(UpdateProductRequest req, @MappingTarget Product product);
}

// Dùng:
@Service
class OrderService {
    private final OrderRepository repo; private final OrderMapper mapper;
    OrderService(OrderRepository repo, OrderMapper mapper) { this.repo = repo; this.mapper = mapper; }

    @Transactional(readOnly = true)
    public OrderResponse get(long id) {
        return mapper.toResponse(repo.findWithItemsById(id).orElseThrow(() -> new NotFoundException("order", id)));
    }
}
⚠️ Mapper chỉ nên chạm vào dữ liệu đã được nạp

toResponse(order) đi qua order.getItems() — nếu quan hệ chưa nạp và ta ngoài transaction ⇒ LazyInitializationException. Luôn gọi mapper bên trong transaction với dữ liệu đã join fetch/@EntityGraph (chương 7). Với danh sách chỉ đọc, cân nhắc projection thẳng ra DTO thay vì entity → mapper.

4. Thiết kế service

4.1. Method service = một use case

OrderService.java
@Service
public class OrderService {

    private final OrderRepository orders;
    private final ProductRepository products;
    private final CustomerRepository customers;
    private final OrderMapper mapper;
    // constructor …

    @Transactional                                            // ranh giới nguyên tử của use case
    public OrderResponse place(CreateOrderRequest req) {
        Customer customer = customers.findById(req.customerId())
                .orElseThrow(() -> new NotFoundException("customer", req.customerId()));

        Order order = new Order(customer);
        for (CreateOrderRequest.Line line : req.lines()) {
            Product p = products.findById(line.productId())
                    .orElseThrow(() -> new NotFoundException("product", line.productId()));
            if (p.getStatus() != ProductStatus.ACTIVE)
                throw new BusinessRuleException("PRODUCT_UNAVAILABLE", "Sản phẩm ngừng bán: " + p.getName());
            order.addItem(p, line.quantity());                 // logic thêm dòng nằm trong entity
        }
        return mapper.toResponse(orders.save(order));
    }
}

4.2. Logic ở entity hay ở service?

Anemic (entity chỉ có getter/setter)Rich (entity có hành vi)
Quy tắc nằm ởServiceEntity cho quy tắc của riêng nó; service cho điều phối nhiều đối tượng
Ví dụorder.setStatus(PAID) ở bất cứ đâuorder.pay() kiểm tra trạng thái hợp lệ, một nơi duy nhất
Rủi roQuy tắc bị lặp / bỏ sót; trạng thái không hợp lệ dễ xảy raEntity phình nếu nhồi cả điều phối
Hành vi nằm trong entity
// Entity bảo vệ bất biến của chính nó
public void pay() {
    if (status != OrderStatus.NEW) throw new BusinessRuleException("ORDER_NOT_PAYABLE", "Đơn không ở trạng thái chờ thanh toán");
    if (items.isEmpty())           throw new BusinessRuleException("ORDER_EMPTY", "Đơn không có sản phẩm");
    this.status = OrderStatus.PAID;
}

public BigDecimal total() {
    return items.stream().map(OrderItem::lineTotal).reduce(BigDecimal.ZERO, BigDecimal::add);
}
Quy tắc nào chỉ liên quan đến một aggregate (Order + OrderItem) → để trong entity; quy tắc cần nhiều aggregate/hệ thống ngoài (kiểm tra tồn kho ở Product, gọi cổng thanh toán) → service điều phối. Đây là ý tưởng của DDD-lite (xem OOP chương 8).

Đừng trả Optional/entity từ service ra controller

Service nên **ném NotFoundException** thay vì trả Optional.empty() để controller tự quyết 404 — như vậy mọi controller xử lý "không thấy" nhất quán, và @RestControllerAdvice lo phần còn lại. Cũng như đã nói: trả DTO, không trả entity.

5.2. Idempotency — thử lại không gây hại

Mạng chập chờn: client gửi POST /payments, không nhận được phản hồi, thử lại — khách bị trừ tiền hai lần? GET/PUT/DELETE vốn idempotent; POST thì không. Giải pháp phổ biến (Stripe, các cổng thanh toán): client gửi header **Idempotency-Key (UUID); server lưu kết quả theo khoá và trả lại cùng kết quả** nếu thấy khoá lần nữa.

IdempotencyFilter (ý tưởng)
@PostMapping("/api/payments")
public ResponseEntity<PaymentResponse> pay(@RequestHeader("Idempotency-Key") String key,
                                           @Valid @RequestBody PaymentRequest req) {
    return idempotency.execute(key, () -> paymentService.pay(req))      // lần 2 cùng key → trả kết quả đã lưu
                      .map(r -> ResponseEntity.status(HttpStatus.CREATED).body(r))
                      .orElseGet(() -> ResponseEntity.status(HttpStatus.CONFLICT).build());   // đang xử lý bởi request khác
}
// Lưu (key, hash(body), response, status) trong bảng/Redis với TTL 24h; ràng buộc UNIQUE(key) chống hai request đồng thời.

6. OpenAPI & Swagger UI — tài liệu sống

OpenAPI là chuẩn mô tả REST API bằng JSON/YAML (đường dẫn, tham số, schema request/response, mã lỗi, xác thực). Swagger UI đọc file đó và dựng trang thử API trong trình duyệt. Với thư viện springdoc-openapi, tài liệu được sinh từ chính code của bạn — không lệch pha.

pom.xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>2.8.4</version>          <!-- không thuộc BOM của Boot — kiểm tra bản mới nhất tương thích Boot 3.x -->
</dependency>
Địa chỉ sau khi chạy
http://localhost:8080/swagger-ui.html     # giao diện thử API
http://localhost:8080/v3/api-docs          # spec OpenAPI dạng JSON
http://localhost:8080/v3/api-docs.yaml     # dạng YAML

Cấu hình chung (tên, version, xác thực JWT)
@Configuration
class OpenApiConfig {
    @Bean
    OpenAPI shopApi() {
        return new OpenAPI()
                .info(new Info().title("Shop API").version("v1").description("API quản lý cửa hàng"))
                .components(new Components().addSecuritySchemes("bearerAuth",
                        new SecurityScheme().type(SecurityScheme.Type.HTTP).scheme("bearer").bearerFormat("JWT")))
                .addSecurityItem(new SecurityRequirement().addList("bearerAuth"));     // nút "Authorize" trong Swagger UI
    }
}

Bean Validation (@NotNull, @Size, @Min…) tự được đưa vào schema (required, maxLength, minimum). Đó là một lý do nữa để đặt ràng buộc trên DTO.

💡 Dùng OpenAPI làm hợp đồng với frontend

Từ file /v3/api-docs, frontend tự sinh client có kiểu (TypeScript) bằng openapi-generator/openapi-typescript/orval — đổi API ở backend ⇒ build frontend báo lỗi biên dịch thay vì nổ lúc chạy. Lưu spec vào Git, so sánh phiên bản (oasdiff) trong CI để phát hiện breaking change trước khi merge.

🔒 Production

Swagger UI mở công khai lộ toàn bộ bề mặt API. Tắt hoặc đặt sau xác thực ở production: springdoc.swagger-ui.enabled=false và springdoc.api-docs.enabled=false trong application-prod.yml.

7. Giữ kiến trúc không "mục" theo thời gian

Quy ước kiến trúc nếu chỉ nằm trong tài liệu sẽ bị phá trong tuần thứ ba. ArchUnit biến chúng thành test — vi phạm thì CI đỏ:

pom.xml & ArchitectureTest.java
// <dependency><groupId>com.tngtech.archunit</groupId><artifactId>archunit-junit5</artifactId>
//   <version>1.3.0</version><scope>test</scope></dependency>

@AnalyzeClasses(packages = "vn.itbasic.shop", importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureTest {

    @ArchTest
    static final ArchRule controllers_khong_goi_repository =
            noClasses().that().haveSimpleNameEndingWith("Controller")
                       .should().dependOnClassesThat().haveSimpleNameEndingWith("Repository");

    @ArchTest
    static final ArchRule service_khong_biet_http =
            noClasses().that().haveSimpleNameEndingWith("Service")
                       .should().dependOnClassesThat().resideInAnyPackage("org.springframework.http..", "jakarta.servlet..");

    @ArchTest
    static final ArchRule khong_tra_entity_ra_controller =
            noMethods().that().areDeclaredInClassesThat().haveSimpleNameEndingWith("Controller")
                       .and().arePublic()
                       .should().haveRawReturnType(annotatedWith(Entity.class));

    @ArchTest
    static final ArchRule khong_vong_giua_cac_feature =
            slices().matching("vn.itbasic.shop.(*)..").should().beFreeOfCycles();
}

Bài tập

Tách fat controller

Cho OrderController.create dài 60 dòng chứa kiểm tra tồn kho, tính tổng, trừ kho, lưu, gửi email. Hãy refactor:

  • Controller còn ≤ 8 dòng.
  • Nghiệp vụ vào OrderService.place có @Transactional.
  • Tính tổng tiền vào Order.total(); email gửi sau commit (chương 7 mục 5.4).
Gợi ý

Controller chỉ: @Valid body → service.place(req) → 201 + Location. Kiểm tra ArchUnit rule "controller không phụ thuộc repository" để chắc chắn không ai kéo logic ngược lại.

DTO & MapStruct

Với entity Customer(id, name, email, passwordHash, role, createdAt, orders):

  • Tạo CustomerResponse (không có passwordHash, orders), CreateCustomerRequest, UpdateCustomerRequest.
  • Viết CustomerMapper (MapStruct) gồm cả method update(@MappingTarget) bỏ qua null.
  • Thử cố ý thêm trường vào CustomerResponse không có nguồn — MapStruct báo gì lúc biên dịch?
Gợi ý

MapStruct cảnh báo Unmapped target property: "x"; đặt unmappedTargetPolicy = ReportingPolicy.ERROR trong @Mapper để biến cảnh báo thành lỗi biên dịch. Mật khẩu băm không bao giờ có trong DTO trả ra.

Package-by-feature

Chuyển dự án từ package-by-layer sang package-by-feature (order, product, customer).

  • Đặt OrderRepository và entity Order là package-private; chỉ OrderService, OrderResponse… public.
  • Một service khác (ReportService) cần số đơn: bạn cho nó phụ thuộc gì? (Gợi ý: thêm method public trên OrderService, không mở repository.)
  • Chạy slices().…beFreeOfCycles() — có vòng phụ thuộc giữa các feature không?
Gợi ý

Che repository buộc mọi truy cập đi qua service ⇒ quy tắc nghiệp vụ không bị vòng qua. Nếu order ↔ customer phụ thuộc lẫn nhau, đó là dấu hiệu cần tách khái niệm thứ ba hoặc dùng sự kiện.

Tài liệu OpenAPI

Thêm springdoc. Mô tả đủ POST /api/v1/orders: mô tả, ví dụ, mọi mã lỗi (400/404/422) với ProblemDetail.

  • Dùng nút Authorize nhập JWT mẫu.
  • Tải v3/api-docs.yaml, sinh client TypeScript bằng openapi-typescript.
  • Đổi tên một trường trong DTO — client sinh lại có lỗi biên dịch không?
Gợi ý

Đó chính là giá trị của contract: thay đổi phá vỡ hiện ra ở build frontend, không phải lúc người dùng bấm nút. Thêm bước CI oasdiff breaking giữa spec cũ và mới.

Idempotency-Key

Cài POST /api/v1/payments idempotent bằng bảng idempotency_keys(key UNIQUE, request_hash, response_json, status).

  • Gửi cùng key hai lần tuần tự ⇒ cùng kết quả, chỉ một lần trừ tiền.
  • Gửi hai request đồng thời cùng key ⇒ một cái thắng, một cái nhận 409 (hoặc chờ).
  • Cùng key nhưng body khác ⇒ trả 422.
Gợi ý

Chốt chặn thật là UNIQUE(key): INSERT trước (trạng thái PROCESSING), request thua cuộc bắt DataIntegrityViolationException. So sánh request_hash để phát hiện tái dùng key sai.

Quiz

Q1

Vì sao không trả thẳng entity JPA ra response?

Xem đáp án
✓ Đáp án
  • Lộ trường nhạy cảm/nội bộ; mass assignment khi nhận vào.
  • Hợp đồng API bị buộc vào schema DB — đổi bảng là vỡ API.
  • Serialize kích hoạt lazy loading → LazyInitializationException, N+1, vòng lặp quan hệ hai chiều.
Q2

Package-by-feature hơn package-by-layer ở điểm nào?

Xem đáp án
✓ Đáp án

Kết dính cao (mọi thứ của một tính năng ở một chỗ), cho phép dùng **package-private** để che repository/entity, tách microservice dễ hơn, và tìm code nhanh. Package-by-layer rải một tính năng khắp 4-5 package và buộc mọi thứ phải public.

Q3

Controller, service, repository mỗi tầng chịu trách nhiệm gì? Điều gì tầng service không được biết?

Xem đáp án
✓ Đáp án

Controller: HTTP (đọc request, validate, mã trạng thái). Service: nghiệp vụ + ranh giới transaction. Repository: truy cập dữ liệu. Service không được biết HTTP (ResponseEntity, mã trạng thái, HttpServletRequest) — để tái dùng ngoài web và test không cần dựng web.

Q4

MapStruct khác ánh xạ bằng reflection (ModelMapper) thế nào?

Xem đáp án
✓ Đáp án

MapStruct sinh mã Java thông thường lúc biên dịch (annotation processor): nhanh như viết tay, không reflection, và thiếu trường được báo ngay lúc build. Reflection-based đoán lúc chạy: chậm hơn và lỗi chỉ hiện khi chạy.

Q5

Idempotency-Key giải quyết vấn đề gì?

Xem đáp án
✓ Đáp án

POST không idempotent: client mất kết nối rồi thử lại có thể tạo giao dịch hai lần. Client gửi một Idempotency-Key duy nhất cho mỗi ý định; server lưu kết quả theo khoá và trả lại đúng kết quả đó khi gặp lại — thử lại an toàn.

Q6

Lợi ích của việc sinh OpenAPI từ code và dùng nó như hợp đồng?

Xem đáp án
✓ Đáp án

Tài liệu không lệch so với code; Swagger UI cho phép thử API; frontend/đối tác sinh client có kiểu — thay đổi phá vỡ thành lỗi biên dịch thay vì lỗi lúc chạy; so sánh spec trong CI phát hiện breaking change sớm.

Tổng kết

Sau chương 8, bạn đã nắm:

  • Layered: Controller → Service → Repository; controller mỏng, nghiệp vụ ở service, service không biết HTTP.
  • Package-by-feature + package-private che ruột từng tính năng.
  • **DTO record theo vai trò (request/response/summary); MapStruct** ánh xạ lúc biên dịch, gọi trong transaction.
  • Quy tắc của một aggregate → entity; điều phối nhiều đối tượng → service; service ném exception thay vì trả Optional.
  • Quy ước API: danh từ số nhiều, lọc/sắp xếp/phân trang thống nhất, ISO-8601, version /v1, tương thích ngược, Idempotency-Key.
  • springdoc sinh OpenAPI + Swagger UI (tắt ở prod); dùng spec làm hợp đồng và sinh client.
  • ArchUnit biến quy ước kiến trúc thành test.

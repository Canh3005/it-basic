Chương 09 · Spring Security

Spring Security — xác thực, phân quyền và những thứ bảo vệ API

Thêm spring-boot-starter-security vào pom.xml — lập tức mọi endpoint đều đòi đăng nhập, và một mật khẩu ngẫu nhiên in ra log. Spring Security "an toàn theo mặc định" nhưng cũng là module khó hiểu nhất nếu chỉ copy-paste cấu hình. Chương này mổ xẻ nó từ kiến trúc (một chuỗi Filter) đến thực hành (người dùng trong CSDL, BCrypt, role, phân quyền theo method, CSRF/CORS), để chương 10 gắn JWT lên trên mà không còn là phép màu.

Bài tập: 5 Quiz: 6 Prerequisites: Chương 1-8
🎯 Mục tiêu chương
  • Phân biệt xác thực (authentication) và phân quyền (authorization); nhớ 401 vs 403.
  • Vẽ được Security Filter Chain và vị trí của nó so với DispatcherServlet.
  • Cấu hình **SecurityFilterChain** bằng lambda DSL của Spring Security 6.
  • Lưu người dùng trong CSDL với **UserDetailsService và mã hoá mật khẩu bằng BCrypt**.
  • Phân biệt role và authority (tiền tố ROLE_), dùng method security (@PreAuthorize).
  • Hiểu khi nào tắt CSRF; cấu hình CORS đúng chỗ.
  • Trả JSON 401/403 thống nhất và tránh các lỗi OWASP phổ biến (IDOR, lộ thông tin).

Nhớ chắc: 401 = chưa biết bạn là ai (thiếu/sai/hết hạn thông tin xác thực). 403 = biết bạn là ai rồi, nhưng bạn không được phép. Trả 403 cho người chưa đăng nhập hay 401 cho người thiếu quyền đều làm client xử lý sai (ví dụ: tự đẩy người dùng sang trang đăng nhập khi thật ra họ đã đăng nhập).

4. SecurityFilterChain — cấu hình hiện đại

Từ Spring Security 6 (Boot 3): **WebSecurityConfigurerAdapter đã bị xoá. Cấu hình bằng bean SecurityFilterChain** và lambda DSL:

SecurityConfig.java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity                                       // bật @PreAuthorize (mục 7)
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**", "/actuator/health").permitAll()          // công khai
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()          // xem sản phẩm: ai cũng được
                .requestMatchers("/api/admin/**").hasRole("ADMIN")                        // chỉ admin
                .anyRequest().authenticated())                                            // còn lại: phải đăng nhập
            .httpBasic(Customizer.withDefaults())                                         // chương 10 sẽ thay bằng JWT
            .csrf(csrf -> csrf.disable())                                                 // xem mục 8
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))   // không tạo session
            .cors(Customizer.withDefaults());                                             // dùng CorsConfigurationSource bean
        return http.build();
    }

    @Bean
    PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}
⚠️ Thứ tự quy tắc rất quan trọng

authorizeHttpRequests khớp từ trên xuống, quy tắc đầu tiên khớp thắng. Đặt anyRequest().authenticated() trước permitAll() thì các URL công khai cũng bị khoá; đặt permitAll("/**") quá sớm là mở toang. Luôn xếp cụ thể → chung và để anyRequest() cuối cùng — tốt nhất là denyAll() hoặc authenticated() (mặc định an toàn: cấm trừ khi cho phép).

requestMatchers và dấu /

Mặc định Spring Security 6 so khớp theo mẫu của Spring MVC (MvcRequestMatcher khi có Spring MVC). /api/products/** khớp /api/products và /api/products/42. Cẩn thận đường dẫn có và không có / cuối, hoặc có đuôi (/api/x.json): luôn thử cả các biến thể bằng curl và viết test (chương 11) cho các endpoint nhạy cảm.

5. Người dùng trong CSDL

5.1. Entity và repository

AppUser.java
@Entity
@Table(name = "app_users")
public class AppUser {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;

    @Column(nullable = false, unique = true, length = 100)
    private String email;

    @Column(nullable = false)
    private String passwordHash;                    // CHỈ lưu hash — không bao giờ lưu mật khẩu gốc

    @Enumerated(EnumType.STRING)
    @ElementCollection(fetch = FetchType.EAGER)     // vai trò: ít, luôn cần khi đăng nhập → EAGER hợp lý ở đây
    @CollectionTable(name = "app_user_roles", joinColumns = @JoinColumn(name = "user_id"))
    private Set<Role> roles = new HashSet<>();

    private boolean enabled = true;
    // constructor, getter ...
}

public enum Role { USER, ADMIN }

public interface AppUserRepository extends JpaRepository<AppUser, Long> {
    Optional<AppUser> findByEmailIgnoreCase(String email);
    boolean existsByEmailIgnoreCase(String email);
}

5.2. UserDetailsService — cầu nối tới CSDL

DbUserDetailsService.java
@Service
class DbUserDetailsService implements UserDetailsService {

    private final AppUserRepository users;
    DbUserDetailsService(AppUserRepository users) { this.users = users; }

    @Override
    public UserDetails loadUserByUsername(String email) throws UsernameNotFoundException {
        AppUser u = users.findByEmailIgnoreCase(email)
                .orElseThrow(() -> new UsernameNotFoundException("Không tìm thấy: " + email));

        return org.springframework.security.core.userdetails.User.builder()
                .username(u.getEmail())
                .password(u.getPasswordHash())                                       // đã là hash
                .authorities(u.getRoles().stream().map(r -> "ROLE_" + r.name()).toArray(String[]::new))
                .disabled(!u.isEnabled())
                .build();
    }
}

Chỉ cần có **một bean UserDetailsService và một bean PasswordEncoder**, Boot tự dựng DaoAuthenticationProvider để dùng chúng — không cần cấu hình thêm. Khi client gửi Basic user:pass, provider gọi loadUserByUsername, rồi passwordEncoder.matches(raw, hash).

5.3. Đăng ký người dùng

AuthController.java
@RestController
@RequestMapping("/api/auth")
class AuthController {

    private final AppUserRepository users;
    private final PasswordEncoder encoder;
    // constructor ...

    @PostMapping("/register")
    @ResponseStatus(HttpStatus.CREATED)
    void register(@Valid @RequestBody RegisterRequest req) {
        if (users.existsByEmailIgnoreCase(req.email()))
            throw new ConflictException("EMAIL_TAKEN", "Email đã được dùng");     // + UNIQUE ở DB (chương 5)
        AppUser u = new AppUser(req.email().toLowerCase(), encoder.encode(req.password()), Set.of(Role.USER));
        users.save(u);
    }
}

public record RegisterRequest(@NotBlank @Email String email,
                              @NotBlank @Size(min = 8, max = 72) String password) { }

6. Lưu mật khẩu đúng cách

Không bao giờ lưu mật khẩu gốc, không bao giờ mã hoá hai chiều (AES) cho mật khẩu, không dùng MD5/SHA-1/SHA-256 trần. Dùng hàm băm chậm có muối được thiết kế riêng cho mật khẩu: BCrypt, Argon2, scrypt, PBKDF2.

# Cùng một mật khẩu băm hai lần cho hai chuỗi KHÁC nhau (muối khác) — dùng encoder.matches(), không so sánh chuỗi.
💡 Cost phải vừa đủ chậm

Mục tiêu: một lần băm mất ~100-300 ms trên server thật. Quá nhanh ⇒ dễ bị dò; quá chậm ⇒ kẻ tấn công gửi nhiều request đăng nhập làm cạn CPU của bạn (DoS). Vì vậy đăng nhập cần giới hạn tốc độ (rate limit/khoá tạm thời sau N lần sai).

Hai chi tiết tránh lộ thông tin ở màn đăng nhập: (1) trả cùng một thông điệp Email hoặc mật khẩu không đúng cho cả "email không tồn tại" và "sai mật khẩu" (chống dò danh sách tài khoản); (2) thời gian phản hồi gần như nhau — Spring Security mặc định băm một mật khẩu giả khi không có user để giảm sai lệch này.

7. Phân quyền: role, authority và method security

AuthorityRole
Bản chấtMột quyền tinh: product:write, order:cancelNhóm quyền thô: ADMIN, USER
Lưu dưới dạngChuỗi "product:write"Chuỗi **"ROLE_ADMIN"** (có tiền tố ROLE_)
Kiểm trahasAuthority("product:write")hasRole("ADMIN") — tự thêm ROLE_
⚠️ Bẫy ROLE_

hasRole("ADMIN") kiểm tra authority **ROLE_ADMIN**. Lưu role là "ADMIN" (thiếu tiền tố) thì hasRole("ADMIN") luôn 403. Hoặc lưu ROLE_ADMIN và dùng hasRole("ADMIN"), hoặc dùng hasAuthority("ADMIN") nhất quán. Đừng trộn.

7.1. Method security — phân quyền ở tầng service

Phân quyền theo URL (authorizeHttpRequests) thô và dễ sót khi thêm endpoint. Method security đặt quy tắc ngay trên method (thông qua proxy — nhớ bẫy self-invocation ở chương 2):

Method security
@Service
class OrderService {

    @PreAuthorize("hasRole('ADMIN')")                                       // chỉ admin
    public List<OrderResponse> findAll() { ... }

    @PreAuthorize("hasAuthority('order:cancel')")
    public void cancel(long id) { ... }

    // QUAN TRỌNG: chủ sở hữu hoặc admin — chống IDOR
    @PreAuthorize("hasRole('ADMIN') or @orderSecurity.isOwner(#id, authentication.name)")
    public OrderResponse get(long id) { ... }

    @PostAuthorize("returnObject.ownerEmail == authentication.name or hasRole('ADMIN')")
    public OrderResponse getAfter(long id) { ... }                          // kiểm tra SAU khi có kết quả
}

@Component("orderSecurity")
class OrderSecurity {
    private final OrderRepository repo;
    OrderSecurity(OrderRepository repo) { this.repo = repo; }
    public boolean isOwner(long orderId, String email) {
        return repo.existsByIdAndCustomerEmail(orderId, email);
    }
}
🔒 IDOR — lỗi phân quyền số một (OWASP A01: Broken Access Control)

Insecure Direct Object Reference: GET /api/orders/42 chỉ kiểm tra đã đăng nhập, không kiểm tra đơn 42 có phải của bạn không ⇒ người dùng đổi 42 thành 43 đọc được đơn người khác. Với mọi tài nguyên thuộc về người dùng: kiểm tra quyền sở hữu (như isOwner ở trên), hoặc lọc theo chủ sở hữu ngay trong truy vấn (findByIdAndCustomerEmail). Trả 404 (không phải 403) khi không phải của bạn để không lộ sự tồn tại của tài nguyên.

8. CSRF và CORS — hai thứ hay bị nhầm

8.1. CSRF

CSRF (Cross-Site Request Forgery): trang độc evil.com khiến trình duyệt của bạn gửi POST bank.com/transfer — và vì trình duyệt tự đính kèm cookie của bank.com, request trông như hợp lệ. Nguy cơ chỉ tồn tại khi xác thực dựa vào thứ trình duyệt tự động gửi (cookie/session, HTTP Basic được trình duyệt nhớ).

Kiểu xác thực của APICSRF?Cấu hình

**Token trong header Authorization: Bearer …* (JWT, chương 10) — *không dùng cookie❌ Không áp dụng (trình duyệt không tự gắn header này)csrf.disable() an toàn

**csrf.disable() chỉ an toàn khi API là stateless và không dựa vào cookie để xác thực.* Tắt CSRF "cho hết lỗi 403" trên ứng dụng dùng session là mở lỗ hổng. Hãy biết *vì sao bạn tắt.

8.2. CORS ≠ bảo mật server

CORS là chính sách của trình duyệt: cho trang ở origin A đọc phản hồi từ origin B hay không. Nó không bảo vệ API khỏi curl/script/ứng dụng khác — chỉ ngăn trang web lạ đọc dữ liệu bằng phiên của người dùng. Khi dùng Spring Security, cấu hình CORS ở đây (filter chạy trước MVC, nếu để ở MVC thì request preflight OPTIONS có thể bị chặn 401):

CORS cho Spring Security
@Bean
CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("http://localhost:3000", "https://shop.example.com"));   // cụ thể, KHÔNG "*" khi có credential
    c.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
    c.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    c.setMaxAge(Duration.ofHours(1));                                                    // cache preflight
    UrlBasedCorsConfigurationSource src = new UrlBasedCorsConfigurationSource();
    src.registerCorsConfiguration("/api/**", c);
    return src;
}
// + http.cors(Customizer.withDefaults())  trong SecurityFilterChain — đã có ở mục 4

9. 401 và 403 dạng JSON

Mặc định Spring Security trả 401 với header WWW-Authenticate và thân rỗng/HTML; 403 thân rỗng. API nên trả **ProblemDetail** như phần còn lại (chương 5). Hai điểm mở rộng: AuthenticationEntryPoint (→ 401) và AccessDeniedHandler (→ 403). Chúng chạy trong filter chain, trước MVC, nên @RestControllerAdvice không bắt được — phải tự ghi response:

SecurityErrorHandlers.java
@Component
class JsonAuthenticationEntryPoint implements AuthenticationEntryPoint {
    private final ObjectMapper mapper;
    JsonAuthenticationEntryPoint(ObjectMapper mapper) { this.mapper = mapper; }

    @Override
    public void commence(HttpServletRequest req, HttpServletResponse res, AuthenticationException ex) throws IOException {
        write(res, HttpStatus.UNAUTHORIZED, "UNAUTHENTICATED", "Cần đăng nhập hoặc token không hợp lệ/hết hạn");
    }

    private void write(HttpServletResponse res, HttpStatus status, String code, String detail) throws IOException {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, detail);
        pd.setProperty("code", code);
        res.setStatus(status.value());
        res.setContentType(MediaType.APPLICATION_PROBLEM_JSON_VALUE);
        mapper.writeValue(res.getOutputStream(), pd);
    }
}

@Component
class JsonAccessDeniedHandler implements AccessDeniedHandler {
    private final ObjectMapper mapper;
    JsonAccessDeniedHandler(ObjectMapper mapper) { this.mapper = mapper; }

    @Override
    public void handle(HttpServletRequest req, HttpServletResponse res, AccessDeniedException ex) throws IOException {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.FORBIDDEN, "Bạn không có quyền thực hiện thao tác này");
        pd.setProperty("code", "FORBIDDEN");
        res.setStatus(403);
        res.setContentType(MediaType.APPLICATION_PROBLEM_JSON_VALUE);
        mapper.writeValue(res.getOutputStream(), pd);
    }
}

// Trong SecurityFilterChain:
// .exceptionHandling(e -> e.authenticationEntryPoint(entryPoint).accessDeniedHandler(deniedHandler))
📌 Exception ném từ @PreAuthorize thì sao?

@PreAuthorize chạy bên trong MVC (qua proxy) nên AccessDeniedException đi qua @RestControllerAdvice — thêm @ExceptionHandler(AccessDeniedException.class) trả 403 ở đó (hoặc để nó "nổi" lên ExceptionTranslationFilter — nhưng khi đã có @ExceptionHandler(Exception.class) chung, nó sẽ bị nuốt thành 500!). Đây là bẫy rất hay gặp: **luôn xử lý AccessDeniedException và AuthenticationException riêng**.

Bài tập

Khám phá cấu hình mặc định

Thêm spring-boot-starter-security vào dự án đang chạy. Không viết cấu hình gì.

  • Gọi các endpoint cũ: kết quả gì? Lấy mật khẩu từ log và gọi bằng curl -u.
  • Bật logging.level.org.springframework.security=DEBUG — liệt kê các filter trong chuỗi.
  • Đặt spring.security.user.name/password để cố định tài khoản dev.
Gợi ý

Log DEBUG in Security filter chain: [DisableEncodeUrlFilter, WebAsyncManagerIntegrationFilter, SecurityContextHolderFilter, HeaderWriterFilter, CsrfFilter, … AuthorizationFilter]. Bạn sẽ thấy CsrfFilter — vì sao POST bằng curl bị 403 khi chưa tắt CSRF?

Đăng ký, đăng nhập (Basic) với CSDL

Cài AppUser, DbUserDetailsService, POST /api/auth/register, GET /api/me (HTTP Basic).

  • Xem cột password_hash trong DB — nó trông thế nào? Đăng ký hai user cùng mật khẩu: hash có giống nhau không?
  • Gọi /api/me đúng/sai mật khẩu: mã trả về? Thông điệp?
  • Viết test nhỏ encoder.matches(raw, hash).
Gợi ý

Hai hash khác nhau (muối ngẫu nhiên) nhưng cùng matches được với mật khẩu gốc. Sai mật khẩu ⇒ 401 — thông điệp không tiết lộ email có tồn tại hay không.

Phân quyền ba tầng

Có GET /api/products (công khai), POST /api/products (ADMIN), GET /api/orders/{id} (chủ đơn hoặc ADMIN).

  • Cấu hình URL-level cho hai cái đầu và method security cho cái thứ ba.
  • Đăng nhập là user1, thử đọc đơn của user2: kết quả? Đổi thành trả 404 thay vì 403.
  • Cố tình sắp xếp sai thứ tự trong authorizeHttpRequests (đặt anyRequest trước) — quan sát.
Gợi ý

Với IDOR: truy vấn findByIdAndCustomerEmail(id, email) trả Optional.empty() khi không phải chủ ⇒ NotFoundException ⇒ 404. Khi sai thứ tự, các quy tắc đứng sau anyRequest() không bao giờ được áp dụng (Spring còn ném lỗi cấu hình khi build trong nhiều trường hợp).

401 và 403 dạng ProblemDetail

Cài AuthenticationEntryPoint và AccessDeniedHandler như mục 9 và đăng ký vào exceptionHandling.

  • Gọi không có thông tin đăng nhập ⇒ 401 JSON; đăng nhập USER gọi /api/admin/x ⇒ 403 JSON.
  • Thêm @PreAuthorize("hasRole('ADMIN')") lên một method service và gọi ⇒ thấy gì? Xử lý bằng @ExceptionHandler.
  • Giải thích vì sao @RestControllerAdvice không bắt được lỗi ở entry point.
Gợi ý

Entry point/handler chạy trong filter chain (trước DispatcherServlet) nên nằm ngoài phạm vi @ControllerAdvice. @PreAuthorize thì chạy trong MVC — nhớ bắt AccessDeniedException trước handler Exception.class.

Kiểm toán bảo mật

Cho cấu hình sau, nêu ít nhất 5 điểm yếu và sửa:

SecurityConfig.java
http.csrf(c -> c.disable())
    .authorizeHttpRequests(a -> a
        .requestMatchers("/**").permitAll()
        .requestMatchers("/api/admin/**").hasRole("ADMIN"))
    .httpBasic(Customizer.withDefaults());
// application.yml:  management.endpoints.web.exposure.include: "*"
// PasswordEncoder: NoOpPasswordEncoder.getInstance()
// CorsConfiguration: allowedOrigins("*") + allowCredentials(true)
Gợi ý

(1) permitAll("/**") đứng trước ⇒ quy tắc ADMIN vô nghĩa; (2) Actuator mở hết; (3) NoOpPasswordEncoder lưu mật khẩu thô; (4) CORS * + credentials (trình duyệt cũng chặn nhưng cấu hình sai); (5) tắt CSRF mà vẫn dùng Basic (trình duyệt tự gửi) — nếu API cho trình duyệt thì cần xem lại; (6) thiếu anyRequest().authenticated() cuối cùng.

Quiz

Q1

401 khác 403 thế nào?

Xem đáp án
✓ Đáp án

401: chưa xác thực — thiếu/sai/hết hạn thông tin đăng nhập ("bạn là ai?"). 403: đã xác thực nhưng không đủ quyền ("không được phép"). Client xử lý khác nhau: 401 → đăng nhập lại/refresh token; 403 → báo không có quyền.

Q2

Mô tả vị trí của Spring Security trong đường đi của request.

Xem đáp án
✓ Đáp án

Là một **chuỗi Filter** (FilterChainProxy) chạy trước DispatcherServlet: nạp SecurityContext → filter xác thực → ExceptionTranslationFilter → AuthorizationFilter. Request bị từ chối ở đây không bao giờ tới controller. Vì vậy 401/403 từ filter không đi qua @RestControllerAdvice.

Q3

Vì sao dùng BCrypt thay vì SHA-256 để lưu mật khẩu?

Xem đáp án
✓ Đáp án

SHA-256 nhanh ⇒ kẻ tấn công thử hàng tỉ mật khẩu/giây (GPU). BCrypt/Argon2 cố tình chậm và có muối ngẫu nhiên (cùng mật khẩu → hash khác nhau, chống rainbow table); độ khó chỉnh được theo phần cứng. Phải dùng encoder.matches() để so khớp.

Q4

hasRole("ADMIN") và hasAuthority("ADMIN") khác nhau thế nào?

Xem đáp án
✓ Đáp án

hasRole("ADMIN") tự thêm tiền tố và kiểm tra authority **ROLE_ADMIN**; hasAuthority("ADMIN") kiểm tra chuỗi **ADMIN** đúng nguyên văn. Lưu ADMIN rồi dùng hasRole sẽ luôn 403 — phải nhất quán.

Q5

Khi nào được phép csrf.disable()?

Xem đáp án
✓ Đáp án

Khi API stateless và không xác thực bằng cookie (token trong header Authorization) — trình duyệt không tự gắn header đó nên CSRF không áp dụng. Với session/cookie (kể cả JWT trong cookie) CSRF vẫn cần được bật hoặc thay bằng SameSite + token.

Q6

IDOR là gì và phòng thế nào?

Xem đáp án
✓ Đáp án

Truy cập tài nguyên của người khác bằng cách đổi id (/orders/42 → /43) vì server chỉ kiểm tra đã đăng nhập mà không kiểm tra sở hữu. Phòng: kiểm tra quyền sở hữu mỗi truy cập (@PreAuthorize với bean kiểm tra, hoặc truy vấn lọc theo chủ sở hữu), trả 404 để không lộ sự tồn tại, và viết test phân quyền cho từng endpoint.

Tổng kết

Sau chương 9, bạn đã nắm:

  • Xác thực = bạn là ai (401); phân quyền = được làm gì (403). Spring Security là chuỗi filter chạy trước DispatcherServlet.
  • Cấu hình bằng bean **SecurityFilterChain** (lambda DSL); quy tắc authorizeHttpRequests khớp cụ thể → chung, kết thúc anyRequest().authenticated().
  • Người dùng từ DB qua **UserDetailsService + PasswordEncoder; mật khẩu băm bằng BCrypt/Argon2**, thông điệp đăng nhập chung chung.
  • Role = authority có tiền tố ROLE_; method security @PreAuthorize cho phân quyền mịn; kiểm tra sở hữu để chống IDOR.
  • CSRF chỉ tắt cho API stateless không dùng cookie; CORS là chính sách trình duyệt, cấu hình trong Security.
  • 401/403 dạng JSON qua AuthenticationEntryPoint/AccessDeniedHandler; bắt AccessDeniedException riêng cho method security.
